## Item 19: the security floor, built (deploy owed)

- Three commits, one design: the module authenticates every route and the `/events`
  upgrade with `Authorization: Bearer` — the port secret (`WrathBench.Secret` ←
  `WRATHBENCH_MODULE_SECRET`) for operator tooling, a per-run lease secret for the
  run. `POST /lease {token, account}` issues a 64-hex CSPRNG secret bound to the
  token; the first `POST /session` binds the character; another token is `403
  token_mismatch`, the operator routes are `403 operator_only`. The secret is issued
  at lease time, before the session exists, because the SDK subscribes to `/events`
  before `POST /session` on purpose (the login burst is the state cache's only source
  for the self block) and that order was worth keeping (950f421 module, 738cff0
  sdk/runner/infra/smokes, `module/PROTOCOL.md` "Authentication", `docs/OPERATIONS.md`
  "Secrets").

  proves `.env` by absolute and relative path, `$HOME` and `/tmp` are `EACCES` from
  `readFileSync`, `Bun.file` and a spawned `cat`; it passes on the host and inside

## Issue #30 and the public dead-link audit

GitHub issue #30: a viewer started with `WRATHBENCH_VIEWER_PUBLIC=1` served
`/api/run/<id>`, `/track`, every aggregate route and the SSE tail without the
projection the static snapshot applies, so whether a public deployment leaked
depended on which URL was asked for. Public mode is now a boundary rather than
a route list: every `/api` body in `runner/viewer/api.ts` is emitted through a
new `pub(body, project)` helper, which applies the same projector
`renderSnapshot` uses when the handle is public. `/stream` joins raw lines and
tiles in answering `403 withheld in public mode` — the live tail has no
projected form, and a public reader's window is the snapshot's one published
tail instead.

`/entries` and `/track` were **projected, not denied**, deliberately. The
snapshot renderer calls this handle in-process and treats any non-200 that is
not a 404 as a fault that throws, so denying either would not degrade one run's
artifacts — it would kill the whole render pass, `live.json` and the aggregates
with it. `/scratchpad` stays served in public mode: the model's own notes are
published as written (operator, 2026-08-30).

`runner/test/viewer-public-mode.test.ts` walks every public JSON route over a
poisoned runs directory (`runner/test/fixtures/poisoned-runs.ts`: a bearer
token, a LAN api base, the operator's objective and paths, free-text pause and
preflight output, a supervisor pid, game prose by opcode, wiki text) and fails
on the *value*, not the key. A companion test asserts the private handle does
carry all of it, so the fixture cannot rot into a vacuous pass, and a third
asserts what the operator decided is public still ships — the character name,
quest/NPC/item names, snippet code, turn text, the scratchpad. Two of the
issue's acceptance criteria are therefore **not** implemented, on purpose:
character names and model-authored prose are published by operator decision
(2026-08-30, `docs/DATA-AND-LEGAL.md` and `docs/PUBLIC-DASHBOARD.md`), so a
test asserting their absence would have required reversing that decision. That
is Mark's call, not an agent's. The Helm/NuSphere criterion has no chart in
this repo to satisfy, and the browser smoke is still owed.

The dead-link audit over `dashboard/src` found nothing to change. Every control
that needs the live viewer is already guarded: the raw-line anchor (`RawLink`

## Item 35: milestone records finished

The three kinds item 35 still owed — `spell`, `talent`, `trade` — are written,
derived, projected and rendered. None of them needed the SDK or the module:
`StateCache.snapshot()` already carries `spells`, `talents` and `trade`, and the
sandbox ships the whole snapshot to the host, so all three producers are reads
over a sample the loop was already taking.

The spellbook copies the achievement backlog: the first sample that sees a
non-empty book writes `spells_at_login` (ids only) and every id appearing after
that is a `spell`. An empty book is not a baseline — the cache simply has not
had `SMSG_INITIAL_SPELLS` yet, and taking it as one would make the whole book
arrive a moment later as fresh learns. That record is also the liveness witness
the other two kinds borrow, the job `achievements_at_login` does for flights:
the three producers shipped together, so a run with a baseline and no talent or
trade mark genuinely spent and traded nothing, while a run from before today has
none of the four records and reads null throughout. A separate `talents_at_login`
was considered and dropped — its trigger depends on `SMSG_TALENTS_INFO` arriving
unprompted at login, which is a belief rather than something verified here.

Talents write a mark when a rank climbs, carrying both the 0-based wire rank and
the points it means, and forget a talent the frame stops listing, so a respec is
silent and a relearn afterwards reads as a spend again. Trades read
`TRADE_STATUS_TRADE_COMPLETE` (8) latching on the trade window — nothing clears
it until the next trade packet — deduped on the cache's own stamp rather than
its `seq`, which restarts when a session is recreated. Two completions inside
one sampling gap record one, the usual lower bound.

**What is not on a trade record:** what was traded. The SDK drops both sides of
the window as soon as the trade stops being open, so by the time a sample lands
only the completion survives. Recording the contents would need either an SDK
change (keep the sides across the completion) or an event tap in the sandbox
child like the death watcher's, and "first trade" — which is what the item asked
for — needs neither.

**What was left out on purpose:** the group-join and instance records (ladder
rung 6). The harness runs one character per session, and per the operator that
work belongs to a proposal rather than to this item. `docs/proposals/GROUP-PLAY.md`
is that proposal: what rung 6 needs, why one process per run is the real blocker
rather than the missing taps, issue #9's opcode list kept by reference, and the
three scoring questions that are the operator's alone. VISION.md's dungeon goal
and the ladder's rung-6 rule both point at it.

Consumers: `scanRunTotals` and the incremental `TrajectoryTail` both derive
`spells` / `talents` / `trades` in their existing passes, `RunTotals`,
`ResultRun` and `RunDetailResponse` carry them, and the public projection copies
them whole — spell and talent ids, counts, turn indices, timestamps, nothing
nameable, which is why these can be projected while `deaths` (corpse positions)
still is not. The run page grows one compact `milestones` tuple in the page's
existing tuple-row style: deaths, level marks, spells learned, talents spent,
trades, with the turns they landed on. It answers item 35's "nothing renders
them yet" for deaths and levels too.
