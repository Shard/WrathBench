## A probe cell with no exit: the attempt cap

class-probe relaunched `x-preview-f` × `human-warrior` 37 times. The cause is a skew between two questions the fan-out was only asking one of: `campaignWork` derived remaining work from *counted* runs, and `probeRunsOf` handed it counted runs only — so a launch that failed left no trace at all, and the fan-out re-picked the first incomplete cell forever. 43 of class-probe's 60 launches ended `attempt-failed`, most of them OpenCode rate-limit pauses that the campaign, not asking to resume, turns into failures.

The fix keeps both questions. `probeRunsOf` now returns every campaign run carrying `counted`, and `campaignWork` tallies twice over the same list: `done` and the breadth-first sweep order stay counted-only (so "how much of this campaign exists" and an operator-cut probe's re-run are unchanged), while a parallel attempts tally feeds the new `campaigns.<name>.maxAttemptsPerCell`. A cell past its cap is skipped exactly the way a finished one is, which is what makes `campaignComplete`, the pinned-campaign job and the policy loop inherit it without any of them learning a second word for "nothing left here". Absent the key, nothing changes — asserted, because that is what protects nav-probe and every future uncapped campaign. class-probe gets `maxAttemptsPerCell: 3`.

Two things found on the way. The `/campaigns` page passed *every* ended run to `campaignComplete` with no counted filter, so it had been reporting cells swept while the scheduler was still relaunching them; it now mirrors `isCounted` over the fields a result row has (`unscored` is useless here — it is non-null for every probe, since `probing` is an unscored episode). And the `nightelf-hunter` cell was `class: 4`, which is a rogue — the campaign has been probing two rogues and no hunter. Fixed; the runs already on disk under that cell id are rogues and should be read as such.

Two consequences to know about. The `campaigns` schema is strict, so `maxAttemptsPerCell` in `fleet.json` is REJECTED by a supervisor still running the old code — the live fleet logged exactly that at 05:42 and is holding its last good config until it restarts on the new build. The config edit and the code are deploy-coupled; nothing else in `fleet.json` applies until then either. And `/campaigns` computes `want` as cells x runsPerCell x models, so an abandoned cell now makes `complete` reachable at, say, 18/24 with nothing on the page to say why — `CampaignsResponse.config` does not carry `maxAttemptsPerCell`. Display gap, not a wrong number.
