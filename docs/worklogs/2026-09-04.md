## What Cerebras costs, and why caching does not help

$0.99/$1.49 per Mtok, and — this is the whole cost story — **no cache discount**.
Cerebras caches aggressively (a 20k-token prefix came back 22016/22280 cached, 98.8%,
across separate processes) but bills every input token at the standard rate whether it
was served from cache or not. So the ~19k-token context an episode plateaus at is paid
in full on every call, which is a different shape from every OpenRouter model in the
fleet, where a cacheRead tier two orders of magnitude below input is what makes a long
episode affordable.

Measured off the first four minutes of the live e90 rather than estimated: 277 calls an
hour, 18.7k prompt and 3.2k completion tokens a call, $0.0233 a call — **$6.46 an hour,
so about $9.69 for a 90-minute e90**. At that pace an episode makes ~416 calls against
the 500-call ceiling, so the wall clock ends it and the cap is not what binds.

Two things in that number are worth separating. The pace landed with the fast group
(277/h against muse-spark's 242–268), not with the local entry's 71–136 calls per
episode — which confirms the local figure was the LM Studio box's speed and not the
model's, and that episode wall-clock rather than inference sets the pace. And
reasoning is on by default, which is where the 3.2k completion average comes from;
it is about a fifth of the bill, so `effort: "none"` would bring an e90 to roughly
$7.75. That is left alone, because the local entry sets no effort either and matching
it is the point of having both.

The practical consequence: $15 is **one and a half episodes**, not several. One t0 run
is the budget.

No per-model call cap was added to hold that number down. The tier table says money is
deliberately not modelled and that a bespoke volume is a named tier rather than a
number edited into one model's entry, and `runner/src/episodes.ts` marks a run with a
non-default `maxToolCalls` as not comparable — so capping this entry to save a few
dollars would have bought the saving with the run's place in the matrix.

The run will show **no cost in the viewer**. `usage.cost` is an OpenRouter field and
Cerebras does not report one, and the price table cannot help: `sync-prices.ts` writes
only ids the OpenRouter catalogue carries and deletes the rest, so a hand-added Cerebras
row would be removed on the next sync — and OpenRouter's `qwen/qwen3.8-27b` row is
neither the same id string nor the same rate. Cost for this run is hand-computed from
the trajectory's token totals, the way the muse-spark baseline was.

## The paid lane, and how the stream was moved aside

`policy.paid.maxConcurrent` is 1 and `accounts.paid` is one account, so a paid entry
only runs when SHAKEOUT2 is free — and SHAKEOUT2 was carrying the muse-spark-13
freeplay stream, 15h21m in at L8, which has no wall clock and which `policyJobDropped`
will not preempt. `muse-spark-13` was flipped to `idle: "none"` to hand the account
over: that takes the pause path, and the trajectory's last record is
`pause / operator-pause / "SIGTERM: supervisor stop"` — a clean stop, the character
logged out, 15h19m of elapsed episode kept.

`idle` was then put straight back to `"unlimited"` so the stream resumes on its own
when the e90 ends, with nobody needing to be around for it. What protects the L8
character across that window is **not** `streamStanding`, which is what it looked like
from the source: a paused run writes a `pause` record and no termination reason, so
`streamsFrom` — which requires `terminationReason !== null` — registers no head at all,
and `--status` says `no head — first session in flight`. The actual protection is that
the paused run still counts as the ref's one session, so `muse-spark-13` reads
`no: running (one stream per model)` and cannot start a fresh character while the pause
is outstanding; the resume path takes the run back when the account frees. The
`boundary` case in `streamStanding` only matters once a stream *has* a head, which is
after a stale sweep has ended the paused run — the second of the two paths named in
`pausesOnDrain`, not the first.

## Note: the fleet container does not hold API keys

Worth recording because it is the opposite of what the compose file suggests. The
`fleet` service lists no keys under `environment:` and has no `env_file`, and
`OPENROUTER_KEY` is genuinely absent from the supervisor's own environment. Keys reach
episodes because Bun auto-loads `.env` from the working directory in *each new
process*, and every episode is one. So a key added to `.env` is usable by the next
episode with no restart and no force-recreate — which is what let this land without
disturbing the running stream.

### WAL is not available here, and that is structural

The #35 sweep set a busy timeout but deliberately **no WAL**, and the reasoning is
worth keeping: WAL is a persistent property of the database file, and a WAL database
cannot be opened at all — not even read-only — without write access to its directory,
because SQLite must create the `-shm` sidecar. `infra/compose.yml` mounts
`../data/runs:ro` for the publisher, and `infra/publish-dashboard.ts` runs the
viewer's handler in-process, so it reaches those opens on a read-only mount. WAL on
the writer would turn every public-dashboard read of a live run into `SQLITE_CANTOPEN`,
swallowed by the existing catches — blanking the public site rather than crashing it.
Rollback journal plus a real busy timeout is the combination that works from a
read-only mount. `immutable=1` is not an escape; it asserts the file never changes,
false for a live run. WAL becomes available only if that mount becomes writable, which
is an operator call. A test pins the journal mode so this cannot drift silently.

### #38 changes the deploy order

**Dashboard first, publisher second.** The reader accepts both manifest shapes, so
that order is correct in both states; the reverse is not. A tab running pre-#38
JavaScript across the publisher deploy reads `m.gen`, derives a key that no longer
exists, and 404s until reloaded — a compat copy under one prefix was considered and
rejected, since that is exactly the cost being removed. A rollback wants
`data/publish/state.json` deleted, or an old binary reads the per-artifact hashes as
generation stamps and plans every aggregate as surplus. No urgency as of today: the
publisher bind-mounts the repo read-only and has held the old code in memory since
2026-09-02, so nothing changes until it restarts.

### Process: `--amend` in a shared worktree

The #35 agent ran `git commit --amend` after the orchestrator had already committed on
top of its commit, which rewrote *the orchestrator's* commit: the message was replaced
by the agent's and two commits ended up with the same subject. No content was lost —

`git add -A`: in a shared worktree, an agent may only *add* commits.

## Item 113 fixed the same day it was filed (operator's call)

- shipped: item 113 — c3b118e — `sdk/src/events.ts`, `sdk/test/events.test.ts`

Filed in the morning as a parked consequence of #34, then **the operator asked
for it fixed rather than parked** — correctly, since unlike the pre-existing
parked items this was a defect the batch had just introduced.

`connect()` now tracks the *stream* rather than one attempt. Callers join a
waiter set; the attempt in flight settles them. `openSocket()` no longer returns
a promise at all, which is what made the failure sticky — nobody holds a handle
on a single attempt. `connect()` starts an attempt only when nothing already
owns the next one (`socket === undefined && reconnectTimer === undefined`), so
the two-sockets-on-one-stream race that ruled out the obvious fix cannot occur;
a test asserts the socket count directly.

The part item 113 left open was the give-up. Riding the ladder alone would hang
a caller forever on a dead server or a 401 upgrade, which at the WebSocket level
are indistinguishable from a transient outage. So a waiter now tolerates one
failure per growing rung (`connectPatience`, derived from the existing
`reconnectMinDelayMs`/`reconnectMaxDelayMs` — 6 at the defaults) and then
rejects with the last error plus the attempt count. **The ladder itself gets no
terminal state: the stream keeps retrying at the cap forever, and the rejection
is the caller's verdict rather than the stream's.** `close()` mid-connect now
rejects pending waiters instead of leaving them unsettled — on the pre-fix code
that test does not fail, it hangs.

**One consequence to weigh (operator's, not settled here):** the all-stalls worst
case is ~38s, which exceeds the 30s snippet timeout, so a total outage of that
shape reaches the model as a snippet timeout rather than an error. That was
judged acceptable because it is exactly the loaded-container case where waiting
is the right behaviour, and the next snippet's `connect()` resolves at once if
the ladder has recovered. Decoupling the bound from the ladder's shape would
mean a new `EventStreamOptions` field, which the agent correctly declined to add
unilaterally.

Filed while there: **item 114**, `sdk.connect()` dropping a client without
closing its stream — pre-existing, but item 113's new rejection path makes it
more reachable.

### Two premises of the brief were wrong, and the agent said so

The brief claimed omen-alpha would queue behind the free OpenCode stream.
It would not: `concurrencyKeyOf`'s platform branch is gated on
`driver === "openai" && billing === "free"`, so a paid entry fell through to the
uncapped `"openai"` driver key. The separate key is still right, but for a
different reason. And `opencode-go: 1` documents intent rather than binding
anything today, since `policy.paid.maxConcurrent: 1` is a single global cap over
every paid model in flight — running the go surface alongside another paid model
means revisiting `policy.paid`, which is the operator's.

The entry also carries an explicit `"billing": "paid"` despite the brief saying
not to, and that is correct: `billingOf` returns paid on the rule alone, but the
roster gate at `infra/run-fleet-config.ts:636` reads `e.billing === "paid"`
*literally*, and `isSharedFreePool` matches `//opencode.ai/` regardless of path,
so without the field the entry is refused as "free models only". `gemini-38-flash`
carries it for the same reason.

### The trap that would have silently under-reported spend

`platformOfBase` returns a hostname and **discards the path**, so `zen/go/v1` and
`zen/v1` both report platform `opencode.ai`. A price table keyed on the platform
string would therefore have priced omen-alpha as the *free* zen/v1 tier — silently,
on the only metered entry on that host, which is exactly the failure item 112
exists to remove. Caught by the roster agent and relayed to the pricing agent
mid-flight. `PROVIDER_PRICES` matches on **full api base (origin + path) AND
model**, never on platform. Verified directly against `priceFor`: omen-alpha on
`/zen/go/v1` → 0.20/0.66; on `/zen/v1` → **null**, not free; `hy3-free` on
`/zen/v1` → free; Cerebras → 0.99/1.49.

### How the alpha's price conflict is recorded

models.dev publishes 0.20/0.66; the endpoint returned `usage.cost 0` on every
live response the same day. The row holds the published rate and its note states
that the two disagree, so the viewer's existing two-figure design carries the
truth — **actual $0, expected listing price, and the gap is the information**.
Neither a free nor a billed alpha is asserted; the day the bill changes, a dated
window is appended. Rates are windowed with the same `SyncedWindow[]` shape as
the synced table, so a price move never rewrites what an old run billed.

`priceFor`'s order is now local → contributor → free → **PROVIDER_PRICES** →
synced OpenRouter → Claude, with a test asserting no provider row names an
`openrouter.ai` base.
