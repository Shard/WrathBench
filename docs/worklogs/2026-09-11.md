## Lean CI, on the checks the repo already had

The repo has claimed a green-from-a-bare-clone suite since the beginning and had
nothing enforcing it; every check ran on whichever workstation was open, against
a tree with `.env` and `data/` sitting in it. `.github/workflows/ci.yml` now runs
on every pull request and every push to master.

Two jobs, deliberately. **Bun checks** reads `.bun-version` through
`oven-sh/setup-bun@v2` and then asserts `bun --version` equals the pin — the
action accepting a version file is not the same as the runner having that
version, and a silent drift there would quietly invalidate every other check in
the job. Then `bun install --frozen-lockfile` and, ordered cheap to expensive so
a bad type or a stale doc fails before the 3,016-test suite: `bun run typecheck`,
`bun run docs:api:check`, `bun run dashboard:build`, `bun test`.

Nothing new was written to make that pass. `docs:api:check` already existed and
already has teeth, which was worth proving rather than assuming: it regenerates
`sdk/API.md` and diffs, so a hand-edit to `API.md` is simply overwritten and
reads clean — what it actually catches is a change to the generator's curated
table that was never regenerated into the committed doc, and perturbing that
table does fail it. Suite, typecheck, drift check and dashboard build were all
green from a worktree with neither `.env` nor `data/`, so nothing was skipped and
nothing is faked green.

**Helm chart** is a separate job so a chart problem cannot present as a test
problem: `helm lint` and `helm template` against `infra/chart/wrathbench` with
`image.tag=ci-lint`, a dummy immutable tag, because the chart's own guard refuses
`""` and `latest` and would otherwise fail to render at all. Confirmed that the
guard is what fires without the override, so the override papers over nothing
else.

`concurrency` cancels superseded runs per ref, permissions are `contents: read`,
and checkout takes no submodules — `deps/azerothcore` is a reference checkout for
the C++ build and nothing under test reads it, so cloning AzerothCore would have
dominated the job for nothing.

Scope held to PR checks: no tag/release workflow, no digest, no chart-as-OCI, no
GitOps wiring, and no C++ module build — that one needs the worldserver image and
the smoke scripts need the live stack, so neither belongs on a hosted runner.

## The map's transport steps between a stream's attempts

A replay was one run id's track, and the play bar knew nothing about the chain
a durable freeplay stream's attempts form — so following one character across
sessions meant going back to the run page to find the next id. The chain was
already computed at read time (`stream` on `/api/run/<id>`, 2026-09-05), just
not anywhere the map could see it.

The choice was between the track carrying the neighbouring ids and the page
fetching the run detail beside the track. The track carries them: four scalars
— `streamId`, `attempt`, `attempts`, `previous`, `next` — against a
`detail.json` that is the largest per-run artifact there is (every state
sample, the entries window, the whole `StreamView` with its totals). The public
site reads static objects, so "fetch the detail too" would have doubled a
replay's download to learn two run ids, and this way the snapshot needs no new
artifact at all: the publisher fetches `/api/run/<id>/track` and projects it,
so the field ships the moment the viewer serves it. The version key is hashed
over the detail, which carries `stream` — so a new attempt rotates the key and
the track republishes beside it rather than going stale.

The route computes it with the *same* gate and the same `streamViewOf` call the
detail route uses, so a scored run's replay pays nothing and the bar's steps
can never name a different neighbour than the run page's attempt strip (on a
fork the served chain and the lineage walk disagree, deliberately). In the bar
the steps are plain links to `/map?run=<id>`: the swap stays the route effect's,
and `cursormemory` therefore keeps each attempt's own place across a step away
and back. A track with no stream renders no control, which is also what an
older snapshot looks like to the page.

## `connect()` closes the stream it failed to open — item 114

`sdk.connect()` constructed a `WrathClient`, awaited `client.events.connect()`
and returned. When that rejected, the client was discarded — and with reconnect
enabled its `EventStream` kept climbing the ladder forever, with nobody left
holding a reference able to `close()` it. One leaked socket ladder per failed
`connect()`, for the life of the process. Item 113 made it reachable: since
then `events.connect()` rejects on a whole failed climb, where an unreachable
server used to simply hang.

The fix is the `try`/`catch` the item described. The general question it raised
— whether `WrathClient` should own that cleanup — was already answered inside
the class: `close()` closes the stream and clears the coalescing timers, so it
is the client's own dispose path and the factory just calls it. Whatever the
constructor starts next is covered without touching `connect()` again.

The test that pins it counts sockets rather than reading `connected`. A fake
that refuses every attempt drives `connect()` to its rejection, the socket count
is taken there, and after sleeping past the reconnect delay it must be
unchanged. `connected` is false either way, which is why it is not the
assertion; without the fix the count went 2 → 9 in 80 ms.

shipped: item 114 — a1b36bf — `sdk/src/client.ts` (`connect()`); test in `sdk/test/client.test.ts`

### A readback verifier for the published bucket

`infra/publish-accept.ts`, fixture-tested in `infra/publish-accept.test.ts` and
green from a bare clone. It walks the generation the manifest points at — every
aggregate key the manifest names, `live.json`, and the four objects each
`runs.json` row points at — and asks two independent questions of every body.

The first is re-projection: feed the published body back through the same
`runner/viewer/public-projection.ts` function the renderer used and diff. The
projection builds fresh objects from an allowlist, so it is a fixed point on its
own output, and any extra field, un-nulled `apiBase`, un-tokenised `pauseReason`
or entry key outside `ENTRY_FIELDS` is a difference with a JSON path on it. That
is the check that needs no list of bad words, and it reuses the rules the
projection suite already pins rather than restating them.

The second is value scans, kept deliberately independent of the projection
because a projection that is wrong would otherwise agree with itself: filesystem
paths, ported or private URLs, credential shapes, tile references, an
un-redacted `search_reference` result, a string-valued `objective`. Hits inside
model-authored `text`/`code` are counted as residual notes rather than findings,
because `docs/PUBLIC-DASHBOARD.md` publishes that surface as written — counting
them keeps the accepted residual visible instead of hidden by a filter.

Read-only structurally: the source interface has `get` and `head` and nothing
else, so there is no write path to reach by accident. The CLI builds it from
`Bun.S3Client` and takes the publisher's own `S3_*` env.

## The viewer's fact cache now has a file behind it

The counts behind `/api/models` are a pure function of each run's
`(size, mtime)`, and a finished run's never change — so the viewer was
recomputing, on every process start, an answer it had already computed and
thrown away. `runner/viewer/fact-store.ts` loads that memo from a file at
construction and writes it back on a two-second debounce. Not on shutdown: the
pod is killed, not asked, so the worst a `SIGKILL` costs is the last couple of
seconds of counting.

Nothing about the caching rule moved. Every entry read off disk is still checked
against the run's live signature by the same comparison the in-memory map made,
so a run whose files moved is recomputed and only that run is, and liveness is
still decided from the trajectory's mtime against `now` on every call. A live
run is never written down at all — its signature moves on every poll, so the
entry would be stale before it landed and the file would be rewritten every
thirty seconds forever.

The file is versioned (`FACT_CACHE_VERSION`), stamped with the runs directory it
was built from, and disposable: corrupt, truncated, mis-versioned or foreign all
read as "no cache" and cost a recount, never a failed page. The version stamp is
the only thing that can notice a change in what a fact *contains* — the files did
not move, the code did — and nobody editing `readRunFact` would remember it
unaided, so a test pins `RunFact`'s key list and fails naming the constant.

JSON rather than `bun:sqlite`, by measurement rather than taste: the whole cache
is 233 KiB for 346 stamped runs, so a whole-file rewrite on a debounce costs
less than the row bookkeeping would. The crossover is somewhere in the tens of
MB — tens of thousands of runs — and the store takes a second collection when
that day comes.

Timings, on the operator's corpus (8.6 GB of runs, 346 stamped, page cache warm
for every measurement, `/api/models` as the first call on a fresh process):

| | cold (no cache file) | warm (cache present) |
| --- | --- | --- |
| `/api/models`, first call | 33.7s, 35.2s | 22.9s, 20.4s |
| the fact fill alone | 11.9s | 4ms |

So the fill this closes is gone, and what remains of the cold cost is the same
route's two *other* cold memos — trajectory totals and run rows, both keyed on
the identical signature and both persistable the same way. That is now item 124;
it was left out deliberately, because a `RunTotals` is a heavier object than a
`RunFact` and the state series behind a run row is unbounded, which wants its
own decision about what is worth writing down.

`WRATHBENCH_FACT_CACHE` names the path, defaulting to a sibling of the runs
directory because the viewer only ever reads that tree — and the path is in the
startup line, because a cache on a path that is not writable (a container's
ephemeral layer, say) silently buys nothing. A handle given no path behaves
exactly as it did before and writes nothing, which is every test and every
one-shot render.

The publisher shares the code and the benefit: `createRenderer` builds the
viewer's own handle and a pass renders `/api/models` (`snapshot.ts:327`), and
the pod restarts on every runner-image bump and on `bun ship --publisher`. The
chart mounts one writable `fact-cache` subPath into both the viewer and the
publisher and points both at the same file — same corpus, same facts, same
signature, and the write is a rename over a pid-named temporary. **Needs a
deploy to take effect** (the mount is new; nothing was deployed from here).

Two holes found in review and fixed in `ff6c329`, both invisible inside one
process a few milliseconds wide: a run that was live when its signature last
moved was never written down at all (nothing tells the store about it a second
time, so `flush` forces a write and sweeps those in on SIGTERM), and the corpus
stamp is `resolve(runsDir)` — the viewer's own default is the relative
`data/runs`, and anything naming the same tree absolutely would have discarded
the file forever. Checked while there: `live` is the only field `readRunFact`
derives from `now` (`runner/src/models.ts:967`), so nothing else in a persisted
fact goes stale on the shelf.

## The ops scripts became cluster-native

The inventory bullet above, taken to its conclusion.

`./infra/fleet-update.sh status` reported the fleet as "container not running,
heartbeat 260151s ago" while the fleet was in fact live — one supervisor, one
freeplay run, a heartbeat under a minute old. It was still asking
`docker compose ps fleet`, and compose has been stopped since the 2026-09-08
cutover. That is worse than a broken script: the graceful/force/drain/resume
verbs are the operator's deploy-window tooling, and the one that still ran
without erroring was telling an operator sizing a window that the fleet was
dead.

The five verbs and their semantics are unchanged; what changed is who executes
them.

**Reads and writes go through the RUNNER pod.** `fleet-state.json` and the pause
switch beside it are on the `wrathbench-data` PVC, which the workstation cannot
see. `infra/k8s-deploy.sh` already read that file through
`deploy/wrathbench-runner`, and this script does the same — the runner rather
than the fleet's own pod because the fleet pod is the thing being recreated and
stops existing mid-window.

**One exec per poll, not five.** The old script had five little bun readers
(alive jobs, drain view, heartbeat, paused runs, switch state), each a separate
process. On the cluster each of those is a `kubectl exec` round trip, and a wait
loop taking five of them every 30 seconds is five ways to get a partial answer
about a state file the supervisor writes non-atomically. They are now one reader
emitting a line protocol (`switch:`, `pickedup:`, `heartbeat:`, `alive:`,
`wait:`, `park:`, `paused:`, terminated by `ok`), parsed once in bash. The `ok`
sentinel keeps its old meaning and gains one: a failed exec reads exactly like a
truncated file, and both are NOT quiet.

**A recreate is `kubectl rollout restart`.** The Deployment's strategy is
`Recreate`, so the old pod is SIGTERMed, gets its full 180s
`terminationGracePeriodSeconds` — the compose `stop_grace_period`, ported — and
only then does the new one start. Two supervisors never overlap, which is the
property `--no-deps` and `--force-recreate` were protecting on compose;
`--no-deps` itself has no analogue and needs none, because restarting one
Deployment cannot reach the worldserver. A fleet already scaled to 0 is scaled
back to 1 instead, since a rollout restart of nothing restarts nothing.

**`drain` scales to 0**, and that is the one verb whose exit shape changed: what
follows a drain is `kubectl scale --replicas=1`, not `compose up`. `resume` now
notices a Deployment at 0 and says the cleared switch scheduled nothing, naming
the scale — a footgun compose did not have, because there `resume` on a stopped
container was obviously incomplete and here it looks like success.

`--dry-run` prints every kubectl command it would run, which is what let the
whole mutating surface be exercised against a live fleet without touching it.
`--namespace`/`--release` are new, so the script can be pointed at a test
release.

Three things surfaced in review that the port introduced or inherited, all
fixed before merge.

**"Did the supervisor come back?" cannot be a timestamp comparison any more.**
The old boot wait captured `date +%s` before the recreate and waited for
`heartbeatAt` to exceed it. On compose those were the same kernel. On the
cluster the heartbeat is written by the pod on `chungusjr` and the timestamp is
the workstation's, so a pod a few seconds ahead makes the OLD supervisor's final
heartbeat — written seconds before its SIGTERM — satisfy the test on the first
poll, and the switch is cleared under a fleet that never came back: precisely
the failure the code exists to prevent. The clock-free discriminator was already
in the file: `startedAt`, from `const START_AT = Date.now()` at module scope in
`run-fleet.ts`, which changes exactly once per process. The wait is now for that
value to CHANGE, compared only against itself. A supervisor too old to write the
field leaves it 0, 0 never counts as a boot, and the window times out with the
switch set — the safe direction.

**A failing kubectl was a silent exit.** The abort path was tested for SIGINT
only, but `set -Eeuo pipefail` with no ERR trap meant a rollout timeout or an
API blip after `set_switch` would kill the script with no message, breaking its
own promise that every way out says the switch is still set. An interrupt is the
unlikely way to get there; a kubectl failure is the likely one. There is an ERR
trap beside the INT/TERM one now, saying the same words.

**`drain` could return before the pod was gone.** `docker compose stop fleet`
blocked until the container was down; `kubectl rollout status` on a Deployment
scaled to 0 does not reliably wait out a Terminating pod, and its result was
discarded with `|| true`. So `drain` could print "nothing live" while the
supervisor was still inside its 180s grace writing pause records — and the
documented recipe starts a deploy on the next line. It now polls the pod list
until it is empty, bounded, and refuses rather than reporting a drain it cannot
prove.

The test suite is the same shape as before with a `kubectl` shim in place of the
`docker` one, and it got better in the process: the shim implements
`exec ... -- <cmd>` by running `<cmd>` locally, so the pod-side reads and writes
are real reads and writes of a fixture directory. That works because the script
now passes the state and pause paths as argv instead of baking
`/wrathbench/data/runs` into its bun snippets. 31 tests, including new ones for
scale-vs-restart, the drained-`resume` warning, a missing Deployment, a
heartbeat-without-a-restart that must not count as a boot, a kubectl that fails
mid-window, a pod still Terminating after a drain, and a grep that no code line
in the script runs `docker compose`.

One bug the tests caught immediately and would not have been found by reading:
a JS comment containing an apostrophe inside the reader, which is a
single-quoted bash string, closed the quote and left every read returning
`none`. The snippet now says so in a comment of its own.

## The dump filename out of the entry window

The acceptance readback's one finding, fixed at the source. `projectEntry`
copied a `harness` entry's `before`/`after` comparability tuples verbatim, so
the wiki bundle stamp the run row withholds shipped a layer down. Any copied
field shaped like a tuple now crosses `projectComparability`, the same

## The Open shape, repository side — items 85 and 111

The public site has run since 2026-08-30 in the **Gated** shape: one Worker
serving the SPA from Static Assets and `/v1/*` and `/tiles/*` from a private R2
binding, behind a shared password, with `run_worker_first: true` so the gate saw
the page load and not only the data. That was never the launch shape and the
document said so from the day it was written. It existed because the account had
no zone, and on Cloudflare access control, WAF and cache are all custom-domain
features — an `r2.dev` URL with a password on it is not a configuration that
exists, so a preview that had to be shareable and not world-readable needed
something in the read path able to say no, and only a Worker can.

The operator's decisions today: the site moves to the **Open** shape on the
personal Cloudflare account, where the `shard.page` zone is. App at
`https://wrathbench.shard.page`, data at `https://wrathbench-data.shard.page`,
bucket name unchanged. One label deep each, and not for looks: Universal SSL
covers `*.shard.page` and not `*.*.shard.page`, so `data.wrathbench.shard.page`
would have wanted an Advanced Certificate. That settles operator decision 3
(domain and naming) and confirms 4 (SKU: free — now on firmer ground, because
with no Worker in the read path the 100k requests/day invocation cliff the gate
sat under does not exist). Decision 5, the attribution wording, stays open.
`shard.page` had been considered and declined on 2026-08-25 because it pointed
elsewhere; that reversed.

`dashboard/wrangler.jsonc` is the shape now: no `main`, no `r2_buckets`, no
`assets.binding` and no `run_worker_first` — all four named a script that no
longer exists — a `custom_domain` route for the app hostname, `workers_dev:
false` so the site has exactly one origin (the card's `og:image` is absolute,
and a second `*.workers.dev` address would serve tags pointing elsewhere), and
`not_found_handling: single-page-application` kept, which is what makes a deep
link survive a refresh. `dashboard/worker/` is deleted, along with its line in
the root typecheck loop and the now-dead `@cloudflare/workers-types`
