## Guaranteed hint delivery: the harness carries its own message home

The delivery track for the principle recorded above. The SDK's recovery hints were only ever readable if the snippet kept the result object, so a11's `.status`-only loops threw 41 of them away. Now `WrathClient` also tallies every hint-bearing failure — the four `MOVE_HINTS` paths plus `unknown_target` and the failed `transferred` / `teleported` verdicts — per `(action, status)`: count, the last occurrence's hint and destination point, ts. Aggregated rather than logged per occurrence because the recipes interpolate coordinates, so 41 `too_far` hints are 41 distinct strings that say one thing; the last one is kept because it is the one nearest where the character now stands. Only the status recipe is recorded, not the per-call budget/timeout notes `withNotes` folds in — those are already in the result and would vary every call.

The sandbox child drains the tally onto each eval result (onto the pong for an abandoned eval, the way logs already ride it), the host hands it up as `SnippetResult.actionHints`, and `tools.ts` renders it at the foot of the snippet result:

```
--- harness ---
moveTo too_far ×21: (-6048, 367) is 312y away in a straight line; a single moveTo covers ~250y. Walk to an intermediate point first.
```

One line per status, most recent first, count only when it repeats, hint text unchanged, at most four groups and 320 chars each with a `(+N other failure statuses)` tail. Nothing is reactive: the count is the collapse marker for repeats of one hint and no ordering, rendering or phrasing decision reads it — no thresholds, no escalation, no harness-authored advice (operator constraint, Mark, 2026-08-29). It goes in the tool result, not the turn's harness-notice block: a claude-code turn is a whole CLI session, so a notice there would land a turn late — the follow-up inspection the principle rules out. Both drivers dispatch through the same `callTool`, so both get it identically, and the trajectory already logs the rendered text as `snippet_result` / `tool_result` — no new record type, no notice-kind sweep. It renders on successful snippets too, which is the main case: a11's snippets all returned `ok`.

`drainActionHints` is listed internal in the API-docs generator, so nothing new appears in the model-visible `sdk/API.md` (regenerated: byte-identical), and it is deliberately not re-exported from the SDK package entry point — that surface is part of the harness version, which this change does not bump. A snippet that went looking could still call `sdk.drainActionHints()` and swallow its own block; undiscoverable and accepted, not worth code. Tests are fixture-based: the client tally and its once-only drain against the SDK stub server, the IPC path against the real sandbox child, and the render's grouping/count/cap/truncation plus a `callTool` case where the snippet returned only statuses. No live check — a11 is still running on RUNNER2 and the recorded statuses plus fixtures cover the path. Harness version deliberately untouched.

## Rate windows for the synced price table (item 91)

`prices.openrouter.json` held one rate per model and one `asOf` for the file, so a
re-sync re-priced every run on disk at today's catalogue. Harmless while rates hold
still, wrong the moment one moves: `z-ai/glm-5.3-flash` is on a launch discount to
roughly 2026-09-09, and the next sync after that would have billed August's runs at
list without anything in the diff saying so.

The mechanism already existed for the Claude rows (`standardAfter`, switched on the
run's own start date) and is now generalised to the synced table as data. Each id maps
to a *list* of windows instead of a row: the same four rates plus an optional `from`,
oldest first. `windowAt` picks the last window whose `from` is at or before the run's
start, and the latest window when the caller names no date (a run with no `startedAt`
wants today's price, not the oldest one on file).

The migration is what makes preservation provable rather than hoped for: every existing
row became a single window with **no** `from`, meaning "everything before the next
window begins". There is no second window yet, so all 803 runs price through the same
branch they always did — no fallback is exercised. `PriceRow.asOf` reads the window's
`from` where it has one and the file's `asOf` where it does not, so the run page's
displayed date stays honest either way.

`infra/sync-prices.ts` now compares the catalogue against the latest window and appends
`{ ...fresh, from: today }` when the four rates differ, rather than replacing the row;
a second sync on a day that already has a window replaces that window instead of
stacking a duplicate, so two syncs in one day cannot leave the reader's answer depending
on array order. The merge is a pure exported `mergeWindows`, which is what the tests
drive — a simulated sync, no fetch. The strongest of them doubles *every* rate in the
file on a date after the whole corpus and asserts that a fixture run on each id prices
to the identical dollar before and after; the others cover the same-day correction, a
new id starting undated, and an unchanged catalogue writing itself back byte-for-byte.
The existing 0/0 invariant now walks every window rather than the row.

One hole this does not close, deliberately: an id the catalogue *drops* is still removed
outright, windows and all, so a delisted model's runs go unpriced rather than keeping
the rates they really billed. That keeps yesterday's item-88 decision standing —
whether a delisted id should retain its history is a question about what a blank means,
and Mark's. It is noted in the sync's header rather than filed, since nothing triggers
it today.

`docs/COSTS.md` needed no edit: it records that its pricing table was removed and does
not describe this file.

## Item 35: deaths and level-ups become milestone records

The death and level-up slice of item 35, produced in the runner from observed state the
same way the zone/area marks are. Two new record families:

- `{ t: "milestone", kind: "level", from: number | undefined, to, xp?, turn }` on every
  change of `self.level`. The first observation of a process carries no `from`, exactly
  as the first zone does, so the run's starting level is on the record and a *level-up*
  is a mark that carries a `from` and climbs — which also means a resumed process's own
  baseline mark cannot be counted as a gain.
- `{ kind: "death", observedTs?, position?: { map, x, y, z, source }, zone?, area?,
  released? }`, with `{ kind: "release", graveyard? }` and `{ kind: "resurrect" }` from
  the ghost flag flipping.

The death is read as a **window**, not as a health edge. A sample lands every
`stateIntervalMs`; an edge detector would see almost no deaths at all. But the state
cache latches the corpse, the graveyard and the reclaim delay from the death until the
resurrect clears them, so any sample inside the window still sees it — and stamps the
death with the cache's own timestamp (`observedTs`) rather than the sample's, which is
why the two timestamps on the record are deliberately different facts. Health is read
off the raw field record, not the derived gauge, which stays undefined until `maxHealth`
has been seen; the ghost bit comes off `playerFlags` exactly as the HUD reads it, and
`PLAYER_FLAGS_GHOST` was exported rather than copied. A window that opened and closed
entirely between two samples leaves nothing, and two deaths with no observed resurrect
between them read as one: the same lower bound `AreaFacts` and `TaxiFacts` carry. A
process that opens on a character already dead seeds and writes nothing, the rule
`lastTaxiFlight` already follows.

**The liveness witness matters more than the counts.** A run that never died writes no
death mark, which without a witness is the same row as every run from before today. The
level mark is that witness: every run under this producer writes one on its first
sample, so `deathFactsFrom(marks, sawLevelMark)` returns `{ deaths: 0, … }` where the
producer was live and `null` where it was not — the job `achievements_at_login` does for
flights. The achievement records cannot do it, since runs predating the death producer
have them.

Consumers, both paths so the incremental tail and the whole-file scan cannot disagree:
`RunTotals.leveling` / `.deaths`, `TrajectoryTail.leveling` / `.deaths` (accumulators
reset in the shrink branch alongside the achievement ones), two more `resultRunOf`
parameters, and optional `leveling` / `deaths` on both `ResultRun` and
`RunDetailResponse`. `LevelUpFacts` carries `levelUps`, `startLevel`, `maxLevel`,
first/last and the timeline; `DeathFacts` carries `deaths`, `releases`, `resurrects`,
first/last and the sites map replay wants (item 22). Named `leveling` / `LevelUpMark`
because `ResultRun.levels: LevelMark[]` already exists and means something else — a
level reading derived from the state samples, with the cost of reaching it.

No rendering: `dashboard/src/pages/RunDetail.tsx` and `styles.css` are another agent's,
and nothing in `ladder.ts` changed but its doc block, which now names what rung 6 still
lacks (a party record and an instance record; a map-id change in the state samples is
not one, since it cannot tell a dungeon from a boat ride) and points at issue #9.

`runner/src/loop.ts` is not in this commit: the producer half of it was swept into
