## Guaranteed hint delivery: the harness carries its own message home

The delivery track for the principle recorded above. The SDK's recovery hints were only ever readable if the snippet kept the result object, so a11's `.status`-only loops threw 41 of them away. Now `WrathClient` also tallies every hint-bearing failure — the four `MOVE_HINTS` paths plus `unknown_target` and the failed `transferred` / `teleported` verdicts — per `(action, status)`: count, the last occurrence's hint and destination point, ts. Aggregated rather than logged per occurrence because the recipes interpolate coordinates, so 41 `too_far` hints are 41 distinct strings that say one thing; the last one is kept because it is the one nearest where the character now stands. Only the status recipe is recorded, not the per-call budget/timeout notes `withNotes` folds in — those are already in the result and would vary every call.

The sandbox child drains the tally onto each eval result (onto the pong for an abandoned eval, the way logs already ride it), the host hands it up as `SnippetResult.actionHints`, and `tools.ts` renders it at the foot of the snippet result:

```
--- harness ---
moveTo too_far ×21: (-6048, 367) is 312y away in a straight line; a single moveTo covers ~250y. Walk to an intermediate point first.
```

One line per status, most recent first, count only when it repeats, hint text unchanged, at most four groups and 320 chars each with a `(+N other failure statuses)` tail. Nothing is reactive: the count is the collapse marker for repeats of one hint and no ordering, rendering or phrasing decision reads it — no thresholds, no escalation, no harness-authored advice (operator constraint, Mark, 2026-08-29). It goes in the tool result, not the turn's harness-notice block: a claude-code turn is a whole CLI session, so a notice there would land a turn late — the follow-up inspection the principle rules out. Both drivers dispatch through the same `callTool`, so both get it identically, and the trajectory already logs the rendered text as `snippet_result` / `tool_result` — no new record type, no notice-kind sweep. It renders on successful snippets too, which is the main case: a11's snippets all returned `ok`.

`drainActionHints` is listed internal in the API-docs generator, so nothing new appears in the model-visible `sdk/API.md` (regenerated: byte-identical), and it is deliberately not re-exported from the SDK package entry point — that surface is part of the harness version, which this change does not bump. A snippet that went looking could still call `sdk.drainActionHints()` and swallow its own block; undiscoverable and accepted, not worth code. Tests are fixture-based: the client tally and its once-only drain against the SDK stub server, the IPC path against the real sandbox child, and the render's grouping/count/cap/truncation plus a `callTool` case where the snippet returned only statuses. No live check — a11 is still running on RUNNER2 and the recorded statuses plus fixtures cover the path. Harness version deliberately untouched.

## Rate windows for the synced price table (item 91)

`prices.openrouter.json` held one rate per model and one `asOf` for the file, so a
re-sync re-priced every run on disk at today's catalogue. Harmless while rates hold
still, wrong the moment one moves: `z-ai/glm-5.3-flash` is on a launch discount to
roughly 2026-09-09, and the next sync after that would have billed August's runs at
list without anything in the diff saying so.

The mechanism already existed for the Claude rows (`standardAfter`, switched on the
run's own start date) and is now generalised to the synced table as data. Each id maps
to a *list* of windows instead of a row: the same four rates plus an optional `from`,
oldest first. `windowAt` picks the last window whose `from` is at or before the run's
start, and the latest window when the caller names no date (a run with no `startedAt`
wants today's price, not the oldest one on file).

The migration is what makes preservation provable rather than hoped for: every existing
row became a single window with **no** `from`, meaning "everything before the next
window begins". There is no second window yet, so all 803 runs price through the same
branch they always did — no fallback is exercised. `PriceRow.asOf` reads the window's
`from` where it has one and the file's `asOf` where it does not, so the run page's
displayed date stays honest either way.

`infra/sync-prices.ts` now compares the catalogue against the latest window and appends
`{ ...fresh, from: today }` when the four rates differ, rather than replacing the row;
a second sync on a day that already has a window replaces that window instead of
stacking a duplicate, so two syncs in one day cannot leave the reader's answer depending
on array order. The merge is a pure exported `mergeWindows`, which is what the tests
drive — a simulated sync, no fetch. The strongest of them doubles *every* rate in the
file on a date after the whole corpus and asserts that a fixture run on each id prices
to the identical dollar before and after; the others cover the same-day correction, a
new id starting undated, and an unchanged catalogue writing itself back byte-for-byte.
The existing 0/0 invariant now walks every window rather than the row.

One hole this does not close, deliberately: an id the catalogue *drops* is still removed
outright, windows and all, so a delisted model's runs go unpriced rather than keeping
the rates they really billed. That keeps yesterday's item-88 decision standing —
whether a delisted id should retain its history is a question about what a blank means,
and Mark's. It is noted in the sync's header rather than filed, since nothing triggers
it today.

`docs/COSTS.md` needed no edit: it records that its pricing table was removed and does
not describe this file.

## Item 35: deaths and level-ups become milestone records

The death and level-up slice of item 35, produced in the runner from observed state the
same way the zone/area marks are. Two new record families:

- `{ t: "milestone", kind: "level", from: number | undefined, to, xp?, turn }` on every
  change of `self.level`. The first observation of a process carries no `from`, exactly
  as the first zone does, so the run's starting level is on the record and a *level-up*
  is a mark that carries a `from` and climbs — which also means a resumed process's own
  baseline mark cannot be counted as a gain.
- `{ kind: "death", observedTs?, position?: { map, x, y, z, source }, zone?, area?,
  released? }`, with `{ kind: "release", graveyard? }` and `{ kind: "resurrect" }` from
  the ghost flag flipping.

The death is read as a **window**, not as a health edge. A sample lands every
`stateIntervalMs`; an edge detector would see almost no deaths at all. But the state
cache latches the corpse, the graveyard and the reclaim delay from the death until the
resurrect clears them, so any sample inside the window still sees it — and stamps the
death with the cache's own timestamp (`observedTs`) rather than the sample's, which is
why the two timestamps on the record are deliberately different facts. Health is read
off the raw field record, not the derived gauge, which stays undefined until `maxHealth`
has been seen; the ghost bit comes off `playerFlags` exactly as the HUD reads it, and
`PLAYER_FLAGS_GHOST` was exported rather than copied. A window that opened and closed
entirely between two samples leaves nothing, and two deaths with no observed resurrect
between them read as one: the same lower bound `AreaFacts` and `TaxiFacts` carry. A
process that opens on a character already dead seeds and writes nothing, the rule
`lastTaxiFlight` already follows.

**The liveness witness matters more than the counts.** A run that never died writes no
death mark, which without a witness is the same row as every run from before today. The
level mark is that witness: every run under this producer writes one on its first
sample, so `deathFactsFrom(marks, sawLevelMark)` returns `{ deaths: 0, … }` where the
producer was live and `null` where it was not — the job `achievements_at_login` does for
flights. The achievement records cannot do it, since runs predating the death producer
have them.

Consumers, both paths so the incremental tail and the whole-file scan cannot disagree:
`RunTotals.leveling` / `.deaths`, `TrajectoryTail.leveling` / `.deaths` (accumulators
reset in the shrink branch alongside the achievement ones), two more `resultRunOf`
parameters, and optional `leveling` / `deaths` on both `ResultRun` and
`RunDetailResponse`. `LevelUpFacts` carries `levelUps`, `startLevel`, `maxLevel`,
first/last and the timeline; `DeathFacts` carries `deaths`, `releases`, `resurrects`,
first/last and the sites map replay wants (item 22). Named `leveling` / `LevelUpMark`
because `ResultRun.levels: LevelMark[]` already exists and means something else — a
level reading derived from the state samples, with the cost of reaching it.

No rendering: `dashboard/src/pages/RunDetail.tsx` and `styles.css` are another agent's,
and nothing in `ladder.ts` changed but its doc block, which now names what rung 6 still
lacks (a party record and an instance record; a map-id change in the state samples is
not one, since it cannot tell a dungeon from a boat ride) and points at issue #9.

`runner/src/loop.ts` is not in this commit: the producer half of it was swept into

## Freeplay streams are durable: disable, re-enable, same character

Operator ask (Mark): a freeplay run should survive being disabled and re-enabled through `fleet.json` — same account, same character, ideally the same scratchpad — instead of coming back as a fresh level-1. Today's case is `sub-opus-low`: a11 (Bromdir, dwarf paladin, level 8, RUNNER2) was killed by hand, terminated `manual`, and the ref set to `idle: "none"`; Mark wants to flip it back later and continue Bromdir.

What actually happened across that cycle, read off `data/runs`, the characters DB and the supervisor:

- There was no stream identity. The only thing that came back was a *pause*: `planResumes` resumes a run that has a pause mark, no termination, a ref still in the `unlimited` lane and less than 12h of silence — same run id, account, character and scratchpad. Every *ended* session — `tool-call-limit` (a1, a3–a5, before the lane was uncapped), `idle` (a6, a10), SIGINT/`manual` (a7–a9, a11) — was followed by a fresh attempt: a new run id, hygiene wiping every character on the launching account, and the model naming a new one. The key a fresh run reuses a character by is the name the model passes to `createSession`, and nothing told it the old one.
- Disable never stopped anything. Flipping `unlimited` → `none` removes the policy job, `diffJobs` drains it, and a drain SIGTERMs only a roster with no episode child — which an unlimited session always has, since it has no wall clock. So the drain waited for the idle watchdog or the operator's kill. a11 was killed by hand: the runner wrote `operator-pause` (a resumable state), and the by-hand `manual` termination written afterwards is what made it unresumable — the roster's `--resume-roster` skips a terminated run and `planResumes` never sees it. - Character limits are not biting. Name-in-use across the realm and delete linger are real mechanisms but not the cause of anything here.
- The scratchpad is per run directory and was never carried between run ids; the claude-code CLI conversation is not preserved even by pause/resume (`resumedFresh`), by design — the scratchpad is the durable memory.

The smallest change that makes the stream durable, shipped:

- **Identity**: a ref's stream is its latest ended freeplay run that recorded an account and a character (`streamsFrom`, matched on model + effort like affinity). Nothing new is stored; a paused run stays `planResumes`' business.
- **Continuation** (`--continue-from <run>`): the next policy pick on an `unlimited` ref carries its stream's run id. The runner refuses it unless the launch is `freeplay`, the predecessor is freeplay on the same account and named a character (`loadContinuation`); then hygiene keeps that character (`keep`), the predecessor's scratchpad is copied in, race/class are the character's, and the model gets `continuedSessionNote` ("this continues run X on Bromdir, last seen at level 8") instead of the naming note. No freshness tripwire, as on a resume. Lineage: `config.continuedFrom` in meta.json, `continued_from` on the run row (migrated like the 0.4-6 columns), a `continue` trajectory record. A character that is gone drops the lineage everywhere (`dropContinuation`, `continue-dropped`) and starts fresh.
- **Account**: a freeplay pick prefers its stream's account (`streamAffinity`); on another account it is held and announced once (`stream-waiting`), never started fresh elsewhere (`planContinuations`).
- **Protection**: every fresh launch gets `--keep-characters` for the other streams' characters on its account, so a scored run's hygiene leaves them (the model is told the names are taken; the tripwire still arms on their guids), and `planNameSweeps` skips stream characters (`protect`).
- **Disable**: a drained policy freeplay job is SIGTERMed at once (`pausesOnDrain`), once — a second SIGTERM would hard-exit the pause. Re-enable within 12h resumes in place; later, the stale sweep has ended it and the continuation takes over.
- **Scored episodes**: untouched. `--continue-from` is refused on `e90`/`e360` at launch, before a directory exists; a hand-written freeplay job never continues (the lineage rides only the `uncappedLane` spawn); the file may not carry `continueFrom`/`keepCharacters`.

Tests are fixture-based: `loadContinuation`'s refusals, two subprocess launches against a fake module (continued, and character-gone fallback), hygiene `keep`, the note, the column and `dropContinuation`, `episodeArgv`, and the supervisor's pure planners. `bun test` and `bun run typecheck` green.

## The freeplay ladder shows the field; `probing` loses its ladder

Mark reported the freeplay ladder empty. It was empty by construction, not by
accident, and had been since the chip was offered: `ladderRows` filters through
`scored()` (`dashboard/src/lib/ladder.ts:17-19, 289`), which keeps only rows
whose `unscored` is null — and `unscoredReason` (`runner/viewer/results.ts:276-279`)
stamps *every* freeplay run `unscored (episode freeplay)` off the episode's
`scored: false` flag, before it ever reaches the run's own facts. The server was
serving the rows; the page dropped all of them. Nothing about the data, the
stamping or the live runs was wrong: three checks confirmed the freeplay runs
carry `comparability.episode: "freeplay"` (so the API's `episodeSource === "stamped"`
membership filter passes them), and the empty table survived every filter above it.

**Operator decision (Mark, 2026-08-29), recorded in METHODOLOGY under "Scores are
derived offline":** the freeplay ladder is an overview of the top characters on
freeplay at the current time — the whole active field, everything not deleted and
not tainted, paused and disabled streams and runs in progress included, not only
finished ones. And with durable streams a row is one *character* across attempts,
never the same character twice. Scored ladders untouched.

- **The taint that applies here is `stillbornOf`, not `badEvidenceReason`.** The
  scored predicate answers "live", "paused" and "in-progress" — the three states
  this page exists to show — and its `NOT_THE_MODELS_FAULT` terminations include
  `manual` and `stale`, which is how freeplay sessions normally end. So the filter
  is the scheduler's own "produced nothing" notion and nothing else, decided
  server-side and published as `ResultRun.stillborn`; state became a column.
- **Lineage on the wire.** `continuedFrom` on `RunRow` and `ResultRun`, read from
  `continued_from` on the run row with `meta.config.continuedFrom` as the fallback
  (`dropContinuation` clears both, so they cannot disagree), and carried by the
  public projection — a run id, which every public listing already holds.
- **The collapse** (`streamRows`) walks `continuedFrom` to a root and keeps the
  longest chain, latest start breaking a tie. Written for production: a
  `continuedFrom` naming a run the set does not hold (archived, filtered, or
  dropped when the character went away) makes that run a root rather than
  vanishing; two runs claiming one predecessor both keep it; a visited set ends a

  missing readings last — the scored ladder's rule.
- **The page.** On `freeplay` the ladder renders the stream table instead of the

  it, the run does not — so a disabled stream reads `paused (operator-pause)` or

## The freeplay field gets a graph: level against active playtime, stitched across attempts

Operator ask: the freeplay ladder should carry a chart in the same visual language
as the episode graphs. It does now — `components/StreamChart`, drawn where the
scored tiers draw their scatter, one stepped series per stream, over exactly the
rows and runs `StreamTable` reads so the two can never disagree about who is on
screen.

**The axis is cumulative active playtime, and choosing it was the decision.**
"Match the episode graphs" is under-determined: `LadderChart` has no time axis at
all — it is a cost/xp scatter — so the family member with an x of time is the run
page's `XpChart`, whose axis is elapsed wall clock bounded by the episode
deadline. That bound is exactly what an unbounded freeplay stream does not have.
Wall clock would draw the days a stream spends paused between attempts — the
operator's calendar, not the character's progress. Turns are worse: `turnsUsable`
exists in `runner/viewer/results.ts` because a run resumed by an older build
restarts its counter, so a cross-attempt turn axis would be summing counters that
each begin again. `LevelMark.playtimeMs` is pause-corrected active time from the
run's start to that sample, already computed server-side by `activeMsUntil`, so
the honest axis is the one the data already carries.

Which also settles where the marks come from. `ResultRun.levels` is the only
source that can be placed on it: the `leveling` facts from item 35 carry `ts` and
`turn` and no playtime at all. **No API change was needed** — `levels` (with its
per-mark playtime) and the run's own `playtimeMs` are already on `ResultRun` and
already in `public-projection.ts`, so the snapshot build is consistent with
nothing touched.

The stitching is the substance, and each rule is a test:

- **A step, never a slope.** `levelMarks` records the first sample that showed a
  level, so a diagonal from L5 to L6 would claim the character was at 5.4
  partway. The level is held flat and rises at the next mark — a lower bound on
  when the ding happened, the sense the whole milestone surface already means.
- **A seam is not a gain.** Attempt *k*'s first mark is the level the character
  already had (the rule `LevelUpFacts` states for its own first mark), so a mark
  at or below the level already drawn is dropped. Without it a twelve-attempt
  stream draws eleven phantom rises. A mark *above* it is a ding that happened in
  the unobserved gap and steps at the seam.
- **A null prior-attempt playtime omits the stream, with its reason.** Folding it
  to zero would silently compress every offset downstream — the distinction
  `AreaFacts` and `TaxiFacts` are emphatic about. Only a *prior* attempt: with no
  span the last attempt's line simply ends at its last mark.
- Every series runs flat to its own total active time; an ended stream did not
  stop existing at its last ding. For a live one the viewer computes that total
  against now, so the line ends at the present for free.

Status is drawn the way the table states it — `--ok` live, `--warn` paused,
`--dim` ended — with the line dashed once ended and the end marker hollow, so the
distinction survives a reader who does not separate those hues. Both themes, from
the palette tokens, no new dependency.

**Two defects found by running it against the live viewer** rather than only
against fixtures. `/api/ladder?episode=freeplay` off the running (unrestarted)
viewer answers 15 rows with `continuedFrom` *absent*, not null — it predates
87419ce — and `undefined !== null` had every stream in the fleet reporting that
its history was truncated. The check is now `typeof … === "string"`, which is the
same "an older viewer must still work" rule `xpEarned` states. And four streams
were omitted as "no level mark carries an active-time reading" when the truth was
that they had no level mark at all: a 52-second paused session is too young to
have been sampled, and that reads "no level recorded yet" now. Against the live
data the chart draws 11 series, Bronzik at L8 over 3.1h of play leading, with the
four young streams named in the caption. Repeated character names — four ended
`Qwenlocal` lines — take their start date, ISO, since a pure module has no
business picking a locale.

Review caught four more before the commit landed. The x axis was taking
`niceTicks`, whose 1/2/5 × 10^k step over a millisecond domain gave a gridline
every 1.39 hours — time is not decimal, so a duration axis got its own ladder of
steps (`timeTicks`: minutes, then hours, then days), and the live data now reads
0/2/4/6h. A 2px line is not a pointer target, so each series carries a
transparent 12px twin under it, the way `LadderChart` gives its puck a `HIT_R`
circle. A last attempt with no active time was pulling `endX` back to its last
mark, behind time the earlier attempts had already proved. And the y axis is
anchored at zero so a two-level gain is not the whole chart, but nothing is ever
level 0, so that gridline goes unlabelled.

**The stitching is fixture-verified and inert until the viewer restarts.** The
running viewer omits `continuedFrom` entirely, so `streamRows` finds no parents
today and the chart draws one series per run. Every multi-attempt case above is
covered by tests and by nothing on screen until the next restart, which is not
this session's to make.

## Graceful stops waiting for the run it costs nothing

The window that had to become a `force` this morning was waiting for the one
run a recreate is free with. `fleet-update.sh graceful` now splits every live
job row in two: the runs that must finish on their own clock — every scored
e90/e360, the ones a recreate ends `manual` and whose attempt is spent — hold
the window, and the runs that come back where they left off are counted as
drained. Each poll names both halves (`waiting on:` / `counted drained:`), so
an operator can see what the wait is for instead of a bare count.

A run is parked only once the switch has put its job in `draining`. That is
the proof the supervisor picked the switch up, it is what makes the observed
hang finish (a freeplay job whose supervisor drains to an episode boundary sits
`draining, alive` forever — an `idle: unlimited` session has no boundary), and
it keeps the deliberate sparing of a refused pin honest: a spared job never
drains, so it still holds the window.

Which runs those are is the supervisor's answer, published per job row as
`resumesInPlace`: the freeplay stream, and a probe campaign with `resume: true`
(`class-probe` today). The script does not re-read `fleet.json` for that flag,
because the switch exists to work while that file is rejected — and a state row
written by a supervisor older than the field falls back to the freeplay pair,
so the first graceful after this ships still works. The supervisor half of that
only takes effect on the next recreate; the freeplay half needs nothing.

Two smaller things from the same morning. Ctrl-C during the wait now says the
pause switch is still set and names `fleet-update.sh resume` — an aborted
window that looks like nothing happened is how a fleet ends up scheduling
nothing until somebody notices. And `force` clears a switch it finds set, once
the new supervisor's heartbeat is in: force starts the container, so a switch
left behind it is a fleet that runs and schedules nothing. `drain` is still the
mode whose job is leaving it set, and it stops the container instead.

Verified with `--dry-run` against the live state (nothing written, nothing
recreated; the sonnet freeplay stream is not draining while the switch is
unset, and the dry-run says so rather than pretending it would park). No
graceful, force or resume was run for real — the stream is live.
