# 2026-09-08

The Helm chart learned the codex lane. `infra/fleet.json` has carried
`codex-astra-high` and `CODEX_HOME` in `policy.subscriptions` since 2026-09-05,
and compose has bind-mounted the operator's `~/.codex` into the fleet and runner
services since then, but `infra/chart/wrathbench` predated all of it: a codex
roster entry on the cluster would have failed its own preflight with no lane to
name.

The lane is a logged-in Codex home *directory* — `auth.json` plus the persisted
threads — that the CLI refreshes in place, so it is a PVC and not a Secret key.
A third claim, `wrathbench-codex-home` (1Gi, same `iscsi-nvme`, Retain,
`helm.sh/resource-policy: keep` as the other two), is mounted at
`/home/bun/.codex` on both the fleet and runner Deployments — a directory, not a
`subPath`, so the token refresh writes through — with `CODEX_HOME` set to match.
RWO is sound for the same reason it is for `wrathbench-data`: everything is
pinned to `chungusjr`. `codex.enabled` (default true) gates the claim, both
mounts, both volumes and both env entries; `--set codex.enabled=false` renders
with no mention of codex at all.

`docs/DEPLOY-NUSPHERE.md` gained "The codex lane" and a cutover step 5. The
thing worth writing down is that the lane is seeded ONCE, from the operator's
logged-in home, after the compose fleet is stopped: two live copies do not give
you two lanes, the first refresh from either side invalidates the other, and the
next call fails with "refresh token was already used". After the seed the
cluster copy is canonical and the host one is not for fleet work; a lapse is
re-authenticated in place with `codex login --device-auth` inside the runner pod
(the CLI is in the runner image), not re-seeded.

Values keys added: `codex.enabled` and `storage.codexHome.size`.

The rollback-to-compose steps carry the lane back the other way now: the host
`~/.codex` goes stale the moment the cluster refreshes it, compose mounts it
unconditionally, and the supervisor's preflight only checks that `CODEX_HOME` is
set — so a rollback that forgot the lane would come up green and fail every
codex episode at its first call.

the desktop's viewer systemd unit is disabled and `infra/wrathbench-viewer.service`

Four things the runbook had wrong or silent, all now fixed in it. The dump and
restore commands expanded `$WRATHBENCH_DB_ROOT_PASSWORD` in the operator's
shell, where the repository `.env` does not set it (compose defaults it), so the

Deployment to scale back, so its EXIT trap reports "phase failed: the fleet did
not scale back up" and writes `phase=failed` after a clean set of smokes; the
supervisor clears it on start, and the runbook now says so rather than letting
the next operator read a pass as a failure. The script itself is unchanged: it
is correct for the day-2 case, which is the one it is for. The codex seed's

permitted` for `.` and lands every file anyway — noted next to the command, with
`codex login status` as the check that actually means something. And the delta
copy, which the runbook only implied, is written out: the seed step copies
everything, the delta step is `find -newermt` piped through the same `wb-seed`
pod, and `wb-seed` is no longer deleted at the end of step 4.

What the cutover did not exercise is `iscsi-nvme` under a live fleet writing two

item 121 carries the streaming fix.

## The publisher's pass, batched — and where its memory actually is

`infra/publish-dashboard.ts` now renders and uploads the per-run half of a pass
in bounded batches instead of building the whole tree first. The renderer takes
an optional `RunStream` (`runner/viewer/snapshot.ts`) and hands each group of
`WRATHBENCH_PUBLISH_BATCH` runs' artifacts to the engine, which uploads them as
the run wave and keeps only their keys, hashes and `(run, version)` pairs;
`publishPass` (`infra/publish-core.ts`) is the same engine as before, with the
run wave arriving in pieces. Default 25, documented beside the other
`WRATHBENCH_PUBLISH_*` names, mirrored in the compose service and the chart
(`publisher.batch`). Every invariant held: the manifest is still written last
and only after every upload of the generation succeeded, a batch that fails to
upload no longer stops the rest of the tree from being attempted (the failures
are raised together, before the flip, exactly as the single-array wave did),
unchanged objects are still skipped by key and stale ones pruned on the same
windows.

The public content did not move by a byte, and that is measured rather than
asserted: old code and new, over the 1,016-run tree against a local fake S3,
uploaded the same 1,294 objects under the same 1,294 keys with the same
clock-normalized SHA-256s, the same 54,592.6 KiB, and the same manifest
generation `02a61a987d44` — at batch 25 and at batch 1 alike.

What it did not do is fix the memory. Peak RSS over the same tree: 4.46 and
4.44 GB on the old code, 3.67 and 4.93 GB batched at 25, 3.10 GB batched at 1 —
run-to-run spread swamps the effect. The reason is that the artifacts were never
the memory: all 1,294 of them are 55 MB in total, which is what a pass used to
hold. Forcing a full collection at every batch boundary moved the peak from 3.67
to 3.65 GB, so the residue is not uncollected garbage either. Sampling RSS every
second shows where it is: ~2.2 GB of spikes in the aggregate phase, which runs
over every run before the per-run loop starts, then a flat 0.35 GB through the
streamed per-run projection, then a climb to 3–4 GB as the viewer handle's
per-run caches (`factCache`, `totalsCache`, `runReadCache`) fill — live data, by
design, one entry per run, in the handle the publisher keeps for the process.
So batching bounds what a pass *retains* (it no longer grows with the tree) and
nothing else. Item 121 stays open, amended with these numbers; the chart default
is left at 1 GiB with the measurement in a comment, because lowering it is not
what the measurement supports and raising it to match the cluster's 8 GiB
stopgap is the operator's call.

landed: db047c2 — infra/publish-core.ts, infra/publish-dashboard.ts,
runner/viewer/snapshot.ts. Item 121 was amended rather than closed at that
point: a bound on what a pass retains, not yet the fix the item asked for.

## …and then where the publisher's memory actually was

Two things, both found by measuring rather than by reading. Neither is in the
projection: the public bytes are identical.

**The scanners read whole files.** `RunTotalsScanner` and the entry index each
pulled the entire unread region of a trajectory into one `ArrayBuffer` before
parsing a record — 638 MB for the largest run in the tree, and a line view per
record over all of it, times eight concurrent readers. They now read in 4 MiB
windows (`SCAN_CHUNK_BYTES`), carrying the partial record at a window's edge in
the same `pending` buffer that has always carried the partial record at the end
of a live file. Nothing else changes, which is what the new boundary tests pin:
a fixture read at a 13- or 17-byte window gives the same totals, the same entry
summaries and the same byte offsets — the offsets being what `raw(i)` reads back
off disk — as the same fixture read whole.

**The viewer handle held an entry index per run.** `createApi` memoises per run
because a viewer is polled; a publish pass is the opposite shape, visiting every
run once and never asking again. So the handle grew a `release(runId)`
(`ApiHandle`), which the renderer calls for each run in a batch once the sink
has taken its artifacts — publisher-only, opt-out via `RunStream.release`, and
nothing in the viewer calls it. It drops the entry index and its scan lock and
nothing else: releasing the row and totals caches too was tried and made a pass
quadratic (64s → 158s), because the listing routes and a freeplay run's stream
view read those *as a set*, so a released run is re-read by the next request
that needs the whole set. That is written next to the code, since it is the kind
of thing that looks like an oversight.

Measured the same way as before — `--once` over the frozen 1,016-run tree
against a local fake S3, peak RSS from `getrusage`:

| | peak | wall |
| --- | --- | --- |
| before (whole-tree projection, whole-file reads) | 4.46 / 4.44 GB | 60s |
| batching alone (2026-09-08, db047c2) | 3.67 / 4.93 GB | 60–66s |
| windows + release, batch 25 | 1.08 GB | 60s |
| windows + release, batch 8 (the new default) | 0.78 GB | 67s |
| windows + release, batch 1 | 0.59 GB | 64s |

The batch is a real dial now that the two big terms are gone, and it costs
almost nothing in time, so the default drops from 25 to 8 — the width of the
per-run read pool. The chart's memory limit comes back down to 2Gi, twice the
measured peak; the cluster's 8Gi override (nusphere PR 157) is redundant and can
go whenever the operator wants.

runner/viewer/api.ts (`ApiHandle.release`), runner/viewer/snapshot.ts
(`RunStream.release`), infra/chart/wrathbench/values.yaml (2Gi).

Byte-for-byte identical output, checked rather than assumed: the old code and
the new one, at batch 25, 8 and 1, each uploaded the same 1,294 keys with the
same clock-normalized SHA-256s, the same 54,592.6 KiB and the same generation
`02a61a987d44`.

## The pod could not name its own harness, so a paused stream was orphaned

At 00:43 UTC the fresh supervisor did not resume
`fleet-nemotron-super-freeplay-...-20260905-a12`, paused `operator-pause` three
minutes earlier by the drain. It logged `attempt 13 (extra) (continues ...a11)`
and started a new run off the ENDED attempt before it, on the same character,
leaving a12 hanging off the chain. The same supervisor had resumed that exact
run at 23:14, which is what made it worth chasing.

`fleet-state.json` is not in the story. `planResumes` reads `readRunFacts` over
`data/runs` and never the state file, so the runs directory already is the
source of truth for a resume — the state write on SIGTERM, the grace period and
the job entry were all fine and none of them could have caused this.

The cause is the version stamp. `infra/run-roster.ts` had its own
`harnessVersion()`, a copy of the host recipe that shells out to `git describe`
and falls back to `"0.0.0-phase0"` — and it ignored `WRATHBENCH_HARNESS_VERSION`,
which `runner/src/version.ts` honours and which the chart sets from the image
tag. The fleet pod has the repo baked in and no git, so every episode it
launched *or resumed* was stamped `0.0.0-phase0`. `harnessSeries()` reads that
as no series at all; `planResumes` filters paused runs by `inSeries`, so a12 was
not resumed, not ended, and not even listed — `paused: []` in the state file
while a paused run sat on the account. The projection (`modelStates`) drops
out-of-series runs the same way, which is why the policy then thought the ref
was free and picked a fresh attempt. The 23:14/00:43 asymmetry falls out of
`run.ts` restamping `meta.json` on resume: at 23:14 a12 still carried the
`harness-0.5-506` stamp of the compose-era launch, the resume rewrote it to
`0.0.0-phase0`, and an hour later it was invisible. Evidence from the live pod:
run-roster (pid 85) had `WRATHBENCH_HARNESS_VERSION=harness-0.5-513-g803bd42` in
`/proc/85/environ` while its `run.ts` child (pid 117) had `0.0.0-phase0`, and
replaying `planResumes` against the live tree returned nothing at all — with the
series filter neutralised it returns a12 and a14, both resumable now.

Three fixes, in order of how much they matter.

`infra/run-roster.ts` reads the env var first, and `infra/run-episode.sh` no
longer recomputes over an inherited one. That script's own k8s branch already
said the chart's value is the honest marker for a baked-in repo; line 140
contradicted it on every launch path.

`streamsFrom` (`infra/run-fleet-plan.ts`) now takes a PAUSED run as a stream
head: not live, and terminated *or* paused. A head the resume planner declines —
another series, a spent ladder, a job the operator disabled — used to vanish
from the stream and the next attempt continued from an older ended run. The
character is the same one either way, so the honest lineage is the newest
attempt. Nothing launches from here: a head that is resumable is resumed by
`planResumes`, which reserves its account and job name before the policy picks.
`loadContinuation` in `runner/src/run.ts` already accepts such a predecessor —
it asks for a freeplay run on the same account that named a character, and
never for a termination — which `runner/test/continue.test.ts` now pins, since
a refusal there would have turned this into a `continue-dropped` and a fresh
level-1 character.

That the head is series-blind is the operator's own decision, not a new one:
"The one exemption that stands is the harness series — a stream is durable
across series, and cutting its older attempts would report a long-lived
character as attempt 1" (`docs/METHODOLOGY.md`). The RESUME gate stays
series-keyed, which is also unchanged — `inSeries` in `planResumes`, exactly as
it was — because resuming a run into a different harness is a different claim
from continuing a character, and because letting the paused set past that filter
would have swept 42 older-series runs. Durable stream, series-keyed resume: both
halves are deliberate.

`planResumes` lists an out-of-series paused run instead of dropping it before
the loop, so `--status` can say why nothing is happening. Listing only, never
ending: the live tree holds 44 paused runs, 42 of them from older series, and
letting them past the filter would write a termination on every one — checked
by replay before the change, and pinned by a test.

The drain itself needed nothing. `CHILD_TERM_GRACE_MS` is 90s against the
chart's 180s and the observed drain took two seconds; `roster.test.ts` now pins
the chart's number against the code's grace, and the stale "30s of grace"
comment in the chart and in `compose.yml` is corrected.

Item 122 carries the live data, which is the operator's: a12 and a14 are still
stamped `0.0.0-phase0` in their own `meta.json`, so the fix does not reach them.
