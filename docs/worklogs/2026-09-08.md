# 2026-09-08

The Helm chart learned the codex lane. `infra/fleet.json` has carried
`codex-astra-high` and `CODEX_HOME` in `policy.subscriptions` since 2026-09-05,
and compose has bind-mounted the operator's `~/.codex` into the fleet and runner
services since then, but `infra/chart/wrathbench` predated all of it: a codex
roster entry on the cluster would have failed its own preflight with no lane to
name.

The lane is a logged-in Codex home *directory* — `auth.json` plus the persisted
threads — that the CLI refreshes in place, so it is a PVC and not a Secret key.
A third claim, `wrathbench-codex-home` (1Gi, same `iscsi-nvme`, Retain,
`helm.sh/resource-policy: keep` as the other two), is mounted at
`/home/bun/.codex` on both the fleet and runner Deployments — a directory, not a
`subPath`, so the token refresh writes through — with `CODEX_HOME` set to match.
RWO is sound for the same reason it is for `wrathbench-data`: everything is
pinned to `chungusjr`. `codex.enabled` (default true) gates the claim, both
mounts, both volumes and both env entries; `--set codex.enabled=false` renders
with no mention of codex at all.

`docs/DEPLOY-NUSPHERE.md` gained "The codex lane" and a cutover step 5. The
thing worth writing down is that the lane is seeded ONCE, from the operator's
logged-in home, after the compose fleet is stopped: two live copies do not give
you two lanes, the first refresh from either side invalidates the other, and the
next call fails with "refresh token was already used". After the seed the
cluster copy is canonical and the host one is not for fleet work; a lapse is
re-authenticated in place with `codex login --device-auth` inside the runner pod
(the CLI is in the runner image), not re-seeded.

Values keys added: `codex.enabled` and `storage.codexHome.size`.

The rollback-to-compose steps carry the lane back the other way now: the host
`~/.codex` goes stale the moment the cluster refreshes it, compose mounts it
unconditionally, and the supervisor's preflight only checks that `CODEX_HOME` is
set — so a rollback that forgot the lane would come up green and fail every
codex episode at its first call.

## The NuSphere cutover

Item 116. The stack moved off the workstation's docker compose and onto the k3s
cluster, with the runs and the world it already had. The staged bring-up
(2026-09-05) had proven the install against a copy; this was the window where
the copy became the original.

`bdc9501` is the pinned commit — the chart's codex lane, above — built and
pushed to Harbor at `harness-0.5-507-gbdc9501`. nusphere PR 155 pinned it with
the flags still off, PR 156 flipped `fleet.enabled` and `publisher.enabled`;
nusphere master is `a38eafa`.

The compose fleet and publisher stopped at 09:02 local with no episode process
left to drain: both in-flight heads had already terminated on their own
(nemotron-super a11 `adapter-error`, minimax-m3-free a13 `attempt-failed`), so
nothing was mid-turn when the world went away. Then a fresh `mysqldump` (306 MB,
`acore_auth` / `acore_characters` / `acore_world`), the runs and publish delta
into the data PVC through the `wb-seed` pod left running from the seed — 158
files changed since the 09-05 copy — and `~/.codex` (75 MB) into the runner
pod's `/home/bun/.codex`, once, which is the only way that lane can be moved.

The evidence that nothing was lost is the reason to write this down: 1016 run
directories on both sides, `run.sqlite` md5 identical on the two live stream
heads, and after the restore (worldserver and authserver scaled to 0 for it) 14
characters at max level 16 and 15 accounts, identical to the source. `codex
login status` in the runner pod: "Logged in using ChatGPT".
`./infra/k8s-deploy.sh` then ran the two gate smokes (quest-accept-status 20 s,
kill-credit 20 s) and the full-arc module-quest smoke (284 s) against the
restored world — all PASS — before either flag was flipped. The cluster fleet
gated itself again on start (PASS, 19 s) and at 23:14 UTC resumed both paused
streams: nemotron-super a12 on RUNNER, minimax-m3-free a14 on RUNNER2. The
viewer is `https://wrathbench.local`, 270 runs in series 0.5, worldserver build
`harness-0.5-507-gbdc9501`.

The compose stack is stopped but still installed, which is the rollback path;
the desktop's viewer systemd unit is disabled and `infra/wrathbench-viewer.service`
is kept for the same reason.

Four things the runbook had wrong or silent, all now fixed in it. The dump and
restore commands expanded `$WRATHBENCH_DB_ROOT_PASSWORD` in the operator's
shell, where the repository `.env` does not set it (compose defaults it), so the
dump failed with access denied; both forms now run `sh -c` inside the container
against its own `MYSQL_ROOT_PASSWORD`. The cutover ordering the runbook
prescribes — smokes, then flip — runs `k8s-deploy.sh` while there is no fleet
Deployment to scale back, so its EXIT trap reports "phase failed: the fleet did
not scale back up" and writes `phase=failed` after a clean set of smokes; the
supervisor clears it on start, and the runbook now says so rather than letting
the next operator read a pass as a failure. The script itself is unchanged: it
is correct for the day-2 case, which is the one it is for. The codex seed's
`tar -x` onto the mount root exits 2 on `Cannot change mode ... Operation not
permitted` for `.` and lands every file anyway — noted next to the command, with
`codex login status` as the check that actually means something. And the delta
copy, which the runbook only implied, is written out: the seed step copies
everything, the delta step is `find -newermt` piped through the same `wb-seed`
pod, and `wb-seed` is no longer deleted at the end of step 4.

What the cutover did not exercise is `iscsi-nvme` under a live fleet writing two
`run.sqlite` files at once; item 120 carries the watch and the local-path
fallback.

The publisher was the one thing the staged bring-up could not have caught: with
`publisher.enabled` true it was `OOMKilled` nine seconds into every pass at the
chart's 1 GiB default. A pass holds the projection of every run in memory
(4.8 GB peak on this tree); nusphere PR 157 raises the limit to 8 GiB and
item 121 carries the streaming fix.

## The publisher's pass, batched — and where its memory actually is

`infra/publish-dashboard.ts` now renders and uploads the per-run half of a pass
in bounded batches instead of building the whole tree first. The renderer takes
an optional `RunStream` (`runner/viewer/snapshot.ts`) and hands each group of
`WRATHBENCH_PUBLISH_BATCH` runs' artifacts to the engine, which uploads them as
the run wave and keeps only their keys, hashes and `(run, version)` pairs;
`publishPass` (`infra/publish-core.ts`) is the same engine as before, with the
run wave arriving in pieces. Default 25, documented beside the other
`WRATHBENCH_PUBLISH_*` names, mirrored in the compose service and the chart
(`publisher.batch`). Every invariant held: the manifest is still written last
and only after every upload of the generation succeeded, a batch that fails to
upload no longer stops the rest of the tree from being attempted (the failures
are raised together, before the flip, exactly as the single-array wave did),
unchanged objects are still skipped by key and stale ones pruned on the same
windows.

The public content did not move by a byte, and that is measured rather than
asserted: old code and new, over the 1,016-run tree against a local fake S3,
uploaded the same 1,294 objects under the same 1,294 keys with the same
clock-normalized SHA-256s, the same 54,592.6 KiB, and the same manifest
generation `02a61a987d44` — at batch 25 and at batch 1 alike.

What it did not do is fix the memory. Peak RSS over the same tree: 4.46 and
4.44 GB on the old code, 3.67 and 4.93 GB batched at 25, 3.10 GB batched at 1 —
run-to-run spread swamps the effect. The reason is that the artifacts were never
the memory: all 1,294 of them are 55 MB in total, which is what a pass used to
hold. Forcing a full collection at every batch boundary moved the peak from 3.67
to 3.65 GB, so the residue is not uncollected garbage either. Sampling RSS every
second shows where it is: ~2.2 GB of spikes in the aggregate phase, which runs
over every run before the per-run loop starts, then a flat 0.35 GB through the
streamed per-run projection, then a climb to 3–4 GB as the viewer handle's
per-run caches (`factCache`, `totalsCache`, `runReadCache`) fill — live data, by
design, one entry per run, in the handle the publisher keeps for the process.
So batching bounds what a pass *retains* (it no longer grows with the tree) and
nothing else. Item 121 stays open, amended with these numbers; the chart default
is left at 1 GiB with the measurement in a comment, because lowering it is not
what the measurement supports and raising it to match the cluster's 8 GiB
stopgap is the operator's call.

landed: db047c2 — infra/publish-core.ts, infra/publish-dashboard.ts,
runner/viewer/snapshot.ts. Item 121 is amended rather than deleted: this is a
bound on what a pass retains, not the fix the item asks for.
