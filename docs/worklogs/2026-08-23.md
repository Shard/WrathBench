Two decisions worth naming. **Membership is stamped-only.** The runs already on disk

override is a membership question, not a scoring one**: a filter that
`?includeOverrides=1` reverses, not a term in `unscoredReason`, or the exclusion could
never be shown. Bare watchdog defaults are unchanged (FOLLOW-UPS 48g).

## Stillborn runs (operator ruling; 10:46)

A run with zero `response` records in its trajectory — the model never spoke — and no
longer live is a launch that did not happen, not a short run. `runner/viewer/
stillborn.ts` (294610c) holds the one definition (zero responses **and** not live: a
run thirty seconds old has no response *yet*); `scanRunTotals` counts the records
inside the memoised whole-file scan, and `stillborn`/`modelResponses` ride on the run
and eval rows. The dashboard hides them from the runs list, eval, ladder and episode
member counts, each saying how many with a `show stillborn (N)` toggle;
`?includeStillborn=1` is the API spelling. `bun runner/src/archive.ts --stillborn
[--dry-run]` moves them to `data/runs/archive/<run-id>/`, which every enumeration
skips by name, and refuses any run whose files or fleet-lane records are warmer than
ten minutes. The count is deliberately not a turn count — the claude driver appends
one `response` record per content block — and a directory with no trajectory at all
is never called stillborn, because that was never a run. First sweep: 83 of 178 run
directories — free-tier lanes that 403'd on the first request, a claude-subscription
run whose CLI exited on a bad MCP path, and two lanes rate-limited into a pause nine
times each. None had a `tool_call` record either, so no externally-scaffolded run is
caught by the predicate.

## Sleeping made observant; `reclaimCorpse` made a helper (11:11)

One ADR-0016 softening pass (68b5a92, eff2a45) over the 2,086 `sleep()` calls of
>=20s in data/runs, which fall into three shapes: `Promise.race([routine,
sleep(28000)])` as a deadline (legitimate), `await sleep(25000);
sdk.reclaimCorpse()` (waiting out the server's corpse reclaim delay by hand), and bare
`await sleep(28000)` idling. Deterministic and identical for every model; not
score-comparable across the boundary.

(1) The sandbox's ambient `sleep(ms, options?)` still resolves after `ms`, but
resolves *with a reason* — `"elapsed" | "attacked" | "died"` — and early for the two
things a sleeping snippet would want to react to: `SMSG_ATTACKSTART` naming us as the
victim, and our own health observed at zero. A model that ignores the value loses
nothing, and `Promise.race` is unaffected by construction (runner/test/sleep.test.ts
pins it). Two deliberate non-wakes: `died` fires on the transition only, so the
corpse-run sleep that is already dead is not woken by the death it is handling, and
`{ wake: false }` is a pure timer. Bad arguments throw with what `sleep` takes rather
than a `setTimeout(undefined)` that returns instantly. Wake subscriptions are
registered after the client's own state fold and torn down in every exit path,
including abort.

(2) `sdk.reclaimCorpse(guid?, options?)` owns the delay and returns a verdict — `{ ok,
status: "reclaimed" | "not_reclaimed" | "unconfirmed", waitedMs, delayMs, attempts,
reason?, hint? }` — on the equipItem/buySpell pattern; the bare dispatch survives as
`reclaimCorpseAsync`. `SMSG_CORPSE_RECLAIM_DELAY { delayMs }` *is* tapped, and
`BuildPlayerRepop` sends it immediately before it resets the corpse's ghost time, so
the most recent one on the stream plus its own `ts` is when the reclaim becomes
legal; the wait is clamped by the announced delay so clock skew can never make it wait
longer than the delay itself. No such event in the retained 500-event buffer means
dispatch *now*, never a made-up 30s wait — the core sends nothing when no delay is
owed (`CalculateCorpseReclaimDelay` returns -1), and a too-early attempt is absorbed by
the retry. What is observable, stated exactly because every refusal path in
`WorldSession::HandleReclaimCorpseOpcode` returns silently (alive, spirit not
released, no corpse, delay not elapsed, further than ~39y): `SMSG_DEATH_RELEASE_LOC`
with `map: -1`, the first packet `Player::ResurrectPlayer` sends, corroborated by own
health leaving the released ghost's body value of 1 (`BuildPlayerRepop` sets health
to 1; a reclaim restores 50%). The ghost aura (8326) was considered as a third signal
and dropped: whether a passive aura reaches the client is a DBC question this repo
cannot check. Pre-flight names the two states that can never work (health 0 = spirit
not released, call `repop()` first; health > 1 = alive) and sends nothing for them; a
delay outlasting the budget answers `delay_not_elapsed` with how much is left;
`still_ghost` lists the three silent refusals; `unconfirmed` is the honest answer
when own health was never observed. Default timeout 25s, matching `killTarget`'s
reason (under the runner's 30s snippet cap); every wait honours the ambient snippet
signal. Prompt lines for both rewritten; sdk/README.md updated (eff2a45).

## `moveTo` takes a unit or guid; abandon says how far the move got (11:31)

From `data/runs/night-report-20260823/fanout-navigation.md` items 1–2 (da93f0a;
ADR-0015/0016 harness change — error text and the prompt both move). (1) 4 of the 7
fan-out runs (oc-b c8, qwen c12/c13, ox-alpha c14) threw a raw `TypeError: moveTo
position x must be a finite number, got undefined` reading `.x` off a
`state.units(...)`/`state.closest(...)` lookup that had returned nothing, always right
after an NPC name filter missed — the crash named the axis, never the lookup.
`moveTo`/`moveToAsync` accept a unit or a guid: a unit resolves through the state
cache at call time (a guid held across a patrol walks to where the unit is now); a
unit the cache has since lost falls back to the coordinates that object carries *and
says so in the hint*; a guid nothing in view answers to returns `{ ok: false, status:
"unknown_target", hint }` rather than throwing. `unknown_target` is deliberately not a
`WB_MOVE_RESULT` status — ADR-0027 gives the module the status vocabulary, and this
arm is the SDK answering before the wire, the way `killTarget` answers `lost`, so it
carries no `moveId`/`position`/`seq`/`ts`. Point calls are untouched down to the
rejection messages: only a guid-shaped argument takes the new path, so `moveTo(-1205,
981)` keeps earning "needs a point object { x, y, z }, got number". `moveToAsync`
takes the same targets but throws on an unresolvable one: the raw tier has no result
object to put a verdict in.

(2) Long synchronous moves against the 30s snippet budget: 6 of 7 runs hit the
abandon wall with a `moveTo` in flight, and nav-probe c4 re-issued the identical
blocking call 5 times, ignoring the abort message's background-routine suggestion

## The ladder's row ordering, stated (item 13)

The operator decided the ordering item 13 was parked on: **highest rung reached,
then total XP, then gold.** It is now what `ladderRows()` does and what ADR-0018
says, rather than an unexamined `b.highest - a.highest || b.runs - a.runs`.

Total XP is the `(level, xp-within-level)` pair compared lexicographically, not a
synthesised integer — there is no XP-per-level table in what the harness records,
so `level * K + xp` would be a fabricated number, and the pair is the same
ordering anyway because xp resets at every ding. Gold is the newest money reading
a run recorded, the number the fleet listing and run page already show; no state
sample the eval surface reads carries money, so no peak is claimed. Both
tie-breaks are independent maxima over the model's counted runs, so the gold
usually comes from a different run than the level — the ladder prints both
columns and puts the source run id in each cell's title, so three numbers on one
row are not misread as one run's ledger. Nulls sort last, never as zero: 0 copper
and 0 xp are real readings.

`EvalRun` gained `xp` and `money` additively (they were in `RunRow` and the state
samples already; nothing new is recorded). `runner/viewer/runs.ts` was not
touched — it already populates `money` via `latest("money")`.

## `infra/fixtures/` — scenario fixtures for smoke characters (item 45)

An operator tool that puts a *logged-out* smoke character into a named scenario
by writing `acore_characters` rows directly, so a smoke can prove a late-game
claim in seconds instead of walking to it. `scenarios.ts` holds the data
(`tram-ironforge`, `trainer-northshire`, `northshire-fresh`), `apply.ts` the CLI,
and a `fixtures` compose service behind the `tools` profile is the host-side
invocation. Refuses any account outside `^(SMOKE\d*|PROBE)$`; nothing in
`runner/` or `sdk/` imports it, so `docs/CONTRACTS.md` is untouched.

Three things worth remembering. The write waits for `characters.online = 0`,
which the logout `SaveToDB` writes — the module's `DELETE /session` acks as soon
as the logout is queued, so anything written before that save lands is silently
overwritten. No items, ever: `item_instance` guids come from an in-memory
generator seeded at boot, and `ObjectMgr.cpp` deletes `character_inventory` /
`mail_items` / `auctionhouse` / `guild_bank_item` rows at or above its watermark
on the next start, so externally written items are both racy now and reaped
later. And `QUEST_STATUS_INCOMPLETE` is **3**, not 1 — 1 is `COMPLETE`, and
`_LoadQuestStatus` silently falls back to 3 rather than erroring, so a wrong
value there is a behaviour change you would never see in a log.

Verified live on Smokenav (SMOKE3, guid 217): applied `tram-ironforge`
(level 1 → 10, money 0 → 10000, zone 12 → 1537, position → -4838.95/-1318.46/
501.87, o 4.604) and put it back with `northshire-fresh`.

## Gate smokes on fixtures: measured first, and the premise did not survive

The plan was to move the three gate smokes (`quest-accept-status.ts`,
`kill-credit.ts`, `module-navigation.ts`) onto persistent fixture characters so the
preflight gate would *start* faster — the same conversion `travel.ts --from
tram-ironforge` got with item 45. Measuring first killed it: there is no startup to
save, and the fixture path would cost more than it saves.

**Where the gate's time actually goes.** From `data/runs/fleet-state.json`
(`preflight.results[].ms`, the supervisor's own child wall time) and the module's
per-session audit logs in `data/logs/wrathbench/`:

| phase | quest-accept-status | kill-credit | module-navigation |
| --- | --- | --- | --- |
| process start → first audit line | <0.1s | <0.1s | <0.1s |
| delete last run's character (real `CMSG_CHAR_DELETE`) | 0.014s | 0.012s | ~0.02s |
| gap delete → `POST /session` | 0.2s | 0.2s | 0.2s |
| `session_create` → `SMSG_LOGIN_VERIFY_WORLD` | 0.1s | 0.1s | 0.1s |
| the proving arc (in world → logout) | 19.4s | 47.8–54.4s (median 50.7) | 22.7–23.1s |
| child total (`results[].ms`) | 19.68s | 48.02s | — (not a gate smoke) |

Startup — delete plus create plus in world — is **0.2s median across 63 recorded
runs** (27 qaccept, 21 kill-credit, 15 nav). The delete is a real round trip, not a
`character_not_found` short circuit: the enum names the character and
`SMSG_CHAR_DELETE` answers result 71. And the gate's wall clock *is* kill-credit's
arc: `preflight-start`→`preflight-pass` measured 42.9s and 48.0s on the last two
gates, against kill-credit arcs of 42.7s and 48.0s. The two smokes run concurrently,
so the slower one is the gate.

**The tail is real but fixtures relocate it rather than remove it.** Three of those
63 startups were long: 22.2s twice (kill-credit) and 66.2s once (nav). Every one is a
run landing inside the previous character's 60s `WorldSession::expireTime`, where
`CMSG_CHAR_DELETE` is silently ignored and the smoke retries past the window — that
is, a gate re-running quickly after a failure, the case ADR-0023 already flags as the
expensive kind. The fixture path hits the *same* window from the other side:
`apply.ts` polls `characters.online = 0`, which only clears when `LogoutPlayer`'s
save lands, measured at ~36s in this same day file for the tram fixture. So the trade
would be a 22–66s delete retry for a ~36s online poll, and the median would go from
0.2s to seconds — a `bun infra/fixtures/apply.ts` subprocess plus a `POST
/characters` enumerate on every single pass, plus `WRATHBENCH_DB_*` on the `fleet`
service (and the recreate that implies). Slower on the common path, no better on the
bad one.

**What would actually cut the gate, and why it was not done.** Only kill-credit's
arc, since it is the critical path, and only by dropping work it currently proves:
its header calls the 783 accept → walk to McBride → turn-in → accept quest 7 "the
price of a kill credit", which is ~35s of the ~50. A scenario with
`quests.inProgress: [7]` and a vineyard-edge start would collapse it to login →
fight → `ADD_KILL` → loot, plausibly ~15s. Every claim that drops is proven by
quest-accept-status on a parallel account, so the *gate* would lose nothing while the
*script* would — a real trade, and the operator's to make, not a refactor's to
smuggle. Left open.

Also noted while reading: `module-navigation.ts` is gate-*ready* (reads
`MODULE_ACCOUNT`, deletes last run's character first) but is not in `fleet.json`'s
`preflight.smokes` at all, so it costs the gate nothing today either way.

times out instead of passing slowly. Lowering `timeoutMs` off the 22s happy path would
do the same.

throws `LegFailure`, kill-credit exits), the create-and-logout step (SDK client vs
raw HTTP), and the contended-account budget — travel keeps its 20 minutes at 60s
intervals, the gate gets 30s at 5s intervals, because a gate that waits twenty

## Service status badge replaces the fleet stats strip

The fleet page's header had grown to four lines of counters (supervisor line,
outstanding work, gate, account classes) that were read once and scanned past.
The one question they answered — is the service up — is now a colour dot and a
word in the top bar, on every page, with a popout (click, Enter/Space; Escape or
an outside click closes) of label → value rows: heartbeat (age; absolute time as
the title), jobs (live N / outstanding lower–upper), exhaust ETA, uptime
(supervisor `startedAt` → now; already on the wire), harness (the deploy's
`server.build`, falling back to the gate's), the worldserver's own build when it
differs, the deploy `detail` line while not `running`, and accounts busy/total
per class. Derivation is a pure function (`dashboard/src/lib/status.ts`):
API error → red "unreachable"; nothing yet → grey "loading"; no fleet-state →
red "down"; `failed`/`rolled-back` → red; a deploy window → yellow with the phase
word, or "paused for deploy" once the heartbeat is gone; no heartbeat → "down";
past three ticks → "stale"; else green "running". `/api/fleet` is polled once,
from the Layout (`lib/feeds.ts`), and shared with the fleet page — no second
poller. No API change was needed. The fleet page is now the table plus only what
needs acting on (deploy window/verdict, REJECTED config, a failed gate); the
strip-only helpers (`supervisorLabel`, `accountClassSummary`, `outstandingLabel`,
`outstandingTitle`) and `.strip` went with it.

Table tweaks in the same change: `tokens` and `cost` (the actual figure only,
`cost.actual` off `/api/runs`, blank with the pricing note as title otherwise)
are back for the job's current run; `source` is gone (it maps to the account
class); `tier` is headed `episode` and the row field is renamed with it; `models`
is headed `model`.

## One bag: worn-bag contents observed, `bag()` spans all bags (item 50)

Why now: `inventory_full` turn-ins on quests 33 and 183, a model hand-rolling
bag-full → `destroyItem` loops against a 16-slot ceiling while a worn bag had

`bagSlot<n>Lo`/`bagSlot<n>Hi` (n 0-35), the same lo/hi idiom as the player's

(swap/split stay off the allowlist). Not CONTRACTS-relevant, so no ADR. Built
to `:next` (b84f39ea1d8d), not deployed.

from the backpack first (`bag 255`, slot 23-38) then each worn bag

`Player::GetItemByPos` resolves behind `CMSG_USE_ITEM` / `CMSG_DESTROYITEM` /
`CMSG_AUTOEQUIP_ITEM` — verified in `PlayerStorage.cpp`), each row
`{ bag, slot, guid, itemId, name, count, quality? }`, `bags:
[{ slot, numSlots, name }]`, `totalSlots = 16 + Σ numSlots`. No
`state.equipped()`: `state.inventory.filter(i => i.slot < 19)` is the one-liner
and API.md says so. A worn bag whose create block has not arrived counts 0
slots rather than guessing. Existing actions keep `(bag, slot)`; no
name-based helpers (ADR-0015).
