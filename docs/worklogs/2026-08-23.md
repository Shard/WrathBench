Two decisions worth naming. **Membership is stamped-only.** The runs already on disk
ran at idle 10m / no-XP 45m, which is not what `e90` pins, so the reader still

compares; the default `?episode=e90` view is empty until the first stamped run. **An
override is a membership question, not a scoring one**: a filter that
`?includeOverrides=1` reverses, not a term in `unscoredReason`, or the exclusion could
never be shown. Bare watchdog defaults are unchanged (FOLLOW-UPS 48g).

## Stillborn runs (operator ruling; 10:46)

A run with zero `response` records in its trajectory — the model never spoke — and no
longer live is a launch that did not happen, not a short run. `runner/viewer/
stillborn.ts` (294610c) holds the one definition (zero responses **and** not live: a
run thirty seconds old has no response *yet*); `scanRunTotals` counts the records
inside the memoised whole-file scan, and `stillborn`/`modelResponses` ride on the run
and eval rows. The dashboard hides them from the runs list, eval, ladder and episode
member counts, each saying how many with a `show stillborn (N)` toggle;
`?includeStillborn=1` is the API spelling. `bun runner/src/archive.ts --stillborn
[--dry-run]` moves them to `data/runs/archive/<run-id>/`, which every enumeration
skips by name, and refuses any run whose files or fleet-lane records are warmer than
ten minutes. The count is deliberately not a turn count — the claude driver appends
one `response` record per content block — and a directory with no trajectory at all
is never called stillborn, because that was never a run. First sweep: 83 of 178 run
directories — free-tier lanes that 403'd on the first request, a claude-subscription
run whose CLI exited on a bad MCP path, and two lanes rate-limited into a pause nine
times each. None had a `tool_call` record either, so no externally-scaffolded run is
caught by the predicate.

## Sleeping made observant; `reclaimCorpse` made a helper (11:11)

One ADR-0016 softening pass (68b5a92, eff2a45) over the 2,086 `sleep()` calls of
>=20s in data/runs, which fall into three shapes: `Promise.race([routine,
sleep(28000)])` as a deadline (legitimate), `await sleep(25000);
sdk.reclaimCorpse()` (waiting out the server's corpse reclaim delay by hand), and bare
`await sleep(28000)` idling. Deterministic and identical for every model; not
score-comparable across the boundary.

(1) The sandbox's ambient `sleep(ms, options?)` still resolves after `ms`, but
resolves *with a reason* — `"elapsed" | "attacked" | "died"` — and early for the two
things a sleeping snippet would want to react to: `SMSG_ATTACKSTART` naming us as the
victim, and our own health observed at zero. A model that ignores the value loses
nothing, and `Promise.race` is unaffected by construction (runner/test/sleep.test.ts
pins it). Two deliberate non-wakes: `died` fires on the transition only, so the
corpse-run sleep that is already dead is not woken by the death it is handling, and
`{ wake: false }` is a pure timer. Bad arguments throw with what `sleep` takes rather
than a `setTimeout(undefined)` that returns instantly. Wake subscriptions are
registered after the client's own state fold and torn down in every exit path,
including abort.

(2) `sdk.reclaimCorpse(guid?, options?)` owns the delay and returns a verdict — `{ ok,
status: "reclaimed" | "not_reclaimed" | "unconfirmed", waitedMs, delayMs, attempts,
reason?, hint? }` — on the equipItem/buySpell pattern; the bare dispatch survives as
`reclaimCorpseAsync`. `SMSG_CORPSE_RECLAIM_DELAY { delayMs }` *is* tapped, and
`BuildPlayerRepop` sends it immediately before it resets the corpse's ghost time, so
the most recent one on the stream plus its own `ts` is when the reclaim becomes
legal; the wait is clamped by the announced delay so clock skew can never make it wait
longer than the delay itself. No such event in the retained 500-event buffer means
dispatch *now*, never a made-up 30s wait — the core sends nothing when no delay is
owed (`CalculateCorpseReclaimDelay` returns -1), and a too-early attempt is absorbed by
the retry. What is observable, stated exactly because every refusal path in
`WorldSession::HandleReclaimCorpseOpcode` returns silently (alive, spirit not
released, no corpse, delay not elapsed, further than ~39y): `SMSG_DEATH_RELEASE_LOC`
with `map: -1`, the first packet `Player::ResurrectPlayer` sends, corroborated by own
health leaving the released ghost's body value of 1 (`BuildPlayerRepop` sets health
to 1; a reclaim restores 50%). The ghost aura (8326) was considered as a third signal
and dropped: whether a passive aura reaches the client is a DBC question this repo
cannot check. Pre-flight names the two states that can never work (health 0 = spirit
not released, call `repop()` first; health > 1 = alive) and sends nothing for them; a
delay outlasting the budget answers `delay_not_elapsed` with how much is left;
`still_ghost` lists the three silent refusals; `unconfirmed` is the honest answer
when own health was never observed. Default timeout 25s, matching `killTarget`'s
reason (under the runner's 30s snippet cap); every wait honours the ambient snippet
signal. Prompt lines for both rewritten; sdk/README.md updated (eff2a45).

## `moveTo` takes a unit or guid; abandon says how far the move got (11:31)

From `data/runs/night-report-20260823/fanout-navigation.md` items 1–2 (da93f0a;
ADR-0015/0016 harness change — error text and the prompt both move). (1) 4 of the 7
fan-out runs (oc-b c8, qwen c12/c13, ox-alpha c14) threw a raw `TypeError: moveTo
position x must be a finite number, got undefined` reading `.x` off a
`state.units(...)`/`state.closest(...)` lookup that had returned nothing, always right
after an NPC name filter missed — the crash named the axis, never the lookup.
`moveTo`/`moveToAsync` accept a unit or a guid: a unit resolves through the state
cache at call time (a guid held across a patrol walks to where the unit is now); a
unit the cache has since lost falls back to the coordinates that object carries *and
says so in the hint*; a guid nothing in view answers to returns `{ ok: false, status:
"unknown_target", hint }` rather than throwing. `unknown_target` is deliberately not a
`WB_MOVE_RESULT` status — ADR-0027 gives the module the status vocabulary, and this
arm is the SDK answering before the wire, the way `killTarget` answers `lost`, so it
carries no `moveId`/`position`/`seq`/`ts`. Point calls are untouched down to the
rejection messages: only a guid-shaped argument takes the new path, so `moveTo(-1205,
981)` keeps earning "needs a point object { x, y, z }, got number". `moveToAsync`
takes the same targets but throws on an unresolvable one: the raw tier has no result
object to put a verdict in.

(2) Long synchronous moves against the 30s snippet budget: 6 of 7 runs hit the
abandon wall with a `moveTo` in flight, and nav-probe c4 re-issued the identical
blocking call 5 times, ignoring the abort message's background-routine suggestion
each time. Deliberately *not* fixed by capping or shortening the move (that would push
pathing detail back onto the model); fixed as an error surface, ADR-0016 rule 2. The
`EventAbortedError` a move raises on abort states how far it got — "~15y covered,
~220y still to go to (x, y)", degrading to naming the target when no position was
observed — and names `sdk.moveToAsync(target)` or a background routine plus polling
as the fix; the sandbox carries that sentence home on the liveness pong
(`abandonNote` → `pong.note`) so it lands in the host's abandon message, the only
channel an abandoned snippet still has. Separately, the host tells the child when the
snippet will be abandoned (`eval.deadline`, epoch ms), the child threads it into the
client as `ConnectOptions.deadline`, and `moveTo` uses it for one thing only: when
the straight-line distance at 7yd/s was always longer than the caller had left, the
*result's* `hint` says so — the estimate explains, it never decides. A deadline
already past reads as *unknown*, not as a budget of zero: a background routine
inherits the async context, and therefore the deadline, of the snippet that launched
it. One prompt sentence added (a move over ~200y cannot finish inside one snippet).
