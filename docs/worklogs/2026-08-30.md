## Strict keys: an unknown key on a roster entry or a queue job is refused by name

The `enabled: false` that silently did nothing (above) is now a refusal.
`parseFleet` compares every roster entry against `ROSTER_ENTRY_KEYS` (model,
tier, idle, driver, effort, apiBase, apiKeyEnv, billing, subscription, race,
class, watchdogs, maxToolCalls) and every queue job against `QUEUE_JOB_KEYS`
(ref, episode, repeat, enabled, account, subscription); anything else refuses
that entry or job, naming the key. Two keys get the obvious alternative rather
than a bare "unknown": `enabled` on an entry names the pause recipe (`idle:
"none"`), and `tokenEnv` — a real run-roster key that was flowing through and
quietly pinning a lane — names `subscription`.

Refusal semantics are the 2026-08-24 ones and nothing new: scheduling only,
never a drain. So the refusal carries the job names the thing could have spawned
under, and for a roster entry that had to be built (`refJobNames`): the file's
own jobs naming it, the policy's `<ref>-<episode>`, and a campaign's
`<ref>-<campaign>-<cell>`. The pre-existing subscription refusal shipped
`jobs: []` and would have drained a live freeplay run for a mistyped lane name;
it now uses the same helper. `--status` prints these through `formatRefusals`
already — its header said "refused by the account rules", which is no longer
the only rule, so it and the tick's spare line now say "config rules".

Ordering, deliberately: a queue job's strict-key refusal runs BEFORE
`applyPinAccountRules`, so a job the harness cannot read does not win an account
off a well-formed one behind it (a refused pin is disabled, and a disabled pin
is already allowed to park anywhere).

Not touched, because the gap is not there: campaigns and cells are zod
`.strict()` already (whole-file, which is their existing behaviour), and the
account lists are plain strings with no keys to get wrong. The retired
spellings (`tiers`, `runsPerEpisode`, `objective`, `character`, `resume`, …)
keep their own `fail()`s ahead of the strict check — naming those is worth
taking the file down for.

Tests in `infra/fleet.test.ts`: the `enabled` case refused by name with the

spared under a refused entry, a refused queue job leaving its neighbour

One consequence worth stating, because the refusal line does not: while an
entry or job is refused, an operator's own `enabled: false` on a job in that
refusal's `jobs` set is inert — the drain is filtered out, so the live run
finishes on its own. Same trade item 66 already made for pins. (A pinned job
whose refs are all gated spawns as `enabled: false` with a `gated` entry, which
is exactly the drain the sparing catches.)
