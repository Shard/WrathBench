## Strict keys: an unknown key on a roster entry or a queue job is refused by name

The `enabled: false` that silently did nothing (above) is now a refusal.
`parseFleet` compares every roster entry against `ROSTER_ENTRY_KEYS` (model,
tier, idle, driver, effort, apiBase, apiKeyEnv, billing, subscription, race,
class, watchdogs, maxToolCalls) and every queue job against `QUEUE_JOB_KEYS`
(ref, episode, repeat, enabled, account, subscription); anything else refuses
that entry or job, naming the key. Two keys get the obvious alternative rather
than a bare "unknown": `enabled` on an entry names the pause recipe (`idle:
"none"`), and `tokenEnv` — a real run-roster key that was flowing through and
quietly pinning a lane — names `subscription`.

Refusal semantics are the 2026-08-24 ones and nothing new: scheduling only,
never a drain. So the refusal carries the job names the thing could have spawned
under, and for a roster entry that had to be built (`refJobNames`): the file's
own jobs naming it, the policy's `<ref>-<episode>`, and a campaign's
`<ref>-<campaign>-<cell>`. The pre-existing subscription refusal shipped
`jobs: []` and would have drained a live freeplay run for a mistyped lane name;
it now uses the same helper. `--status` prints these through `formatRefusals`
already — its header said "refused by the account rules", which is no longer
the only rule, so it and the tick's spare line now say "config rules".

Ordering, deliberately: a queue job's strict-key refusal runs BEFORE
`applyPinAccountRules`, so a job the harness cannot read does not win an account
off a well-formed one behind it (a refused pin is disabled, and a disabled pin
is already allowed to park anywhere).

Not touched, because the gap is not there: campaigns and cells are zod
`.strict()` already (whole-file, which is their existing behaviour), and the
account lists are plain strings with no keys to get wrong. The retired
spellings (`tiers`, `runsPerEpisode`, `objective`, `character`, `resume`, …)
keep their own `fail()`s ahead of the strict check — naming those is worth
taking the file down for.

Tests in `infra/fleet.test.ts`: the `enabled` case refused by name with the
pause recipe, `tokenEnv` pointed at `subscription`, a live `glm-freeplay`
spared under a refused entry, a refused queue job leaving its neighbour
untouched and not taking the account, and a guard that the SHIPPED
`infra/fleet.json` refuses nothing (it carries no `enabled` on any entry —
75133d0 replaced it with `idle: "none"`, so the next recreate refuses nothing).
`bun test infra` 322 pass, root `bun run typecheck` green.

One consequence worth stating, because the refusal line does not: while an
entry or job is refused, an operator's own `enabled: false` on a job in that
refusal's `jobs` set is inert — the drain is filtered out, so the live run
finishes on its own. Same trade item 66 already made for pins. (A pinned job
whose refs are all gated spawns as `enabled: false` with a `gated` entry, which
is exactly the drain the sparing catches.)

## Reflection at rest, and an episodic log written before each trim

Three operator decisions landed together (docs/METHODOLOGY.md, "Reflection is
the model's to take, and only at rest" and "An episodic log, written before
each trim, read back at rest"). The tool surface goes from six to nine.

The reason all of this hangs off one world fact is that a rest area is the only
place the game itself says "nothing is happening to you right now". So the SDK
decodes `PLAYER_FLAGS_RESTING` (0x20, AzerothCore `Player.h`) off the
`playerFlags` integer the module already serves — no module change, the same
shape as the existing `taxiFlight` decode off `unitFlags`, and only from a
block that actually carried the field, so an update that omits it does not read
as "not resting". The HUD prints `resting` on its `ui` line when it is true and
nothing when it is not: a per-turn "not resting" is a token for a fact the
model can act on only in one direction.

`reflect` refuses with that world fact and nothing else, so the harness never
tells the model where an inn is. One reflection per rest visit, re-armed by the
false→true edge the context builder observes — which is why the gate is fed
from the state sample rather than from reflect calls: a model that reflects,
travels and returns has to be re-armed by a leaving nobody asked about. Reflect
turns count as turns; a free turn would be worth gaming for.

The episodic log is deliberately not the scratchpad. Working memory the model
rewrites at will cannot tell it where things went wrong, so `log_status`
appends and the harness stamps turn/level/zone. It is read only through
`read_log`, only inside the window `reflect` opens — which closes when the
character leaves the rest area, on a 30-turn breaker, or at run end.

The one place the spec could not be met literally: the block trim is exact in
the message *count*, but the count a turn adds is not known until the model has
answered, so "the last turn before a trim" is not decidable at the turn's
start. `trimExpected` estimates from the previous turn's growth — exact while
the tool-call count is steady, off by a turn when it changes — and the notice
therefore says the trim is about to happen rather than naming a turn. Saying
otherwise would put a false sentence in the prompt, which `contextSentence`
already settled as the worse fault.

Not built, deliberately: no exemption of reflect turns from turns-to-level (the
decision says they count, so `results.ts` needed no edit), and no UI — the
reflect and episodic counts surface on the terminal timeline, which is a
consumer that already existed. The harness version needed no bump either: it is
`git describe`-derived in both `runner/src/version.ts` and `infra/run-roster.ts`,
so the commits below *are* the patch; the 0.5 series is unchanged.

Review pass, same day. The first cut of the pre-trim prompt *predicted* the
crossing from the previous turn's message growth, and that is simply wrong when
the crossing turn is bigger than the one before it: at 47 messages with a
previous growth of 1 nothing fires, the model then makes three calls, and the
trim lands having never been announced. The fix is to stop predicting. The cut
is now applied one turn after the crossing that earns it (`laggedLength`), so
the crossing is a fact already in the history when the prompt is raised: every
trim is preceded by exactly one prompt, on the turn immediately before it, for
any growth pattern. The window therefore sits above `MESSAGE_WINDOW_MAX` by at
most one turn's growth, for one turn per block — the constants are untouched,
the cut still moves only in whole blocks, and the cache prefix is still stable
within a block, which is what the ceiling was protecting. The notice went back
to the decision's own wording ("will be trimmed after this turn"), which is now
true. Three window tests in `context.test.ts` were updated deliberately for
this, including the ceiling bound.

Also from the review: the claude-code driver never wrote the `run_end` close
for an open reflection window (its teardown is `shutdown`, not `runLoop`'s
`finally`), and the breaker's turn count is named to the model in the notice
that says the window has closed — a fact about what happened, which the earlier
comment wrongly claimed never reached the model.

One implementation detail the decision does not reach: the standalone MCP
server has no context builder, so nothing there samples the world on a clock or
counts turns — a reflection window opened in that mode could never observe the
character leaving and the breaker could never fire. It answers `reflect` and
refuses `read_log` rather than serve the log through a window that cannot
close.

## The run feed reads the reflection windows, and its clock counts from the run

The operator's "chat stream" was the run page's turn feed, not in-game chat.
Turns inside a reflection window now carry the same experience purple the map's
rest glyph uses — a left rule on every row of the window, the word on the turn
header only, or it would repeat down the feed — and the three tools of the
surface (`reflect`, `log_status`, `read_log`) are labelled wherever they are
called, independent of the accent: a refused `reflect` opens no window and is
still one of them.

The windows are served rather than derived client-side. They are derivable from
the entry feed in principle, but the `open` that starts a window routinely sits
above the two hundred entries the page has loaded, and a window whose opening
record scrolled off would silently stop accenting. `/api/run/<id>` carries them
as half-open `[fromTurn, toTurn)` turn ranges off the same incremental tail that
already accumulates achievements and levels, so a live run's accent grows with
it. Half-open is not an arbitrary convention: both records are drained in the
context builder at the top of a turn, before the model answers it, so the close
names the first turn spent *acting* again. `run_end` is the exception and reads
as "to the end of the run", since there is no turn after it.

Separately, the feed's per-row stamp became elapsed time on the run's own clock
(`0:00`, `12:34`, `1:05:22`), with the wall clock kept on hover. "03:41:22" is
not a question anyone reading a trajectory has; "how far in" is, and it is the
figure that reads the same across two runs compared side by side.

## `WRATHBENCH_VIEWER_TILES_PUBLIC`: minimap tiles opt back in on a public viewer

Public mode withholds three routes, and minimap tiles are the one an operator
may want back: a public deployment that has decided it may serve them had no

## Minimap tiles on the gated public site

The operator's call today: the gated Cloudflare site serves tiles, so the map
page shows terrain there. Four pieces, and the shape of each is chosen so that
"the routine publish never carries these bytes" is true by construction rather
than by a conditional.

- **`infra/publish-tiles.ts` is its own script, not a flag.** The snapshot loop
  runs unattended every five minutes; a `--tiles` flag on it would be one env
  var away from uploading the extraction on a timer. The tile publisher is run
  by hand (`--dry-run` prints the plan, `--upload` performs it), reads only
  `data/minimap/<mapId>/<row>_<col>.png`, and writes only
  `tiles/<mapId>/<row>_<col>.png` in the same bucket with the same `S3_*` key
  pair. Skip-unchanged is a content hash, not size+mtime: a re-extraction
  rewrites every mtime without changing a byte, and a run with nothing new must
  cost nothing. The hash manifest lives in the bucket (`tiles/manifest.json`)
  and is written after the objects it names, for the reason `publish-core.ts`
  flips `manifest.json` last.
- **The key is the viewer's path, verbatim.** Content addressing lives in the
  manifest and never in the key: the SPA and the gate both address a tile by
  map/row/col, so a hashed key would need a lookup in the read path.
- **The gate.** `/tiles/*` is served from the R2 binding behind the same
  `authorize()` as `/v1/*`, `image/png`, `private, max-age=3600`,
  `X-Robots-Tag: noindex` — the viewer's own `TILE_PUBLIC_*` constants, copied
  into the Worker because `runner/viewer/tiles.ts` reads the filesystem and
  cannot be bundled, and pinned equal in `gate.test.ts`. Only
  `/tiles/<digits>/<digits>_<digits>.png` is reachable: anything else under the
  prefix is a 404 rather than a fall-through to the SPA's index.html, which is
  what keeps `tiles/manifest.json` and a probe for a listing from answering
  200. `/robots.txt` is now answered ahead of the gate (`Disallow: /tiles/`,
  `Disallow: /`) — a crawler handed a 401 login form has been told nothing.
- **The SPA drops its `SNAPSHOT_MODE` guard on tiles.** One path in both
  builds; a host with nothing behind the prefix 404s, which is the same miss a
  lab machine without the extraction already produces, and the labelled grid
  square is drawn either way. `dashboard/test/snapshot-client.test.ts` pinned
  the old fact and now pins the new one.

Two follow-on hardenings after review: the manifest read distinguishes a
missing object from a failed one (a 403 or a wrong endpoint would otherwise
read as "no manifest yet" and quietly re-upload the whole extraction while
reporting success), and the report says whether the bucket had a manifest at
all, so `--dry-run`'s "everything would upload" means a first run and nothing
else. Bytes are hashed and dropped rather than held, and re-read for the
handful that survive the diff, so a no-op run's memory does not scale with the
extraction. Item 85's retirement steps gained the line they were missing: the
same-origin `/tiles/` path only resolves while one Worker serves both planes.

Guards: the tiles are under `data/`, gitignored at the directory level, and the
publisher's only writes are to the bucket; nothing reaches the SPA bundle.
`runner/test/snapshot.test.ts` already pins that no snapshot artifact path
names a tile, with the flag set in the environment — that test is the one that
would catch a regression here and it is unchanged.
