# 2026-08-27

## A restart still strands the freeplay session it was supposed to preserve

Removing the six-hour cap (#26) made the `idle: "unlimited"` lane one continuous session, but it did not make that session survive a supervisor restart. Live evidence: `fleet-sub-opus-low-freeplay-opus-low-20260825-a6` was operator-paused by a forced fleet restart, `planResumes` reported it as `paused, not in config — resume by hand or archive`, and the policy then launched a7 and a8 on fresh level-1 characters. The cap was gone and the continuity was still gone with it, which is the whole reason the lane exists.

The cause is one gate in `planResumes`. A paused run with no matching job in the file is mapped onto a synthetic policy job, and that branch was written when `e90` and `e360` were the only episodes the policy produced. The policy makes freeplay picks now (`wantsIdle`, models.ts), so a freeplay lapse fell straight through to the listing. Nothing downstream was wrong: the attempt number reads off the run id's `-aN`, the job name is `${ref}-freeplay`, `isExtraJob` still stamps `extra: true`, and `jobSpawn`/`withResume` already put the paused run id on the front entry with `episodeMs: null`.

Fixed by admitting `freeplay` to that branch, gated on the ref actually being in the unlimited lane (`idle === "unlimited"`). A ref whose idle lane the operator turned off owes no session and is still listed rather than resumed.

Second defect found while testing the first. The candidate ref was resolved by scanning the roster for any entry sharing the run's model and effort, so with two entries on one model+effort the resume could land on whichever came first in the file — continuing a session under a ref that owes none, on a job name it was never launched as. The ref the run id names is the authority now, and model+effort is the fallback only when the run id matches no ref at all. This tightens `e90`/`e360` by the same rule; in practice they never reach the branch, because `classifyLapse` ends a scored lapse as a failed attempt before it gets there.

That authority rule was at first applied to only half the function, which review caught. `planResumes` decodes `launchedUnder` from the run id at the top, but the `fromFile` lookup ahead of the synthetic-policy branch still scanned the configured jobs for one whose refs intersect *any* model+effort sibling. So a run launched under ref A could be claimed by a pinned or queue job written for ref B — B's job name, lane, account and credentials, none of which the run was launched with. The visible symptom was worse than a mis-selection: with B pinned to another account the run was stranded and listed as `pinned job <B> is on RUNNER4, the run was on RUNNER3`, naming a job it had nothing to do with. `[launchedUnder]` is the candidate ref set for both lookups now, falling back to the model+effort scan only when the run id decodes to no ref. It narrows which *refs* may match, not which jobs, so a rotation job that genuinely lists the authoritative ref still claims its run.

Also corrected two statements in OPERATIONS.md that still described the idle lane as capped at 6h.

## The resume argv carried no leash at all

Planning the resume was only half of it. `episodeArgv(spec, true)` returned `[launcher, --resume, <run-id>]` and nothing else, and `run.ts` reloads the stored `meta.json` config on `--resume`, replacing a watchdog only when the flag is explicitly present. So a freeplay run created before #26 — stored `watchdogs.episodeMs: 21600000` — comes back under its stored six hours no matter what the roster now says. The absence of `--episode-ms` proves nothing here; only `--watchdogs-json {"episodeMs":null}` migrates the run. That is exactly why the live a6 needed a hand: the operator resumed it with that JSON override explicitly. My first regression asserted the absence of `--episode-ms` and would have shipped the cap.

Fixed by splitting the limit and watchdog flags into one `leashArgv` helper that both paths call, so a resume now restates `--max-tool-calls`, numeric `--episode-ms`, and `--watchdogs-json` from the current roster while identity — driver, model, account, effort, objective, wiki, race/class, episode, campaign/cell — still comes back from `meta.json` and is never restated. Automatic resumption of a pre-#26 freeplay run now migrates its leash onto the current no-cap policy instead of preserving the old one. Both spellings are pinned: the numeric case in `roster.test.ts` and the `episodeMs: null` freeplay migration in both `roster.test.ts` and the incident test in `fleet.test.ts`.

The general shape is worth naming: two components were each correct about their own half and wrong about the boundary. The supervisor assumed a resume re-applies the roster; the runner assumed anything it was not told to change should stay as stored.

Not shipped: this is a worktree branch (`fix/freeplay-policy-resume`), unpushed and unmerged, and the live supervisor is running the old code. Until it restarts on this build, a6 is the operator's to resume by hand (`--resume fleet-sub-opus-low-freeplay-opus-low-20260825-a6`) or archive; the a7/a8 characters it raced are unaffected either way.

## The wall clock was not the only thing resetting the session

Removing the six-hour cap and fixing the resume still left the lane with an automatic reset in it, found by reading the live run rather than the code. `fleet-sub-opus-low-freeplay-opus-low-20260825-a6` was at **410 of 500 tool calls** — roughly ninety calls from terminating `tool-call-limit`, after which the fleet would have started a fresh freeplay run on a fresh level-1 character, exactly the outcome #26 and the resume fix were both for. It was not hypothetical: all six historical `sub-opus-low` freeplay runs stored `maxToolCallsPerEpisode: 500`, **four of them ended `tool-call-limit`** and a fifth ended `episode-limit`, and each next policy attempt rolled a new character. The continuity work had been aimed at the clock while the ceiling was doing the same job faster.

The path was entirely ordinary, which is why nobody had looked at it: `episodeDimensions("freeplay")` returned `maxToolCalls: undefined`, so `run-roster` omitted the flag, so `runner/src/config.ts` defaulted the effective ceiling to 500, so `adapter-claude.ts` terminated there. Every layer was doing what it was written to do. A runaway guard sized at a thousand calls per thirty minutes is a rate, and a rate has no meaning on a session with no minutes.

To stop the imminent loss while this was fixed, the operator paused and resumed that exact run with a finite `--max-tool-calls 1000000` override. That is an operational leash, not the contract — a number large enough not to be reached, chosen because it needed no code change. Bramwick is the same character throughout.

The contract this branch implements is narrower than "freeplay is unlimited":

- `RunConfig.maxToolCallsPerEpisode` is `number | null`, null meaning disabled. `--max-tool-calls 0` is the external spelling, normalised to null on read in both the fresh and the resume path, so the transport sentinel is never stored, compared or served — the same trick `--no-xp-ms 0` already used for a watchdog.
- Only the policy-generated `idle: "unlimited"` lane materialises with it. `episodeDimensions("freeplay").maxToolCalls` is null, and `jobSpawn` drops that key unless all three hold: `job.source === "policy"`, `job.episode === "freeplay"`, and the ref's idle axis is `unlimited`. The first of those was missing in review — the gate read the ref's idle axis alone, so a freeplay job written into the fleet file naming an idle-capable ref would have inherited the uncapped lane it never asked for. It is the job that earns this, not the ref: an arbitrary freeplay experiment and every `probing` job keep stating their own ceiling and inheriting the 500 when they state none.
- Both the fresh and the resumed argv carry the flag, for the reason the section above gives: absence of a flag is not absence of a cap. A resume rewrites a run stored with 500 to null while its run id, account, character, session token, trajectory and scratchpad stay the stored run's, and the comparability tuple restamps because a budget really did change.
- The MCP boundary still enforces every positive ceiling unchanged. The extracted predicate matters more than it looks: the old branch was `toolCalls >= cap`, and widening `cap` to `number | null` would have coerced null to 0, so `0 >= null` is true and an *uncapped* run would have terminated `tool-call-limit` on its very first tool call. The RED test caught exactly that.

What is deliberately unchanged: the 20-minute idle watchdog, the snippet-runaway guard, fatal adapter and harness errors, stale handling, and any explicit operator limit all still end the session. This removes one automatic reset; it does not make the lane survive every fatal condition.

Not shipped, again: branch only, unpushed and unmerged, live supervisor still on the old code, and the live a6 is untouched by this work — it is running under the operator's 1,000,000 leash and stays there until the supervisor restarts on a build that carries this.
