# 2026-09-05

A durable freeplay stream reads as one run now. Its stats were only ever recorded
per attempt, so the run page answered "how many quests has this character done"
with the last session's tally and a reader could only see the run one session at
a time. The chain is aggregated at READ time in the viewer, the runner is
untouched, and the run page leads with the whole stream.

## The problem

A freeplay stream is one character across attempts (docs/OPERATIONS.md, "Freeplay
streams are durable"), linked only by `continuedFrom`. Every counter the runner
keeps is per attempt: `questsCompleted` is that session's own
`completions.length`, the tokens and the cost are that attempt's trajectory, the
playtime is that attempt's active segments. `fleet-sub-opus-low-...-a12` reports
0 quests; the character has done 7. The run page's only acknowledgement of the
chain was a one-line "attempt 2 of 2 · continues …", so seeing the run meant
renavigating attempt by attempt, and every figure on the page was the session's.

## What was built

**The lineage walk moved into the viewer** (`runner/viewer/lineage.ts`, 80d96ff).
The server needs the chain too, and the aggregation and the page's attempt strip
must count the same attempts. It is import-free, so the dashboard reaches it over
the `@viewer/*` alias the way it already reaches `worldmap.ts` — the third module
to cross that line, and the three places that say "two modules" were swept with
it. Its tests moved to `runner/test/viewer-lineage.test.ts`.

**`/api/run/<id>` carries a `stream`** (`runner/viewer/stream.ts`, 0886d23): the
whole chain oldest first, each attempt with its own figures, plus the totals over
them. Served only for a run with lineage, and only behind a freeplay gate
(stamped tier or a `continuedFrom`), so a scored run's page pays nothing; behind
the gate it is the listing's own memoised rows, so an ended attempt is read once
per process and this page and the ladder cannot disagree about what a stream is.
The chain served is the FORWARD one — the deepest under the root — because a
reader on attempt 11 wants to see 12.

Nothing is written back. What the runner records is the model-visible surface and
a methodology matter; an old run is read differently, not relabelled. The rules,
which are the whole substance of the change:

- a tally sums (quests, xp, playtime, tokens, calls, deaths, flights, spells,
  talent spends, trades); a sum over attempts where NONE recorded a kind is null,
  never 0, and an attempt whose `run.sqlite` predates a column contributes
  nothing rather than a zero;
- a state comes from the furthest attempt that recorded one: level (the highest
  observed — a character never de-levels), money, and `achievements`, which is
  already the character's whole backlog and would be counted once per
  continuation if summed. `SpellFacts.atLogin` is the same rule pointing the
  other way — the OLDEST served attempt's baseline, since attempt 2 logged in
  holding attempt 1's book — and `TalentFacts.talents` is the distinct ids of the
  merged marks rather than a sum of distinct counts;
- **cost is two sums and a coverage.** A `CostFigure` carries a basis, a price id
  and a date, and a chain of attempts priced three different ways has no honest
  single basis — so `StreamCost` adds the dollars, keeps actual and expected
  apart as `CostView` does, and states how many attempts each sum covers.
  `asIfMetered` rides along so a subscription stream does not read as a bill;
- the token `source` degrades to the weakest any attempt reported: one
  `snapshot`-sourced attempt makes the stream's total under-read, and calling it
  `reported` would hide the caveat the label exists to carry.

The public projection ships it whole (`projectStream`): every id and figure is
already public per attempt. Two things are withheld for reasons the file already
gives — a pause reason becomes the fixed token, and the death figures are dropped
outright, because `RunDetailResponse.deaths` is not projected at all (corpse
positions) and the stream must not open a second door onto the same fact. They
are `deaths?:` rather than `deaths: null` so "this viewer does not answer" stays
distinct from "the run recorded none".

**The run page is the stream.** An attempts strip replaces the one-line lineage
paragraph: every attempt in order, the current one marked, each a link carrying
its status, level and playtime. Above this attempt's XP chart is the stream's
level-against-cumulative-playtime line, drawn by the same `StreamPlot` the
freeplay field uses — `stitchStream` was factored out of `streamSeries` so the
field's twelve lines and the run page's one are the same stitching, not two.
The sidebar leads with the character's totals ("the stream · N attempts") and
keeps the run's own figures underneath, under a heading that says "this attempt".
The feed stays per attempt, because a trajectory is one run's; it gets a link at
each seam — "earlier: attempt N-1" at the top of the earliest window loaded, and
"continues in attempt N+1" at the bottom of an attempt that has ended.

The client-side `/api/results` lineage fetch is now the FALLBACK only: it runs
when the server answered no `stream`, which is a snapshot or a viewer built
before today. It recovers the line, not the totals, which cannot be derived
there.

**The ladder's `streamRows.questsCompleted` is the chain's sum**, with the same
null-vs-zero rule. Level, xp and money stay the furthest attempt's: they are what
the character holds, not a tally. The runs table is untouched by design — it is
an inventory of runs, and a run's row is that run's figures.
