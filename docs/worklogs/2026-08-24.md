## Run view redesign: two-column layout, fixed autoscroll, prominent XP/level chart

The run detail page (`dashboard/src/pages/RunDetail.tsx`) was one long scroll —
meta cards on top, feed below, a tiny XP sparkline buried among the cards, and an
autoscroll that called `window.scrollTo` and did nothing useful. Reworked into a
two-column inspection view.

**Layout.** The page is a flex column: a `fleet / <id>` heading, a full-width XP
chart, then a `.runview-cols` row. Left (`--log-col`, default 70%) is the feed,
its own scroll container. Right (~30%) is everything else — the autoscroll toggle
and live-activity line, all the meta cards (model, character + inventory, tokens,
playtime, cost ×2, level trace), the comparability tuple, termination/pause
banners, and the server footer. Both columns scroll independently, so the run's
meta and the toggle stay in view while the feed scrolls; no sticky needed. Under
900px they stack, sidebar first, feed kept a scroll container (`max-height: 70vh`)
so the autoscroll path is identical in both modes. `.runview-cols` has a 320px
floor so a short viewport lets `main` scroll rather than crushing the feed.

**Autoscroll.** The log column is the scroll container. A new entry pins it to the
bottom (`scrollTop = scrollHeight`) *from an effect on `entries`*, not from the SSE
callback — reading `scrollHeight` before Solid commits the new nodes lands
mid-list and silently flips follow off (the old bug in a new costume). Scrolling up
past 32px turns follow off; scrolling back within it turns it on (`atBottom`,
pure). The manual toggle in the sidebar overrides and is persisted in localStorage
(try/catch guarded); a scroll-driven off is session-only and never saved.

**XP/level chart.** Full-width inline SVG above both columns (`components/XpChart.tsx`).
X = time from run start to `min(now|endedAt, start+episodeMs)` with ~5 elapsed-time
ticks (mm:ss / Hh Mm). Y = cumulative XP, with a dashed gridline + `L<n>` label at
the XP offset each level began. Cumulative XP is a *lower bound* reconstructed in
`lib/runview.ts`: `StatePoint.xp` is within-level and resets, so the total carried
into a level is the sum of each lower level's last observed within-level xp — it
under-counts by whatever was earned between a level's final sample and the ding, a
gap bounded by the sampling interval and never invented upward. Level and xp are
read off the *same* sample (the old sparkline filtered the two into separate lists,
which mis-pairs them), samples sorted by ts, curve clamped monotonic. Comment notes
this is the simple version and uPlot is the long-term plan for denser series; no dep
added. The small level sparkline stays in the sidebar; the XP sparkline is dropped.

**Inventory.** The `carrying:` / `equipped:` lines (item 50, shipped db43c3c) moved
into the sidebar character card with the rest of the meta — not duplicated. `—` for
a run that predates the `items` column, `none` for a recorded-empty side.

Tests: new `dashboard/test/runview.test.ts` pins the band derivation (offsets, same-
sample pairing, monotonic clamp, unordered sort, level-jump, x-window with episodeMs
capped at now / endedAt) and `atBottom`. `bun test` 111 pass, `bun run build` clean.

Verified against the live freeplay run `fleet-nav-probe-freeplay-sonnet-...-c2`
(L5, 6254 entries, 187 state samples, 6h episode): served bundle
`index-B1mKDya-.js` → `RunDetail-BdSHtGji.js` is the new one; the derivation
yields bands L1–L5 at cumulative offsets 0 / 200 / 1028 / 2356 / 4444. Inventory
shows `—` (this run predates the column).

## Fleet: concurrency cap keys on a rate-limit key (free pools capped per platform)

`policy.maxConcurrent` keyed on the driver, so every free OpenRouter + OpenCode +
local model shared the `openai` driver and could not be capped apart. OpenRouter
enforces a daily cap on `:free` models; running several free OpenRouter runs in
parallel burned the budget and produced broken runs. The cap now keys on a
rate-limit KEY (`concurrencyKeyOf`, `runner/src/models.ts`): a free model on a
shared free platform counts under `openrouter` / `opencode`; everything else keeps
its driver key. `fleet.json` now ships `maxConcurrent { claude-code: 2,
openrouter: 1, opencode: 1 }`.

Roster → key mapping (stated for the record):
- `nav-probe`, `sub-opus`, `sub-opus-low`, `sonnet`, `sonnet-low` (claude-code) → `claude-code`
- `ox-alpha`, `nemotron-ultra`, `nemotron-super`, `nemotron-nano`, `north-mini-code`, `laguna-or` (free, OpenRouter/no-apiBase) → `openrouter`
- `muse-spark`, `hy3`, `laguna-oc`, `x-preview-f` (free, opencode.ai) → `opencode` (host normalized in the key fn only)
- `deepseek-flash` (paid, projects to openrouter) → `openai` — NOT a free key; governed by `policy.paid.maxConcurrent: 1`
- `qwen3-8-27b` (local, LAN) → `openai` — NOT capped by the free keys; its one local account is its limit

The free branch gates on `driver === "openai"` and reads the platform from
`platformOfBase(apiBase) ?? "openrouter"` (never the driver), so a `:free` slug
pinned to `driver: "openai"` with no base still lands in `openrouter`. `platform.ts`
is untouched — `run.platform` keeps the `opencode.ai` host spelling; the key fn is
the one seam that normalizes it to `opencode`. Named "key" not "lane" because
`lane` is retired (ADR-0034); ADR amendment records the concept.

Naming swept everywhere: `concurrencyKeyOf` / `CONCURRENCY_KEYS` / `isConcurrencyKey`
(models.ts), `concurrencyKeyOfRef` + the `{ keyOf, max, running }` concurrency
field + `keyCount`/`countKey` locals (run-fleet.ts), the two `--status`/`--dry-run`
print lines, the held reason (`cap: <key> <= n`), the fleet.json `_notes`, and the
viewer doc comments. `parsePolicyBlock` validation accepts the new keys and rejects
unknowns listing the allowed set.

Tests: extended `runner/test/models.test.ts` (key derivation per roster class,
validation accept/reject) and `infra/fleet.test.ts` (openrouter free key caps at
one while a paid openrouter model runs beside it; shipped-fleet.json assertion).
`bun test` in runner/ = 530 pass / 0 fail; typecheck clean. `bun test infra/` =
155 pass / 1 fail — the one failure (`fleet.json` nav-probe `repeat: 1` vs the test's
expected `"loop"`) is pre-existing at HEAD and untouched by this change.

Deploy: the running supervisor validates config with BOOTED code, so it keeps the
old per-driver cap (and shows a REJECTED banner on the new `openrouter` key) until
`docker compose -f infra/compose.yml up -d fleet` recreates it. Benign — no runs
break, runs resume on recreate.

### Item 59 fell out of validating the slugs: cache writes were never read

Probing `gemini-3.7-flash` showed OpenRouter sends `cache_write_tokens` **nested
under `prompt_tokens_details`**, and `toUsage` (`runner/src/adapter.ts`) read only
a top-level `cache_write_tokens` — so the counter arrived on every response and
was dropped, and the viewer's `expected` priced every cache write at zero. COSTS.md
had predicted this gap but mis-diagnosed the cause as "no provider emits one"; the
provider does emit one. `toUsage` now flattens writes exactly as it already
flattened reads (top-level wins, details are the fallback), the zod usage block
accepts the field in both positions, and `costOf` already subtracts reads *and*
writes from the prompt before charging input, so nothing double-counts. Three
tests in `runner/test/adapter.test.ts` pin the nested shape, the top-level
precedence, and that a provider reporting nothing leaves the field absent rather
than zero. Runs before this fix carry no write counter and never will; `actual` was
never affected, since OpenRouter reports `usage.cost`.

It mattered now because luna ($0.25/M write, 1.25x input) and gemini-3.7-flash
($0.0208/M, a storage-only rate below input) are the first two roster models to
quote a write tier at all.

`bun test runner/` = 533 pass / 0 fail, `bun test infra/` = 156 pass / 0 fail.

## Viewer bound to the LAN so other machines can help

The viewer was running on 127.0.0.1:8090 with no `WRATHBENCH_VIEWER_LAN`, so only
this host could reach it. Restarted with the opt-in that already exists
(`runner/viewer/serve.ts`; `WRATHBENCH_VIEWER_LAN=1` → `0.0.0.0`), keeping the env
the old process had (`WRATHBENCH_MODULE_URL=http://192.168.192.3:8086`,
`WRATHBENCH_FLEET_CONFIG=infra/fleet.json`). Now `LISTEN 0.0.0.0:8090`, `/api/info`
and the SPA both 200. No code change — the opt-in was always there, it just was
not being passed.

Two things worth writing down, both of which have bitten this setup before:

- **The firewalld rule has to be `--permanent`.** The note in
  `.claude/commands/orchestrate.md` recorded the rule as "runtime-only", which is
  exactly why LAN access kept lapsing — a runtime rule does not survive
  `--reload` or a reboot. `runner/viewer/README.md` now carries the two-step
  recipe (env + rich rule) with the rule scoped to `192.168.1.0/24` rather than a
  bare `--add-port`, which would open 8090 to every network in the `public` zone.
  `enp8s0` is in `public`, the default zone.
- **`curl http://<lan-ip>:8090` from the host proves nothing.** That traffic is
  delivered over `lo` and never crosses the zone, so it returns 200 whether or not
  the port is open to anyone else. It has to be verified from another machine.

The rule itself is not applied — `firewall-cmd` needs root and this session has no
passwordless sudo. Left for the operator; the command is in the README.

## Trial cap on the two new paid models, after measuring luna in flight

The pre-launch estimate for luna was ~$0.42/e90, derived from the token shape of a
deepseek e90 (1.8M prompt / 54k completion). Watching the real run made that 3.5x
wrong, and the reason generalises: **token volume per episode is set by the
model's speed, not by the episode length.** Luna ran 107 snippets in 15.8 minutes
where deepseek managed 139 in 114, so it burns ~8M prompt tokens in the same
90-minute window. Provider-reported `usage.cost` at 15.8 min was **$0.2562**,
projecting to **~$1.46 for a full e90** — and a full paid quota (3 e90 + 1 e360, an
e360 being ~4x the wall clock) lands near **$10**, which is the whole daily budget
for one model.

So both new entries take a per-entry `runsPerEpisode {e90: 1, e360: 0}` instead of
the paid default 3/1. `targetFor` (`runner/src/models.ts`) prefers the entry over
`policy.paid`, so this needs no policy change and no supervisor restart — the
field is already in the booted schema. `--status` confirms it live with no
REJECTED banner: `gpt-luna 1/1` (its in-flight run *is* the trial) and
`gemini-flash 0/1`, held behind it on the paid cap. Bounded spend for the pair is
now ~$3–6 rather than ~$10–17.

Worth noting for whoever scores it: luna reached **L3 at 17 minutes**, which is
where deepseek's best e90 finished after 114.

The general lesson is now in COSTS.md §5: take a real `usage.cost` reading from
the first 15 minutes of a new model's first run; do not extrapolate a cost from
another model's episode shape.

## The map replay recursed, and the fix was a seam rather than an `untrack`

Firefox reported `InternalError: too much recursion` under the play slider, and
the map froze while the slider itself moved. One cause for both. `ingest()` read
`activeMap()` and `selected()` and wrote `setMaps`, `setCount`, `setActiveMap`
and `setSelected` — from inside the effect that fed it. Live, that mostly settled
by accident: the poll hands out the same objects each time, so `setSelected` saw
an unchanged identity and stopped. Replay does not have that luck. `positionsAt`
mints a fresh `AgentPosition` on every call, so the write always looked like a
change, the effect always re-entered, and it never reached a coherent frame —
which is exactly what "the slider works but the map does not move" looks like.

An `untrack` around the reads would have silenced it and left the shape that
produced it. The real answer was to finish the split the file's own header
claims: the renderer owns mutable state and `requestAnimationFrame`, Solid owns
what is displayed. So the fold became `syncPips`, a plain function over a plain
`Map` that touches no signal (`lib/mapview.ts`), and everything the page shows
moved into `lib/mapstate.ts`, which is memos over four sources — the feed, the
track, the pinned map, the selected *id* — and writes nothing at all. Selection
is an id rather than a reading, so a fresh object per tick can no longer be
mistaken for a change. The sticky "stay on this map while it still has an agent"
choice, the one thing that genuinely needed to read its own last answer, is a
`createMemo` reducer taking `prev` as an argument: `chooseMap` is pure and the
stickiness is an input, not a write-back.

Effects in the page now go one way. The feed effect reads the track, cursor and
poll and writes the feed signal plus the pip map; the follow effect reads the
cursor's map and writes the pin; the fit and route effects read signals and write
only renderer state. No signal is read and written in one scope, which is a
property of the file's shape now rather than a thing to remember.

The review that followed found three real things and left two. Fixed: playback
stepped with `points.find`, a full scan of the track four times a second, now
`nextSampleAfter` over the existing binary search; the replay route was rebuilt
from the whole prefix on every frame including every frame of a pan, now cached
by the effect that owns it; and a fast `?run=a` to `?run=b` could let the loser of
the race win, now guarded by a token. Fitting the view is deliberately *not*
reactive — it happens on a track load, a chip click and the first map to appear,
because an unrelated agent logging out can flip which map is busiest and yanking
a panned view for that would be hostile. Deferred as item 60: the 4096 stroked
grid cells when zoomed out, and route decimation for tracks long enough to feel.

The regression test is a live reactive graph, which needed one piece of plumbing
worth knowing about: `bun test` resolves `solid-js` under the node condition,
which is the server build whose signals never notify. A graph test against it
passes no matter what the graph does. `test/mapview.test.ts` redirects the name
to the browser build before loading the derivation, then counts how many times a
downstream computation runs across five feed updates carrying fresh identities.
Six. Under the old shape it did not terminate.

## Map navigation: two URL states, and going back the other way

The map had a working way in and a half-working way out. `/map?run=<id>` loaded a
replay, but the only way back to live was a text link trailing the timestamp at
the end of the scrubber, and the state it left behind was whatever the replay had
accumulated. The clearing that did exist happened inside the track fetch's
response, which is the wrong moment twice over: nothing was cleaned up at all on
the way back to live, and swapping one replay for another kept the first run's
pips on screen under the second run's identity until the second track landed.

So the swap has one owner now. The effect that reads the search parameter clears
unconditionally and *before* it fetches, which makes every route into the two
states the same code path — the new control, browser back and forward, a deep
link opened cold, one replay straight to another. The clear itself is
`clearReplayState`, a pure writer taking setters as arguments, which is what lets
it be tested against a real reactive graph instead of by looking at a canvas.

One line of it looks like dead weight and is the interesting part. `activeMap` is
the reducer memo from yesterday's refactor, and its stickiness lives inside the
memo rather than in any source signal, so clearing the four sources does not by
itself forget which continent the replay ended on. Pushing an empty feed through
once does: the memo recomputes over an empty map list, finds its own previous
answer no longer present and returns null. Without it, returning to live from a
replay of Outland sits on Outland because one straggler happens to be standing
there, while the crowd is on Azeroth. Three of the new tests fail if the line goes
away, which is the only durable way to say "load-bearing" about a line that reads
as redundant.

Returning to live stayed a link rather than becoming a button with a handler.
Since the route change is what performs the swap, the control needs no logic, and
an anchor keeps what an anchor gives: a real history entry, middle-click, the
focus ring. It sits with play; the trailing link is gone, because two affordances
for the same thing where one cleaned up less is how the stale state got there.

The other direction turned out to exist already — and to be invisible. `replay on
map` was wedged into the `comparability` section heading on the run page, which
is why it read as missing: nobody looks for navigation inside a heading about
budget tuples. It moved to the sidebar's controls row, which now renders whether
or not the run is live, so the loop closes at both ends against the map's
`open run →`.

Nothing fast-changing went into the URL. Cursor, playback, pinned map, selection,
pan and zoom stay in memory — a cursor in the query string would rewrite history
four times a second under the play slider. The price is that coming back to a
replay restarts it at the first sample, which is item 61 rather than a silent
regression.

Verified without clicking anything: the reset tests drive the real graph into
mid-replay, read `activeMap` so the reducer caches its answer, clear, and assert
the derived state is back to the live baseline and that a following live feed
picks its own busiest map; `runParam` pins the URL-to-mode mapping including the
empty and repeated forms. Back/forward and deep links are the same effect as the
button by construction, not by observation. 1324 tests pass, dashboard build
clean.

## Episode progress in the fleet table's state cell

The state column now carries a percentage beside its badge, and the cell's title
reads `ETA: <time> — <elapsed> of <budget>`. One number an operator will believe,
which is the whole reason the interesting part of this was deciding where it is
allowed to appear.

The denominator is the run's own recorded `comparability.budget.episodeMs` and
nothing else. A tier's nominal 90 or 360 minutes is a claim about the tier, and
`nav-probe` is the standing proof that a roster entry overrides it; deriving a
budget from an episode id would have produced a confident wrong number on exactly
the row most worth watching. A run with no recorded budget shows nothing. That
also meant no viewer API change: the runs feed already carries the tuple.

The numerator is `playtimeMs`, and it is the right clock now — but it was not
always. `tail.ts` still says the `episode-limit` watchdog resets on every resume
and never sees paused time, which was true when it was written (6f44a06,
2026-08-22) and stopped being true a day later, when 08cd691 made run.ts carry
`elapsedBeforeMs` from the persisted `episodeElapsedMs`. Both clocks now exclude
paused stretches; they are accumulated differently — trajectory segments against
process uptime — so they agree to within a segment boundary and the comment on
`rowProgress` says so rather than implying millisecond agreement. The stale
comment is item 62, not an edit: a live run was going through the viewer.

Only `running` and `draining` show progress. Everything else is a row whose
episode clock is not moving, and a countdown that ticks while nothing runs is a
lie: `paused` and `paused-deploy` hold a run that gave its session back,
`resuming` has not picked one up yet, `idle` holds nothing, `exited` is over. The
`resuming` gate is on the state and not on a missing run id, because a resuming
row *has* one (`runId ?? job.resuming`) and today shows nothing only by accident
of where the run lookup keys — there is a test that fails if that accident is
refactored away.

Freeplay shows nothing, against the evidence that it could. `nav-probe` records a
real six-hour watchdog and would light up honestly, but the id is uncapped and
"72% of freeplay" reads as a tier fact it is not. The gate is one predicate and
item 63 says where to delete it if the operator wants that number after all.

Over budget prints the real figure. `fleet-deepseek-flash-e90-…-a3` ran 114
minutes against 90 and ended on `episode-limit`; 127% is the signal, and clamping
to 100% would hide it. Past due, the title stops counting down and says how far
past it is, so no negative duration can reach `fmtDuration`.

No new timer. Both numbers come off the existing 10s poll of `/api/runs`, which
charges a live run's playtime up to request time — and because numerator and
denominator ride the same snapshot they cannot tear.

The one caveat is written into the comment rather than left implied: a run
resumed from a pause mark written before `episodeElapsedMs` existed restarts the
watchdog at zero while playtime keeps its earlier segments, so the percentage
over-reads on exactly those runs. It errs toward "further along", never toward
hiding an overrun.

Verified without clicking: eight new tests in the pure layer assert the shipped
strings, not just the maths — normal, draining, freeplay, over-budget, paused,
resuming, idle-and-exited, and no recorded budget — which is where the row maths
belongs (dashboard/README.md). `bun test dashboard/test/fleet.test.ts` is 30 pass,
0 fail; the full suite ran green (1337) alongside another session's unstaged map
work in the shared worktree, so that total is not a clean measure of this change.
The component was read against the tests and the built bundle checked for the
shipped title strings and the `.progress` rule; the title's elapsed figure is the
same `fmtDuration(elapsedMs)` the elapsed column prints, so the two cannot
disagree on screen. Dashboard build clean.
