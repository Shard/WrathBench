# 2026-08-24

## Run view redesign: two-column layout, fixed autoscroll, prominent XP/level chart

The run detail page (`dashboard/src/pages/RunDetail.tsx`) was one long scroll —
meta cards on top, feed below, a tiny XP sparkline buried among the cards, and an
autoscroll that called `window.scrollTo` and did nothing useful. Reworked into a
two-column inspection view.

**Layout.** The page is a flex column: a `fleet / <id>` heading, a full-width XP
chart, then a `.runview-cols` row. Left (`--log-col`, default 70%) is the feed,
its own scroll container. Right (~30%) is everything else — the autoscroll toggle
and live-activity line, all the meta cards (model, character + inventory, tokens,
playtime, cost ×2, level trace), the comparability tuple, termination/pause
banners, and the server footer. Both columns scroll independently, so the run's
meta and the toggle stay in view while the feed scrolls; no sticky needed. Under
900px they stack, sidebar first, feed kept a scroll container (`max-height: 70vh`)
so the autoscroll path is identical in both modes. `.runview-cols` has a 320px
floor so a short viewport lets `main` scroll rather than crushing the feed.

**Autoscroll.** The log column is the scroll container. A new entry pins it to the
bottom (`scrollTop = scrollHeight`) *from an effect on `entries`*, not from the SSE
callback — reading `scrollHeight` before Solid commits the new nodes lands
mid-list and silently flips follow off (the old bug in a new costume). Scrolling up
past 32px turns follow off; scrolling back within it turns it on (`atBottom`,
pure). The manual toggle in the sidebar overrides and is persisted in localStorage
(try/catch guarded); a scroll-driven off is session-only and never saved.

**XP/level chart.** Full-width inline SVG above both columns (`components/XpChart.tsx`).
X = time from run start to `min(now|endedAt, start+episodeMs)` with ~5 elapsed-time
ticks (mm:ss / Hh Mm). Y = cumulative XP, with a dashed gridline + `L<n>` label at
the XP offset each level began. Cumulative XP is a *lower bound* reconstructed in
`lib/runview.ts`: `StatePoint.xp` is within-level and resets, so the total carried
into a level is the sum of each lower level's last observed within-level xp — it
under-counts by whatever was earned between a level's final sample and the ding, a
gap bounded by the sampling interval and never invented upward. Level and xp are
read off the *same* sample (the old sparkline filtered the two into separate lists,
which mis-pairs them), samples sorted by ts, curve clamped monotonic. Comment notes
this is the simple version and uPlot is the long-term plan for denser series; no dep
added. The small level sparkline stays in the sidebar; the XP sparkline is dropped.

**Inventory.** The `carrying:` / `equipped:` lines (item 50, shipped db43c3c) moved
into the sidebar character card with the rest of the meta — not duplicated. `—` for
a run that predates the `items` column, `none` for a recorded-empty side.

Tests: new `dashboard/test/runview.test.ts` pins the band derivation (offsets, same-
sample pairing, monotonic clamp, unordered sort, level-jump, x-window with episodeMs
capped at now / endedAt) and `atBottom`. `bun test` 111 pass, `bun run build` clean.

Verified against the live freeplay run `fleet-nav-probe-freeplay-sonnet-...-c2`
(L5, 6254 entries, 187 state samples, 6h episode): served bundle
`index-B1mKDya-.js` → `RunDetail-BdSHtGji.js` is the new one; the derivation
yields bands L1–L5 at cumulative offsets 0 / 200 / 1028 / 2356 / 4444. Inventory
shows `—` (this run predates the column).

## Fleet: concurrency cap keys on a rate-limit key (free pools capped per platform)

`policy.maxConcurrent` keyed on the driver, so every free OpenRouter + OpenCode +
local model shared the `openai` driver and could not be capped apart. OpenRouter
enforces a daily cap on `:free` models; running several free OpenRouter runs in
parallel burned the budget and produced broken runs. The cap now keys on a
rate-limit KEY (`concurrencyKeyOf`, `runner/src/models.ts`): a free model on a
shared free platform counts under `openrouter` / `opencode`; everything else keeps
its driver key. `fleet.json` now ships `maxConcurrent { claude-code: 2,
openrouter: 1, opencode: 1 }`.

Roster → key mapping (stated for the record):
- `nav-probe`, `sub-opus`, `sub-opus-low`, `sonnet`, `sonnet-low` (claude-code) → `claude-code`
- `ox-alpha`, `nemotron-ultra`, `nemotron-super`, `nemotron-nano`, `north-mini-code`, `laguna-or` (free, OpenRouter/no-apiBase) → `openrouter`
- `muse-spark`, `hy3`, `laguna-oc`, `x-preview-f` (free, opencode.ai) → `opencode` (host normalized in the key fn only)
- `deepseek-flash` (paid, projects to openrouter) → `openai` — NOT a free key; governed by `policy.paid.maxConcurrent: 1`
- `qwen3-8-27b` (local, LAN) → `openai` — NOT capped by the free keys; its one local account is its limit

The free branch gates on `driver === "openai"` and reads the platform from
`platformOfBase(apiBase) ?? "openrouter"` (never the driver), so a `:free` slug
pinned to `driver: "openai"` with no base still lands in `openrouter`. `platform.ts`
is untouched — `run.platform` keeps the `opencode.ai` host spelling; the key fn is
the one seam that normalizes it to `opencode`. Named "key" not "lane" because
`lane` is retired (ADR-0034); ADR amendment records the concept.

Naming swept everywhere: `concurrencyKeyOf` / `CONCURRENCY_KEYS` / `isConcurrencyKey`
(models.ts), `concurrencyKeyOfRef` + the `{ keyOf, max, running }` concurrency
field + `keyCount`/`countKey` locals (run-fleet.ts), the two `--status`/`--dry-run`
print lines, the held reason (`cap: <key> <= n`), the fleet.json `_notes`, and the
viewer doc comments. `parsePolicyBlock` validation accepts the new keys and rejects
unknowns listing the allowed set.

Tests: extended `runner/test/models.test.ts` (key derivation per roster class,
validation accept/reject) and `infra/fleet.test.ts` (openrouter free key caps at
one while a paid openrouter model runs beside it; shipped-fleet.json assertion).
`bun test` in runner/ = 530 pass / 0 fail; typecheck clean. `bun test infra/` =
155 pass / 1 fail — the one failure (`fleet.json` nav-probe `repeat: 1` vs the test's
expected `"loop"`) is pre-existing at HEAD and untouched by this change.

Deploy: the running supervisor validates config with BOOTED code, so it keeps the
old per-driver cap (and shows a REJECTED banner on the new `openrouter` key) until
`docker compose -f infra/compose.yml up -d fleet` recreates it. Benign — no runs
break, runs resume on recreate.

## The wiki bundle's identity is in the run's tuple

The run config recorded the bundle's path and nothing about the file behind it,
so the era-cutoff rebuild (FOLLOW-UPS 49) would have been invisible: same path,
different prose, indistinguishable runs. `openWikiBundle`'s module now also
reads the bundle's `meta` table — `schema_version`, `built_at`, `source`, and
the era cutoff the upcoming build will write as `era_cutoff` — and `run.ts`
stamps it into the comparability tuple as `wikiBundle`.

It is an annotation, not a new grouping key. The harness series is already what
groups behaviour changes, so the rule is that a rebuild changing page text
ships with a harness minor bump, and the annotation is the evidence of what the
bump was about; the reasoning is an addendum on ADR-0033. Everything is
nullable and optional: an old bundle with no `era_cutoff`, an empty `meta`, or
no `meta` at all annotates as nulls and never fails a launch. The one gate that
fails closed stays `openWikiBundle`'s schema check.

This record does not close item 49 on its own; the era bundle below does, and
this is what makes the rebuild visible when it is deployed.

## A `<page>` block is not a page

A full-dump census for the era-cutoff work turned up a bug under it: the history
dump emits one `<page>` element per 50 revisions, so a page with 627 revisions
arrives as 13 consecutive blocks, newest-first. `parse.ts` finished a page on
`</page>`, which made every block a row — 114,501 `pages` rows for 104,808
distinct (title, ns). The 9,693 extra rows held 2005-2009 text and competed
with the same page's current text in `pages_fts`; `resolveTitle` picked between
them by rowid luck.

The parser now holds a page open and finishes it when the (title, ns) key
changes or the stream ends, adopting the pending accumulator when the next block
continues the same page. Blocks for a title are contiguous in the dump (the
census found zero exceptions), and `beats` already selects on (timestamp, rev
id), so peak memory is still one revision body whatever the history depth.

Two guards, because luck is not a design: `resolveTitle` orders explicitly
(ascending id — the dump is newest-first, so the block holding the newest
revision was written first), and the build calls `assertUniquePages` before it
indexes, recording `pages_distinct_keys` in `meta` and throwing otherwise, with
a UNIQUE index behind it. The check sits inside the try that unlinks the temp
file, so a failure leaves the deployed bundle untouched.

The deployed bundle keeps its 9,693 stale rows until it is rebuilt.

## The bundle reads the era it plays: prose from 2010, structure from 2020

Item 49's real fix, and the one the day's other wiki commits were clearing the
way for. A page row is now built from **two** revisions of itself: the prose is
the newest revision saved before 2010-10-12 (patch 4.0.1, the Cataclysm
pre-patch), while everything structured — coordinates, entity ids, the quest
infobox — still comes off the newest revision, where a decade of corrections
lives and where 30% of the coordinates only exist. ADR-0040 has the reasoning;
the short version is that prose ages badly and a `{{coords}}` template does not.

Two hygiene rules decide the era revision, because "newest before the cutoff" is
not the same as "what the page said": a revision where the page was a
`#REDIRECT` is not prose, and a revision that was immediately reverted (the next
revision restored a sha1 the page already had) is not what the page said either.
A page with no pre-cutoff revision at all — 20,428 of them, 18.6%, the wiki grew
after 2010 — keeps its newest text and carries a fixed page-level label saying
so. Nothing is dropped for being late. `meta` records both paths
(`pages_era_swapped`, `pages_era_fallback`), so the split is auditable per build.

Verified on a full rebuild: pages that mention Cataclysm with no label at all
2,025 → 650; Deathwing / the Shattering / Pandaria 2,032 → 306; the Coldridge
Valley "prior to its collapse" prose that triggered the item, 3 hits → 0.
Coordinates are down 2.6% and ids 1% — not the era swap, which does not touch
them, but the duplicate rows the block merge removed.

The residue is real and now its own item (FOLLOW-UPS 62): the ~650 left are
mostly 2009–10 prose about the expansion that had been *announced*, which no
revision line can reach, plus the labelled fallback pages.

**The deploy has not happened.** The rebuilt bundle sits at
`data/wiki/bundle.next.sqlite`; swapping it changes what every model reads, so
per the ADR-0033 addendum it ships as a harness minor bump in a deploy window
after review, not as a quiet `mv`.

## Out-of-game reference pages rank last and say so

The other half of the reference budget. Trajectory mining over 462
`search_reference` calls found a `Hotfixes` archive served fifteen times and a
pop-culture-reference list thirty-eight, to a character standing in a zone: the
wiki documents the patch history, the Lua addon API, the client UI and the boxed
products, and the full-text index cannot tell those from the world.

`classifyMetaPage` (`wiki/src/meta-pages.ts`) classifies from the **title**
alone — the wiki namespaces this material by prefix (`API GetSpellInfo`, `MACRO
cast`, `Hotfixes/…`) or disambiguates it with `(AddOn)` — and `searchReference`
bands such a hit below every body hit and prefixes its snippet with
`META_PAGE_LABEL`. Nothing is deleted, and an exact-title hit is never demoted:
asking for the page by name is a deliberate request, not a stray match.

The rules are deliberately conservative, since a missed hotfix archive costs one
slot and a demoted quest page costs the run. `Widget*` was dropped because
`Widget the Departed` is an NPC, `Patch *` because `Patch of Bat Hair` is an
item, and `* (old)` because those are mostly superseded spell and quest versions
— an era problem, which `markEraSections` owns, not an out-of-game one. 2,570 of
104,808 titles classify: 2.45%. Since 65% of them are API/UI/macro documentation
the label now names that band outright: `[out-of-game reference page: patch
notes, UI/API docs, addon or real-world topic]`.

## Direction change: the bundle is a Wrath snapshot, not a labelled dump

The operator's call, mid-item: nothing is labelled by era any more, because
content that is not 3.3.5 is not in the bundle. ADR-0029's "mark, never delete"
was never an operator decision — the implementing agent made it on 2026-08-23
and it went in as if it were policy — and the standing position is the opposite:
the dump is a known rough source, the bundle is a product filtered and stripped
as the evidence warrants, and removal is reversible by rebuilding. ADR-0029 now
carries a dated retraction of that rule; ADR-0040 was rewritten around the
principle.

What that made possible: the revision cutoff can now decide the whole page, not
just its prose. A page with no revision before 2010-10-12 is not emitted
(`pages_dropped_post_cutoff`), and redirect-ness is decided from the Wrath
snapshot too — a page that was a redirect then is one here, a page that was an
article then is an article here even if it was merged away in 2014 (144 pages
flip), and a redirect whose chain does not end at a surviving page goes with its
target.

Three levels below that, each counted in `meta`. **Page:** `admitPage`
(`wiki/src/post-wrath.ts`) is one pure function with five reasons —
`pre_cutoff`, `post_cutoff_wrath_signal`, `dropped_post_cutoff`,
`dropped_post_wrath`, `dropped_meta` — and the build test asserts those five plus
`empty_pages` account for every non-redirect page the parser yields, which is the
only thing that would catch a page counted twice or lost quietly. **Section:** a
`{{cata-section}}` or `== In Cataclysm ==` section is dropped, heading and all.
**Paragraph:** narrow phrase rules over the prose of a blank-line block, with the
templates removed first so an infobox field never decides.

The rules are narrow where the words collide, and the census is the evidence: of
the category names on late pages, `Burning Legion` appears 39 times against
`Legion`'s 29, so "category contains Legion" would have deleted the Burning
Legion from a bundle whose world contains it. The category rule fires only on a
category that *is* `Legion` or starts with `Legion `. `{{Removedwithlegion}}` and
`{{Removedwithcataclysm}}` are not signals at all — content removed later exists
here — and `{{legion-inline}}` (278 uses) marks a clause, not a page. Draenor is
Outland's own name, so only `Warlords of Draenor` counts. Deathwing, Garrosh and
the 7th Legion are all in this world and none of them is a rule.

The amendment that arrived with the direction change: a page created after the
cutoff that is right about Wrath should ideally be admitted.
`post_cutoff_wrath_signal` does it where the evidence is explicit — an infobox
`|patch=` below 4.0, an `|expansion=` naming Wrath or earlier, one of four
category names, with a Classic-2019 veto because WoW Classic's 1.13/1.14 patches
read as vanilla to every one of those rules. That reaches 15 of 20,407 late
pages. The rule that would reach the other 18,717 is a server-side id
cross-check, and it is deliberately not implemented: the wiki tooling reads
nothing from the server by design, so that is an operator decision (FOLLOW-UPS
62, ADR-0040).

Out-of-game pages moved with the same principle: `classifyMetaPage` runs at
build time and the build does not emit what it classifies. The search band,
`META_PAGE_LABEL` and the `metaPage` result field are gone, and with them the
carve-out that kept an exact-title hit at the top — the page is not there to
return. `search_reference`'s description loses the clause about labelled
paragraphs, since there are none, and keeps one fixed sentence: the bundle is a
Wrath-era snapshot of the wiki and describes this world, prefer what you can
observe in game.

`schema_version` stays 5 — no table changed — so a deployed bundle keeps
answering until it is rebuilt. The `pages_dropped_*` counters are what tells a
version-5 bundle built before this from one built after. The deploy is still
pending: swapping the bundle changes what every model reads, so per the ADR-0033
addendum it ships as a harness minor bump in a deploy window.

## The bundle keeps only what a character can act on

The era rules ask which world a page is about. A heading census over the
Wrath-snapshot revisions says that question was the smaller half of the problem:
`External links` sits on 66,140 pages and is 14.1% of raw bytes on its own, the
patch record another 1.4%, lore and story about 1.3%, and the commentary and
media set — trivia, quotes, speculation, galleries, videos, the other Warcraft
products — about 1.8%. None of that names a coordinate, an id, a giver or a
reward. The unambiguous candidates come to 16.3% of corpus bytes, all of it
reading cost inside a snippet window.

So a fixed heading drop set now runs at build time, on the raw wikitext, in the
same section walker the era cut already uses — heading line through the next
heading of the same or a shallower level, and nothing is rewritten. The era
check runs first, so a heading can never be counted under both. The match is on
the normalised heading (trimmed, case-folded, markup and trailing punctuation
gone) and it is exact, never a prefix or a substring: that is the whole reason
`changes` goes while `past changes` stays and `notes and trivia` goes while
`notes` stays. There is no keep list in the code — only the drop set exists, and
what was considered and deliberately kept (`notes`, `tips`, `tactics`,
`strategy`, `abilities`, `drops`, `source`, `objectives`, `description`,
`progress`, `completion`, `rewards`, `gains`, `quests`, `location`) is written
down in `wiki/README.md` instead.

A third pass runs last, after the paragraph rules, because those rules are
themselves a source of orphan headings: a section whose subtree carries no prose
after everything is stripped is not emitted at all. The test is on the subtree
rather than the direct body, so a heading with no text of its own but an
occupied subsection survives while an empty subsection of an occupied section
still goes.

`sections_trimmed` is the total and `sections_trimmed_json` the per-heading
breakdown, keys sorted so two builds from the same dump write the same string,
with empty-section removals under `(empty)`. The era counters stay separate — a
regression in one should not be able to hide in the other. The one wording debt:
a page that was nothing but a link list now empties and lands under
`pages_dropped_post_wrath`, which is the wrong name for the right outcome, and
the five-reasons-plus-`empty_pages` identity the build test asserts is not worth
widening for it.

Follow-on to item 49; the deploy is still pending with the rest of the era work,
since this changes what every lane can read. The staged bundle at
`data/wiki/bundle.next.sqlite` was built before this and has to be rebuilt
before the swap — deployed as it stands it would ship the era rules with no
section trim and no `sections_trimmed` in `meta` at all.

## Pages that predate the Cataclysm beta are Wrath pages, and a canary guards the capitals

`admitPage` was dropping 6,935 pages as post-Wrath. An attribution pass over the
dump splits them: 4,859 are the mid-2010 bot import of beta-datamined Cataclysm
items and quests, with no revision at all before the beta — correct drops, and
the reason the rule exists. 1,429 have no pre-cutoff revision, so the post-Wrath
label was answering a question nobody asked. And **588 are pages of this world**
— Stormwind City, Undercity, Durotar, the Barrens, Thousand Needles, Auberdine,
Southshore, Camp Taurajo, Azshara, Darkshore, Desolace, Stonetalon Mountains,
Stranglethorn Vale, the Wetlands, Westfall — that picked up `|patch=4.0.1` or a
Cataclysm category in a 2010 revision, written by editors reading the beta notes
about zones that were about to change. Reading the signal on the era revision
rather than the newest was supposed to prevent exactly this. It does not, because
some of those annotations arrived before the cutoff.

The wikitext cannot tell the two apart: both say Cataclysm, in the same fields,
in the same words. The page's age can. A page that existed before the beta
documented this world first; a page created during the beta was written about
the world that was coming. So the parser now tracks each page's oldest revision
timestamp and `admitPage` protects any page created before `CATACLYSM_BETA_START`
(2010-06-01) from the post-Wrath signals. The section and paragraph rules still
run — the Cataclysm paragraph that arrived with the category still goes, the page
stays. `pages_pre_beta_protected` counts the kept ones; it is a subset of
`pages_pre_cutoff`, not a sixth bucket, and stays out of the accounting identity
the build test asserts.

The counter fix goes with it: a page with no pre-cutoff prose is
`dropped_post_cutoff` whatever else it says. The admitted set does not move — the
post-Wrath signal still vetoes the explicit-Wrath-signal admission — only the
reason. Verified over the whole dump: the five reasons plus `empty_pages` sum to
112,121 before and after, with `dropped_post_cutoff` up by exactly 1,429.

**The lesson is not the rule, it is that nothing caught this.** Every counter in
that build added up. Six thousand drops, five reasons, an accounting identity a
test asserts — and no capital city in the bundle. A rule one word too broad is
invisible to counters and obvious to a list of names. So the build now ends with
a canary (`wiki/src/canary.ts`): 41 titles — the ten capitals, the eight racial
starting zones, the classic and Wrath zones an over-broad rule reaches first —
which must resolve in the finished bundle, through redirects, **before** the temp
file is renamed into place. A miss fails the build, names every missing title,
and leaves the deployed bundle where it is. `--max-pages` smoke builds skip it
(`--no-canary`, on by default for them). `wiki/src/verify.ts` is the operator-run
pre-swap gate on an already-written bundle: the same titles, plus
Cataclysm-or-later titles that must **not** be there, plus 18 forbidden and 10
required phrase pairs. Both lists were checked against the dump rather than
recalled — a name that also existed pre-2010 as lore (Mount Hyjal, Tol Barad,
Grim Batol, Kul Tiras, Zandalar, Worgen, Goblin) is not a forbidden title, and a
phrase pair the wiki's own 2010 editors had already broken is not a pair. A gate
that cries wolf is a gate that gets skipped.

Checked against the dump, not just the tests: of the 41 canary titles, 16 are
missing from the staged `bundle.next.sqlite` and 15 of those come back under the
new rule. The sixteenth is **Orgrimmar**, and the canary is right to fail on it:
its 2010 revision — 14,412 characters of real article — strips to the empty
string before any era rule runs, so the page has been dropped as empty by every
build since the era work and counted under `empty_pages`. That is a `strip.ts`
defect (`removeBraced` never returns to depth 0 on a multi-line `{{infobox
zone}}` with nested `{{Race|…}}` arguments), not an era one: FOLLOW-UPS 63. The
next full build will fail the canary on it, which is the gate doing its job.

Residue, measured rather than assumed: 119 of the 588 protected pages were
created in 2009 or later, clustered on 2009-08-21/22/23 — BlizzCon, where
Cataclysm was announced — and 2010-04, and most of those are Cataclysm content
that the June line now admits. Moving the line to the announcement date would
keep about 500 and drop about 88 of them. Not done here: 2010-06-01 is where the
588 was measured. FOLLOW-UPS 64.

## The stripper survives a nested infobox, and protection starts at the announcement

Two residue items from 49, and the first one was not where the note said it was.

**Item 63.** The Orgrimmar canary failure was blamed on `removeBraced` never
returning to depth 0 on a multi-line infobox with nested template arguments. It
does not, but that is the symptom. An instrumented scan of the page's own 2010
revision — a stack of openers, printing what is still unclosed at end of input —
named the `{{infobox zone}}` opener and nothing else, on a page whose braces
balance. What unbalances them is upstream of the brace scanner: `CONTAINER_TAGS`
matches `<(ref|gallery|…)\b[^>]*>`, and `[^>]*` happily swallows the slash of a
repeated citation written `<ref name="Errata" />`. The regex reads that
self-closing tag as an *opening* one and deletes everything to the next
`</ref>`: 1,486 characters on that page, including the `}}` that closed the
infobox. After that the scanner is counting a document that really is
unbalanced, and it discarded the whole page. A `(?<!/)` before the closing angle
bracket is the fix; `SELF_CLOSING` already handles the tag itself.

The scanner is hardened as well, because the same page class has two more ways
to lose. Braces are now consumed a **run** at a time, `floor(run / 2)` on each
side: reading two characters at a time made the third brace of `{{{param|x}}}`
open a `{|` table that nothing ever closes, and the mirror case over-closed and
leaked a template's own fields out as prose (a synthetic achievement box in the
test file pins both directions). And a closer now matches its opener's kind, so
a `{|` written inside a template argument cannot eat the template's `}}`.
Finally, unbalanced input costs a paragraph rather than a page: an opener still
unclosed at end of input keeps the prose before it as before, and the strip
resumes at the first blank line after it, on the assumption that a malformed
template does not cross a paragraph boundary. Only when there is no blank line
after it does the tail go with it.

Measured over the dump, read-only, on the same definition before and after —
non-redirect pages whose newest pre-2010-10-12 revision strips to the empty
string while its raw text holds at least 200 characters of non-template prose:
**47 → 11**. Attribution, measured by stubbing each piece out rather than
asserted, because a fallback that carries the recovery would mean the defect was
never found: the ref fix alone recovers **22** of the 47, the run-and-kind
scanner with the paragraph fallback stubbed out takes it to **28**, and the

## A page the section trim empties keeps its row

A full rebuild said `dropped: 22890 post-cutoff, 10027 post-Wrath`, and the
post-Wrath number should have been about five thousand: 6,935 pages carry a
post-Wrath signal on their era revision, 1,429 of them have no pre-cutoff prose
and are counted post-cutoff instead, and 489 are protected. The other five
thousand were pages the **section trim** emptied. `build.ts` had one branch for
a page that came out with no prose — had it prose before? then a cut took it,
call it post-Wrath — and that branch could not tell the two cuts apart.

Trimming an external-links section is not evidence that a page is from a later
world. It is evidence that the page's body was a link list, which is true of
28,471 sections the same build reported under `(empty)`. And dropping the row
threw away more than prose: the title, the `page_ids`, the `page_coords` and the
`page_quest` rows went with it, which is why id rows had fallen 71,231 → 64,284
between the pre-era bundle and this one. An NPC page whose body was an infobox
is still that NPC, and an exact-title or id query is exactly the query it
answers. Three of the first empty rows in the fixed build are `"Charlie"
Northtop`, `"Mad" Jonah Sterling` and `1000 Daily Quests Complete`.

So the discriminator is the **trim-only** text, not the era-only text: run the
same section walker with the era half switched off (`dropOutOfWorldOnly`, one
walker, an `eraCuts: false` option) and ask whether anything would have
survived. Something survives → the era cuts are what emptied the page and it is
dropped as post-Wrath; nothing survives → the page was a link farm or an
infobox, and it stays as an empty row. Era-only text was the first attempt and
is wrong: a Cataclysm page that also has an external-links section still has
prose in its era-only text, so it would have been kept. The trim-only text is
computed on demand, only for a page that came out empty, because the
empty-section sweep strips every section body to decide; the full build cost 3
seconds of 56.

Empty rows are rows, not FTS documents. A page with no body is the shortest
document in the index, and letting bm25 rank its title against pages that have
something to say would trade a real regression for the recovered ids. It is
found by exact title and by id, which is what it is there for.

Measured on a full rebuild to a scratch path (not `data/`), against the same
dump: post-Wrath drops 10,027 → **5,016** (the arithmetic above predicts 5,017),
empty rows 1,899 → **6,910** of which 5,011 were emptied by the trim, id rows
64,284 → **71,751** — above the pre-era bundle's 71,231, because the 1,899 pages
that never had prose were not rows in that build either. Coords 7,433 → 7,631,
quest rows 7,889 → 7,907, pages kept 74,393 → 81,303, and 174 redirects that
used to dangle now land on a target that exists. The accounting identity holds:
the five reasons plus `empty_pages` sum to 112,121, and the canary passes.

Eleven of the moved pages were pulled off the dump and walked through the
pipeline step by step to check the emptiness is real. It is, and no era cut
fired on any of them: four are an infobox plus a link list (14 to 55 characters
of prose in the whole page, all of it the link labels), one is an item page whose
`Random enchantments` and `Source` sections are tables that the empty-section
sweep takes, and three are NPC pages with 634 to 871 characters that live
entirely under `== Quotes ==` — the drop set doing exactly what ADR-0040 says it
does. Braces balance on all eleven and every lead strips to nothing on its own
merits, so the stripper's unclosed-opener fallback is not involved. Two of the
three `(Warcraft III)` pages sampled are not empty at all and are indexed
normally. The quote-only NPC pages are the one judgement call in there: if a
trajectory wants an NPC's lines back, that is an edit to `OUT_OF_WORLD_SECTION`,
not to this branch — and those pages now keep their title and their npc id
either way, which is the point.

The staged `data/wiki/bundle.next.sqlite` predates this fix as well as the

dropped 5,011 pages of this world, and must be rebuilt before any swap.

**Item 49 residue: names survive Cataclysm page moves.** A MediaWiki move
carries a page's history to the destination, which is a fact about the *dump*
that no era rule can see. When Cataclysm rebuilt the low-level dungeons the wiki
moved this world's article aside and wrote the new one under the bare title, so
`Deadmines` is a 2010-09 page whose first revision is a redirect to
`Deadmines (original)` and whose later pre-cutoff revisions are the Cataclysm
article. Dropped, correctly — and then the name a character would search for is

via a sibling that is itself only a redirect.

Two rules, both candidate generation into the one pending list the existing
six-hop walk already resolves. The newest revision is read when the Wrath
snapshot does not answer — a snapshot redirect whose target dangles retries the
newest one, and a refused page whose newest revision is a `#REDIRECT` becomes a
name (183 + 1,277 measured over the dump). And a bare title with no page and no
redirect whose `(original)`/`(old)` sibling is in the bundle redirects to it (68,
Deadmines, Ragefire Chasm and Scarlet Monastery among them). Whichever target
actually resolves is the one written, because the row is walked again at query

demoted, and `verify.ts` resolves `Patch 4.0.1` through the redirect table to
check exactly that. Recovering a name never puts a page back, which is where the
accounting identity had to move: a redirect row can now be generated for a title
that is also a counted page, so the five reasons plus `empty_pages` are counted
against `pages_in_namespaces - pages_era_redirect` rather than against the rows
written. Stepping back through a page's revisions to find the pre-move article
was considered and rejected — a move takes those revisions *with* it, what
survives under the bare title is superseded text, and the yield is about 3% of
what these two rules reach.

regression here: the pages stay in the bundle either way, under names nobody
types.

## An empty reference page answers with what it states, or not at all

Keeping infobox-only pages as rows (9f06265) left roughly 6,900 pages with empty
`text`. An exact-title query for one of them returned it at `EXACT_TITLE_RANK`
with a blank snippet, ahead of a page with prose on the same topic: the model
read silence at rank 1 and had no way to tell "the wiki is quiet about this"
from "there is nothing here". `searchReference` now returns such a page from the
title and id bands only when it carries something structured — a `page_quest`
row, `page_ids` rows, or coordinates when coordinates are being served — and its
snippet is a fixed literal saying the page has no article text, with the quest
line following it, so the giver, ender and id the page does state still reach the
model. An empty page with nothing structured is skipped outright and the query
falls through to the other bands. The emptiness test is `text.length === 0`, the
same predicate `makeWriter` uses when it decides not to index the page, so the
two cannot drift and a whitespace-only page cannot be skipped by one and served
blank by the other.

## A redirect that dangles does not answer for its title

The canary caught a real one: 53 of 54, missing `Scarlet Monastery`. The page is
correctly absent — its first revision is 2012 — and this world's article is in
the bundle under `Scarlet Monastery (original)`, exactly the shape the sibling
rule exists for. It did not fire.

The cause was one line in the order of the two rules. `siblingRedirects` is told
which titles already answer so it leaves them alone, and the build was passing it
every kept page *plus every pending redirect source*. A source is not an answer:
the candidate still has to walk to a page, and the one that shadowed this title
never did. A lower-cased spelling of the title, `Scarlet monastery`, redirected
to the bare title; the bare title had no page; the row was dropped as dangling
and never written — but its source had already put `scarlet monastery` into the
answered set, so the sibling rule skipped the key and the article sat under a
title nobody types. The alternate spelling and `The Scarlet Monastery` were dead
rows for the same reason, and the case-variant candidate was in fact a self-loop:
source and target share a lower-cased key, so the walk burned its six hops.

So the resolution runs in two passes now. Every candidate the stream produced is
walked first; one that leads nowhere is held back rather than dropped. The
sibling rule then runs over the titles that are still unanswered — a kept page,
or a redirect that actually landed — and its candidates go into the same target
map, overwriting the dead entry for that key. That overwrite is the load-bearing
part and is commented as such: it is what lets the held-back rows land on the
retry, which is how `Scarlet monastery` and `Scarlet Cathedral` come back with
the name they were pointing at. A sibling is now only ever made from a page or
from a redirect that landed, so it can no longer point into a dead row.

Measured on a full rebuild, canary on: redirects 13,368 → 13,413, dangling
3,206 → 3,173, `(original)` siblings 63 → 75. The twelve new siblings are all
this world's — `Scarlet Monastery`, `Molten Core`, `Zul'Gurub`, `Zul'Aman`,
`Ignite`, `Seal of Justice` and six more — and the other 33 rows are the ones
that were pointing at those bare titles all along. `verify.ts` is green on that
bundle: 54 required pages, 19 forbidden titles, 28 phrase checks. The
`Ruins of Gilneas` → `Gilneas` worry from FOLLOW-UPS 62 does not materialise —
there is no `Ruins of Gilneas (original)` for the rule to reach, and the bare
title has no candidate of any kind — so no title veto was added and the ns-0
lore pages stay as they are.

## The build may ask the world DB whether an id exists

Mark approved the open decision ADR-0040 left (FOLLOW-UPS 62): the build — not
the agent, not the runner — may use the world DB as an existence oracle for the
late pages that say nothing about their era. `infra/export-world-ids.sh` writes
the four id sets to `data/wiki/world-ids.json` (quest 9,464, creature 29,947,
item 46,096, gameobject 21,580; server-derived, stays out of git) and
`--world-ids` feeds them to the build, which admits a page with no pre-cutoff
revision when an id it states about itself is one of them. An export file rather
than a live query, so the build stays a function of files and reproducible from
them. `spell` and `unknown` ids never match, the post-Wrath and Classic vetoes
still stand ahead of the door, and `meta.world_ids` records the export's
identity — or `none`, when the flag was absent.

The interesting part is the number. The rule was approved on "≈18,700
undecidable late pages, most of them real here"; it admits **145**. A control
rebuild without the flag reproduces the current bundle counter for counter
(81,217 kept), and with it the bundle is 81,368 rows: 145 admitted pages and 6
more empty rows. The reason is that the undecidable population is not what the
census implied — 16,010 of the 22,727 late pages state no id at all (lore,
tactics, disambiguation), and of the 6,717 that do, nearly all state an id in
the 40,000–130,000 range this server has never had. A hand-check of 18 admitted
titles found 5 false: Aeonaxx, Daakara, Grotto Vole, Feral Vermling and Guild
Herald are Cataclysm-or-later pages carrying a 3.3.5 id, either inherited (the
Cataclysm Zul'Aman boss states Zul'jin's 23863) or copy-pasted (three unrelated
pages all state `itemid=44822`). So the door buys 0.18% coverage at roughly 0.7
precision, and the levers if it ever matters — name agreement, and distrusting
an id many unrelated pages claim — are written down in item 62 and not built.
Canary and `verify.ts` are both green on the flag build, but neither can see
this: verify's forbidden titles are zones and dungeons, and every false admit is
a mob or an item.

An exhaustive review of all 151 rows followed — two reviewers, every title
judged, DB names joined in — and it came back 94 true / 57 false, precision
**0.62**, worse than the 18-title sample. It also found the fix, which was
already written down as an unbuilt lever: nearly every false admit states an id
the DB knows under a different name. So the export carries id→name now
(`LogTitle` for quests, `name` for the other three, ~3 MB) and the door requires
agreement between the DB's name and the page's subject — the title minus its
namespace prefix and its trailing parentheticals, compared as words with case
and punctuation folded, one name's words being all of the other's. Word
containment and not substring, because `car` sits inside `carnie`; measured over
the same 151, exact-match and substring rules both lost real pages this keeps
(`Darkmoon Carnie` is `Darkmoon Faire Carnie`, `Rexxar/PI` is `Rexxar`).

The rebuild admits **95 pages (98 rows)** and refuses **53** on the name
(`pages_id_name_mismatch`, a subset of `pages_dropped_post_cutoff`). Every false
admit named above is gone: Aeonaxx (whose 3868 is a Blood Seeker here), Daakara
(Zul'jin's 23863), Grotto Vole (an Adder), the seven pages on the Albino Snake's
44822. The cost is the honest pages that state a wrong id — Corpse Rompers, the
Wrath glyphs, the Frostwyrm mount list — which the rule cannot tell from an
inherited one. ~15 false admits survive by design, their stub id and name both
being real here (Custer Clubnik, Foreman Fisk, Fern Feeder Moth, `Quest:Jaina's
Locket`, …); they are listed in ADR-0042 and item 62 as measured residue, and
per-title exclusions were deliberately not built. 81,315 pages kept, identity
112,121 = 112,121, canary and verify green, 441 tests.
