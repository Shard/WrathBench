## Run view redesign: two-column layout, fixed autoscroll, prominent XP/level chart

The run detail page (`dashboard/src/pages/RunDetail.tsx`) was one long scroll —
meta cards on top, feed below, a tiny XP sparkline buried among the cards, and an
autoscroll that called `window.scrollTo` and did nothing useful. Reworked into a
two-column inspection view.

**Layout.** The page is a flex column: a `fleet / <id>` heading, a full-width XP
chart, then a `.runview-cols` row. Left (`--log-col`, default 70%) is the feed,
its own scroll container. Right (~30%) is everything else — the autoscroll toggle
and live-activity line, all the meta cards (model, character + inventory, tokens,
playtime, cost ×2, level trace), the comparability tuple, termination/pause
banners, and the server footer. Both columns scroll independently, so the run's
meta and the toggle stay in view while the feed scrolls; no sticky needed. Under
900px they stack, sidebar first, feed kept a scroll container (`max-height: 70vh`)
so the autoscroll path is identical in both modes. `.runview-cols` has a 320px
floor so a short viewport lets `main` scroll rather than crushing the feed.

**Autoscroll.** The log column is the scroll container. A new entry pins it to the
bottom (`scrollTop = scrollHeight`) *from an effect on `entries`*, not from the SSE
callback — reading `scrollHeight` before Solid commits the new nodes lands
mid-list and silently flips follow off (the old bug in a new costume). Scrolling up
past 32px turns follow off; scrolling back within it turns it on (`atBottom`,
pure). The manual toggle in the sidebar overrides and is persisted in localStorage
(try/catch guarded); a scroll-driven off is session-only and never saved.

**XP/level chart.** Full-width inline SVG above both columns (`components/XpChart.tsx`).
X = time from run start to `min(now|endedAt, start+episodeMs)` with ~5 elapsed-time
ticks (mm:ss / Hh Mm). Y = cumulative XP, with a dashed gridline + `L<n>` label at
the XP offset each level began. Cumulative XP is a *lower bound* reconstructed in
`lib/runview.ts`: `StatePoint.xp` is within-level and resets, so the total carried
into a level is the sum of each lower level's last observed within-level xp — it
under-counts by whatever was earned between a level's final sample and the ding, a
gap bounded by the sampling interval and never invented upward. Level and xp are
read off the *same* sample (the old sparkline filtered the two into separate lists,
which mis-pairs them), samples sorted by ts, curve clamped monotonic. Comment notes
this is the simple version and uPlot is the long-term plan for denser series; no dep
added. The small level sparkline stays in the sidebar; the XP sparkline is dropped.

**Inventory.** The `carrying:` / `equipped:` lines (item 50, shipped db43c3c) moved
into the sidebar character card with the rest of the meta — not duplicated. `—` for
a run that predates the `items` column, `none` for a recorded-empty side.

Tests: new `dashboard/test/runview.test.ts` pins the band derivation (offsets, same-
sample pairing, monotonic clamp, unordered sort, level-jump, x-window with episodeMs
capped at now / endedAt) and `atBottom`. `bun test` 111 pass, `bun run build` clean.

Verified against the live freeplay run `fleet-nav-probe-freeplay-sonnet-...-c2`
(L5, 6254 entries, 187 state samples, 6h episode): served bundle
`index-B1mKDya-.js` → `RunDetail-BdSHtGji.js` is the new one; the derivation
yields bands L1–L5 at cumulative offsets 0 / 200 / 1028 / 2356 / 4444. Inventory
shows `—` (this run predates the column).

## Fleet: concurrency cap keys on a rate-limit key (free pools capped per platform)

`policy.maxConcurrent` keyed on the driver, so every free OpenRouter + OpenCode +
local model shared the `openai` driver and could not be capped apart. OpenRouter
enforces a daily cap on `:free` models; running several free OpenRouter runs in
parallel burned the budget and produced broken runs. The cap now keys on a
rate-limit KEY (`concurrencyKeyOf`, `runner/src/models.ts`): a free model on a
shared free platform counts under `openrouter` / `opencode`; everything else keeps
its driver key. `fleet.json` now ships `maxConcurrent { claude-code: 2,
openrouter: 1, opencode: 1 }`.

Roster → key mapping (stated for the record):
- `nav-probe`, `sub-opus`, `sub-opus-low`, `sonnet`, `sonnet-low` (claude-code) → `claude-code`
- `ox-alpha`, `nemotron-ultra`, `nemotron-super`, `nemotron-nano`, `north-mini-code`, `laguna-or` (free, OpenRouter/no-apiBase) → `openrouter`
- `muse-spark`, `hy3`, `laguna-oc`, `x-preview-f` (free, opencode.ai) → `opencode` (host normalized in the key fn only)
- `deepseek-flash` (paid, projects to openrouter) → `openai` — NOT a free key; governed by `policy.paid.maxConcurrent: 1`
- `qwen3-8-27b` (local, LAN) → `openai` — NOT capped by the free keys; its one local account is its limit

The free branch gates on `driver === "openai"` and reads the platform from
`platformOfBase(apiBase) ?? "openrouter"` (never the driver), so a `:free` slug
pinned to `driver: "openai"` with no base still lands in `openrouter`. `platform.ts`
is untouched — `run.platform` keeps the `opencode.ai` host spelling; the key fn is
the one seam that normalizes it to `opencode`. Named "key" not "lane" because
`lane` is retired (ADR-0034); ADR amendment records the concept.

Naming swept everywhere: `concurrencyKeyOf` / `CONCURRENCY_KEYS` / `isConcurrencyKey`
(models.ts), `concurrencyKeyOfRef` + the `{ keyOf, max, running }` concurrency
field + `keyCount`/`countKey` locals (run-fleet.ts), the two `--status`/`--dry-run`
print lines, the held reason (`cap: <key> <= n`), the fleet.json `_notes`, and the
viewer doc comments. `parsePolicyBlock` validation accepts the new keys and rejects
unknowns listing the allowed set.

Tests: extended `runner/test/models.test.ts` (key derivation per roster class,
validation accept/reject) and `infra/fleet.test.ts` (openrouter free key caps at
one while a paid openrouter model runs beside it; shipped-fleet.json assertion).
`bun test` in runner/ = 530 pass / 0 fail; typecheck clean. `bun test infra/` =
155 pass / 1 fail — the one failure (`fleet.json` nav-probe `repeat: 1` vs the test's
expected `"loop"`) is pre-existing at HEAD and untouched by this change.

Deploy: the running supervisor validates config with BOOTED code, so it keeps the
old per-driver cap (and shows a REJECTED banner on the new `openrouter` key) until
`docker compose -f infra/compose.yml up -d fleet` recreates it. Benign — no runs
break, runs resume on recreate.

## Paid track: two new models on the standard eval track (gpt-5.6-luna, gemini-3.7-flash)

`deepseek-flash` finished its 3/3 e90 target (best run level 3, below the rung-1
gate, so no e360 earned), which gave the paid class its first real cost basis.
Two models added beside it: `gpt-luna` (`openai/gpt-5.6-luna`, $0.20/$1.20) and
`gemini-flash` (`google/gemini-3.7-flash`, $0.375/$1.875). Both `billing: "paid"`,
both `race: 1, class: 2` with their own character, matching the deepseek baseline
so the start state is not a new dimension. Placed *after* `deepseek-flash` in the
roster because `byPriority` falls through to roster order on a tie, which keeps
the shipped-config test's `deepseek-flash → SHAKEOUT2` assertion meaningful.

There is no `openai/chatgpt-luna`; the catalogue carries an `openai/gpt-5.6-luna`
sub-family (plus a `-pro` at the same price and `:batch` at half). `gemini-3.7-flash`
is not a sale — it is a generational cut: $0.375/$1.875 against 3.6-flash's
$0.75/$3.75 and 3.5-flash's $1.50/$9.00, and it is what `~google/gemini-flash-latest`
currently resolves to.

**The cost basis, corrected.** Fitting the synced rates to what OpenRouter actually
charged the deepseek runs shows our `expected` figure overstates this lane by
1.66–1.88× (a2: $0.0543 actual vs $0.1017 expected; a3: $0.0717 vs $0.1188). To
reproduce the real bill at listed rates ~70% of prompt tokens must have been cache
reads, but `cached_tokens` logs only 12–30% — the provider is discounting beyond
what the usage block reports. So **$0.07/e90 is a floor produced by implicit
caching, not a yardstick**: candidates were priced assuming none, at
`1.8M × $/M-in + 54k × $/M-out` (the a3 e90 shape). That gives ~$0.42/e90 for luna
and ~$0.78 for gemini-flash, ~$3.60 for all six runs.

**Money is not the constraint; the paid account is.** `accounts.paid` is one
account at `maxConcurrent: 1`, and a3 took 114 min wall for a 90-minute episode —
so 2 models × 3 e90 is ~12h strictly serial. That, not dollars, is what sizes the
paid roster; the operator chose two models and the full 3 e90 each.

Prices synced (`bun run sync-prices`, `asOf` 2026-08-24), both rows present. The
slug for each was validated with a live completion before trusting the catalogue —
`gpt-oss-20b:free` taught us catalogue presence is not endpoint reachability.
`gemini-3.7-flash` answers and reports `usage.cost`; note it is a heavy reasoner

### Item 59 fell out of validating the slugs: cache writes were never read

Probing `gemini-3.7-flash` showed OpenRouter sends `cache_write_tokens` **nested
under `prompt_tokens_details`**, and `toUsage` (`runner/src/adapter.ts`) read only
a top-level `cache_write_tokens` — so the counter arrived on every response and
was dropped, and the viewer's `expected` priced every cache write at zero. COSTS.md
had predicted this gap but mis-diagnosed the cause as "no provider emits one"; the
provider does emit one. `toUsage` now flattens writes exactly as it already
flattened reads (top-level wins, details are the fallback), the zod usage block
accepts the field in both positions, and `costOf` already subtracts reads *and*
writes from the prompt before charging input, so nothing double-counts. Three
tests in `runner/test/adapter.test.ts` pin the nested shape, the top-level
precedence, and that a provider reporting nothing leaves the field absent rather
than zero. Runs before this fix carry no write counter and never will; `actual` was
never affected, since OpenRouter reports `usage.cost`.

It mattered now because luna ($0.25/M write, 1.25x input) and gemini-3.7-flash
($0.0208/M, a storage-only rate below input) are the first two roster models to
quote a write tier at all.

`bun test runner/` = 533 pass / 0 fail, `bun test infra/` = 156 pass / 0 fail.

## Viewer bound to the LAN so other machines can help

The viewer was running on 127.0.0.1:8090 with no `WRATHBENCH_VIEWER_LAN`, so only
this host could reach it. Restarted with the opt-in that already exists
(`runner/viewer/serve.ts`; `WRATHBENCH_VIEWER_LAN=1` → `0.0.0.0`), keeping the env
the old process had (`WRATHBENCH_MODULE_URL=http://192.168.192.3:8086`,
`WRATHBENCH_FLEET_CONFIG=infra/fleet.json`). Now `LISTEN 0.0.0.0:8090`, `/api/info`
and the SPA both 200. No code change — the opt-in was always there, it just was
not being passed.

Two things worth writing down, both of which have bitten this setup before:

- **The firewalld rule has to be `--permanent`.** The note in
  `.claude/commands/orchestrate.md` recorded the rule as "runtime-only", which is
  exactly why LAN access kept lapsing — a runtime rule does not survive
  `--reload` or a reboot. `runner/viewer/README.md` now carries the two-step
  recipe (env + rich rule) with the rule scoped to `192.168.1.0/24` rather than a
  bare `--add-port`, which would open 8090 to every network in the `public` zone.
  `enp8s0` is in `public`, the default zone.
- **`curl http://<lan-ip>:8090` from the host proves nothing.** That traffic is
  delivered over `lo` and never crosses the zone, so it returns 200 whether or not
  the port is open to anyone else. It has to be verified from another machine.

The rule itself is not applied — `firewall-cmd` needs root and this session has no
passwordless sudo. Left for the operator; the command is in the README.

## Trial cap on the two new paid models, after measuring luna in flight

The pre-launch estimate for luna was ~$0.42/e90, derived from the token shape of a
deepseek e90 (1.8M prompt / 54k completion). Watching the real run made that 3.5x
wrong, and the reason generalises: **token volume per episode is set by the
model's speed, not by the episode length.** Luna ran 107 snippets in 15.8 minutes
where deepseek managed 139 in 114, so it burns ~8M prompt tokens in the same
90-minute window. Provider-reported `usage.cost` at 15.8 min was **$0.2562**,
projecting to **~$1.46 for a full e90** — and a full paid quota (3 e90 + 1 e360, an
e360 being ~4x the wall clock) lands near **$10**, which is the whole daily budget
for one model.

So both new entries take a per-entry `runsPerEpisode {e90: 1, e360: 0}` instead of
the paid default 3/1. `targetFor` (`runner/src/models.ts`) prefers the entry over
`policy.paid`, so this needs no policy change and no supervisor restart — the
field is already in the booted schema. `--status` confirms it live with no
REJECTED banner: `gpt-luna 1/1` (its in-flight run *is* the trial) and
`gemini-flash 0/1`, held behind it on the paid cap. Bounded spend for the pair is
now ~$3–6 rather than ~$10–17.

Worth noting for whoever scores it: luna reached **L3 at 17 minutes**, which is
where deepseek's best e90 finished after 114.

The general lesson is now in COSTS.md §5: take a real `usage.cost` reading from
the first 15 minutes of a new model's first run; do not extrapolate a cost from
another model's episode shape.
