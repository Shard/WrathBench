## Run view redesign: two-column layout, fixed autoscroll, prominent XP/level chart

The run detail page (`dashboard/src/pages/RunDetail.tsx`) was one long scroll —
meta cards on top, feed below, a tiny XP sparkline buried among the cards, and an
autoscroll that called `window.scrollTo` and did nothing useful. Reworked into a
two-column inspection view.

**Layout.** The page is a flex column: a `fleet / <id>` heading, a full-width XP
chart, then a `.runview-cols` row. Left (`--log-col`, default 70%) is the feed,
its own scroll container. Right (~30%) is everything else — the autoscroll toggle
and live-activity line, all the meta cards (model, character + inventory, tokens,
playtime, cost ×2, level trace), the comparability tuple, termination/pause
banners, and the server footer. Both columns scroll independently, so the run's
meta and the toggle stay in view while the feed scrolls; no sticky needed. Under
900px they stack, sidebar first, feed kept a scroll container (`max-height: 70vh`)
so the autoscroll path is identical in both modes. `.runview-cols` has a 320px
floor so a short viewport lets `main` scroll rather than crushing the feed.

**Autoscroll.** The log column is the scroll container. A new entry pins it to the
bottom (`scrollTop = scrollHeight`) *from an effect on `entries`*, not from the SSE
callback — reading `scrollHeight` before Solid commits the new nodes lands
mid-list and silently flips follow off (the old bug in a new costume). Scrolling up
past 32px turns follow off; scrolling back within it turns it on (`atBottom`,
pure). The manual toggle in the sidebar overrides and is persisted in localStorage
(try/catch guarded); a scroll-driven off is session-only and never saved.

**XP/level chart.** Full-width inline SVG above both columns (`components/XpChart.tsx`).
X = time from run start to `min(now|endedAt, start+episodeMs)` with ~5 elapsed-time
ticks (mm:ss / Hh Mm). Y = cumulative XP, with a dashed gridline + `L<n>` label at
the XP offset each level began. Cumulative XP is a *lower bound* reconstructed in
`lib/runview.ts`: `StatePoint.xp` is within-level and resets, so the total carried
into a level is the sum of each lower level's last observed within-level xp — it
under-counts by whatever was earned between a level's final sample and the ding, a
gap bounded by the sampling interval and never invented upward. Level and xp are
read off the *same* sample (the old sparkline filtered the two into separate lists,
which mis-pairs them), samples sorted by ts, curve clamped monotonic. Comment notes
this is the simple version and uPlot is the long-term plan for denser series; no dep
added. The small level sparkline stays in the sidebar; the XP sparkline is dropped.

**Inventory.** The `carrying:` / `equipped:` lines (item 50, shipped db43c3c) moved
into the sidebar character card with the rest of the meta — not duplicated. `—` for
a run that predates the `items` column, `none` for a recorded-empty side.

Tests: new `dashboard/test/runview.test.ts` pins the band derivation (offsets, same-
sample pairing, monotonic clamp, unordered sort, level-jump, x-window with episodeMs
capped at now / endedAt) and `atBottom`. `bun test` 111 pass, `bun run build` clean.

Verified against the live freeplay run `fleet-nav-probe-freeplay-sonnet-...-c2`
(L5, 6254 entries, 187 state samples, 6h episode): served bundle
`index-B1mKDya-.js` → `RunDetail-BdSHtGji.js` is the new one; the derivation
yields bands L1–L5 at cumulative offsets 0 / 200 / 1028 / 2356 / 4444. Inventory
shows `—` (this run predates the column).

## Fleet: concurrency cap keys on a rate-limit key (free pools capped per platform)

`policy.maxConcurrent` keyed on the driver, so every free OpenRouter + OpenCode +
local model shared the `openai` driver and could not be capped apart. OpenRouter
enforces a daily cap on `:free` models; running several free OpenRouter runs in
parallel burned the budget and produced broken runs. The cap now keys on a
rate-limit KEY (`concurrencyKeyOf`, `runner/src/models.ts`): a free model on a
shared free platform counts under `openrouter` / `opencode`; everything else keeps
its driver key. `fleet.json` now ships `maxConcurrent { claude-code: 2,
openrouter: 1, opencode: 1 }`.

Roster → key mapping (stated for the record):
- `nav-probe`, `sub-opus`, `sub-opus-low`, `sonnet`, `sonnet-low` (claude-code) → `claude-code`
- `ox-alpha`, `nemotron-ultra`, `nemotron-super`, `nemotron-nano`, `north-mini-code`, `laguna-or` (free, OpenRouter/no-apiBase) → `openrouter`
- `muse-spark`, `hy3`, `laguna-oc`, `x-preview-f` (free, opencode.ai) → `opencode` (host normalized in the key fn only)
- `deepseek-flash` (paid, projects to openrouter) → `openai` — NOT a free key; governed by `policy.paid.maxConcurrent: 1`
- `qwen3-8-27b` (local, LAN) → `openai` — NOT capped by the free keys; its one local account is its limit

The free branch gates on `driver === "openai"` and reads the platform from
`platformOfBase(apiBase) ?? "openrouter"` (never the driver), so a `:free` slug
pinned to `driver: "openai"` with no base still lands in `openrouter`. `platform.ts`
is untouched — `run.platform` keeps the `opencode.ai` host spelling; the key fn is
the one seam that normalizes it to `opencode`. Named "key" not "lane" because
`lane` is retired (ADR-0034); ADR amendment records the concept.

Naming swept everywhere: `concurrencyKeyOf` / `CONCURRENCY_KEYS` / `isConcurrencyKey`
(models.ts), `concurrencyKeyOfRef` + the `{ keyOf, max, running }` concurrency
field + `keyCount`/`countKey` locals (run-fleet.ts), the two `--status`/`--dry-run`
print lines, the held reason (`cap: <key> <= n`), the fleet.json `_notes`, and the
viewer doc comments. `parsePolicyBlock` validation accepts the new keys and rejects
unknowns listing the allowed set.

Tests: extended `runner/test/models.test.ts` (key derivation per roster class,
validation accept/reject) and `infra/fleet.test.ts` (openrouter free key caps at
one while a paid openrouter model runs beside it; shipped-fleet.json assertion).
`bun test` in runner/ = 530 pass / 0 fail; typecheck clean. `bun test infra/` =
155 pass / 1 fail — the one failure (`fleet.json` nav-probe `repeat: 1` vs the test's
expected `"loop"`) is pre-existing at HEAD and untouched by this change.

Deploy: the running supervisor validates config with BOOTED code, so it keeps the
old per-driver cap (and shows a REJECTED banner on the new `openrouter` key) until
`docker compose -f infra/compose.yml up -d fleet` recreates it. Benign — no runs
break, runs resume on recreate.

### Item 59 fell out of validating the slugs: cache writes were never read

Probing `gemini-3.7-flash` showed OpenRouter sends `cache_write_tokens` **nested
under `prompt_tokens_details`**, and `toUsage` (`runner/src/adapter.ts`) read only
a top-level `cache_write_tokens` — so the counter arrived on every response and
was dropped, and the viewer's `expected` priced every cache write at zero. COSTS.md
had predicted this gap but mis-diagnosed the cause as "no provider emits one"; the
provider does emit one. `toUsage` now flattens writes exactly as it already
flattened reads (top-level wins, details are the fallback), the zod usage block
accepts the field in both positions, and `costOf` already subtracts reads *and*
writes from the prompt before charging input, so nothing double-counts. Three
tests in `runner/test/adapter.test.ts` pin the nested shape, the top-level
precedence, and that a provider reporting nothing leaves the field absent rather
than zero. Runs before this fix carry no write counter and never will; `actual` was
never affected, since OpenRouter reports `usage.cost`.

It mattered now because luna ($0.25/M write, 1.25x input) and gemini-3.7-flash
($0.0208/M, a storage-only rate below input) are the first two roster models to
quote a write tier at all.

`bun test runner/` = 533 pass / 0 fail, `bun test infra/` = 156 pass / 0 fail.

## Viewer bound to the LAN so other machines can help

The viewer was running on 127.0.0.1:8090 with no `WRATHBENCH_VIEWER_LAN`, so only
this host could reach it. Restarted with the opt-in that already exists
(`runner/viewer/serve.ts`; `WRATHBENCH_VIEWER_LAN=1` → `0.0.0.0`), keeping the env
the old process had (`WRATHBENCH_MODULE_URL=http://192.168.192.3:8086`,
`WRATHBENCH_FLEET_CONFIG=infra/fleet.json`). Now `LISTEN 0.0.0.0:8090`, `/api/info`
and the SPA both 200. No code change — the opt-in was always there, it just was
not being passed.

Two things worth writing down, both of which have bitten this setup before:

- **The firewalld rule has to be `--permanent`.** The note in
  `.claude/commands/orchestrate.md` recorded the rule as "runtime-only", which is
  exactly why LAN access kept lapsing — a runtime rule does not survive
  `--reload` or a reboot. `runner/viewer/README.md` now carries the two-step
  recipe (env + rich rule) with the rule scoped to `192.168.1.0/24` rather than a
  bare `--add-port`, which would open 8090 to every network in the `public` zone.
  `enp8s0` is in `public`, the default zone.
- **`curl http://<lan-ip>:8090` from the host proves nothing.** That traffic is
  delivered over `lo` and never crosses the zone, so it returns 200 whether or not
  the port is open to anyone else. It has to be verified from another machine.

The rule itself is not applied — `firewall-cmd` needs root and this session has no
passwordless sudo. Left for the operator; the command is in the README.

## Trial cap on the two new paid models, after measuring luna in flight

The pre-launch estimate for luna was ~$0.42/e90, derived from the token shape of a
deepseek e90 (1.8M prompt / 54k completion). Watching the real run made that 3.5x
wrong, and the reason generalises: **token volume per episode is set by the
model's speed, not by the episode length.** Luna ran 107 snippets in 15.8 minutes
where deepseek managed 139 in 114, so it burns ~8M prompt tokens in the same
90-minute window. Provider-reported `usage.cost` at 15.8 min was **$0.2562**,
projecting to **~$1.46 for a full e90** — and a full paid quota (3 e90 + 1 e360, an
e360 being ~4x the wall clock) lands near **$10**, which is the whole daily budget
for one model.

So both new entries take a per-entry `runsPerEpisode {e90: 1, e360: 0}` instead of
the paid default 3/1. `targetFor` (`runner/src/models.ts`) prefers the entry over
`policy.paid`, so this needs no policy change and no supervisor restart — the
field is already in the booted schema. `--status` confirms it live with no
REJECTED banner: `gpt-luna 1/1` (its in-flight run *is* the trial) and
`gemini-flash 0/1`, held behind it on the paid cap. Bounded spend for the pair is
now ~$3–6 rather than ~$10–17.

Worth noting for whoever scores it: luna reached **L3 at 17 minutes**, which is
where deepseek's best e90 finished after 114.

The general lesson is now in COSTS.md §5: take a real `usage.cost` reading from
the first 15 minutes of a new model's first run; do not extrapolate a cost from
another model's episode shape.

## The map replay recursed, and the fix was a seam rather than an `untrack`

Firefox reported `InternalError: too much recursion` under the play slider, and
the map froze while the slider itself moved. One cause for both. `ingest()` read
`activeMap()` and `selected()` and wrote `setMaps`, `setCount`, `setActiveMap`
and `setSelected` — from inside the effect that fed it. Live, that mostly settled
by accident: the poll hands out the same objects each time, so `setSelected` saw
an unchanged identity and stopped. Replay does not have that luck. `positionsAt`
mints a fresh `AgentPosition` on every call, so the write always looked like a
change, the effect always re-entered, and it never reached a coherent frame —
which is exactly what "the slider works but the map does not move" looks like.

An `untrack` around the reads would have silenced it and left the shape that
produced it. The real answer was to finish the split the file's own header
claims: the renderer owns mutable state and `requestAnimationFrame`, Solid owns
what is displayed. So the fold became `syncPips`, a plain function over a plain
`Map` that touches no signal (`lib/mapview.ts`), and everything the page shows
moved into `lib/mapstate.ts`, which is memos over four sources — the feed, the
track, the pinned map, the selected *id* — and writes nothing at all. Selection
is an id rather than a reading, so a fresh object per tick can no longer be
mistaken for a change. The sticky "stay on this map while it still has an agent"
choice, the one thing that genuinely needed to read its own last answer, is a
`createMemo` reducer taking `prev` as an argument: `chooseMap` is pure and the
stickiness is an input, not a write-back.

Effects in the page now go one way. The feed effect reads the track, cursor and
poll and writes the feed signal plus the pip map; the follow effect reads the
cursor's map and writes the pin; the fit and route effects read signals and write
only renderer state. No signal is read and written in one scope, which is a
property of the file's shape now rather than a thing to remember.

The review that followed found three real things and left two. Fixed: playback
stepped with `points.find`, a full scan of the track four times a second, now
`nextSampleAfter` over the existing binary search; the replay route was rebuilt
from the whole prefix on every frame including every frame of a pan, now cached
by the effect that owns it; and a fast `?run=a` to `?run=b` could let the loser of
the race win, now guarded by a token. Fitting the view is deliberately *not*
reactive — it happens on a track load, a chip click and the first map to appear,
because an unrelated agent logging out can flip which map is busiest and yanking
a panned view for that would be hostile. Deferred as item 60: the 4096 stroked
grid cells when zoomed out, and route decimation for tracks long enough to feel.

The regression test is a live reactive graph, which needed one piece of plumbing
worth knowing about: `bun test` resolves `solid-js` under the node condition,
which is the server build whose signals never notify. A graph test against it
passes no matter what the graph does. `test/mapview.test.ts` redirects the name
to the browser build before loading the derivation, then counts how many times a
downstream computation runs across five feed updates carrying fresh identities.
Six. Under the old shape it did not terminate.

## Map navigation: two URL states, and going back the other way

The map had a working way in and a half-working way out. `/map?run=<id>` loaded a
replay, but the only way back to live was a text link trailing the timestamp at
the end of the scrubber, and the state it left behind was whatever the replay had
accumulated. The clearing that did exist happened inside the track fetch's
response, which is the wrong moment twice over: nothing was cleaned up at all on
the way back to live, and swapping one replay for another kept the first run's
pips on screen under the second run's identity until the second track landed.

So the swap has one owner now. The effect that reads the search parameter clears
unconditionally and *before* it fetches, which makes every route into the two
states the same code path — the new control, browser back and forward, a deep
link opened cold, one replay straight to another. The clear itself is
`clearReplayState`, a pure writer taking setters as arguments, which is what lets
it be tested against a real reactive graph instead of by looking at a canvas.

One line of it looks like dead weight and is the interesting part. `activeMap` is
the reducer memo from yesterday's refactor, and its stickiness lives inside the
memo rather than in any source signal, so clearing the four sources does not by
itself forget which continent the replay ended on. Pushing an empty feed through
once does: the memo recomputes over an empty map list, finds its own previous
answer no longer present and returns null. Without it, returning to live from a
replay of Outland sits on Outland because one straggler happens to be standing
there, while the crowd is on Azeroth. Three of the new tests fail if the line goes
away, which is the only durable way to say "load-bearing" about a line that reads
as redundant.

Returning to live stayed a link rather than becoming a button with a handler.
Since the route change is what performs the swap, the control needs no logic, and
an anchor keeps what an anchor gives: a real history entry, middle-click, the
focus ring. It sits with play; the trailing link is gone, because two affordances
for the same thing where one cleaned up less is how the stale state got there.

The other direction turned out to exist already — and to be invisible. `replay on
map` was wedged into the `comparability` section heading on the run page, which
is why it read as missing: nobody looks for navigation inside a heading about
budget tuples. It moved to the sidebar's controls row, which now renders whether
or not the run is live, so the loop closes at both ends against the map's
`open run →`.

Nothing fast-changing went into the URL. Cursor, playback, pinned map, selection,
pan and zoom stay in memory — a cursor in the query string would rewrite history
four times a second under the play slider. The price is that coming back to a
replay restarts it at the first sample, which is item 61 rather than a silent
regression.

Verified without clicking anything: the reset tests drive the real graph into
mid-replay, read `activeMap` so the reducer caches its answer, clear, and assert
the derived state is back to the live baseline and that a following live feed
picks its own busiest map; `runParam` pins the URL-to-mode mapping including the
empty and repeated forms. Back/forward and deep links are the same effect as the
button by construction, not by observation. 1324 tests pass, dashboard build
clean.

## Episode progress in the fleet table's state cell

The state column now carries a percentage beside its badge, and the cell's title
reads `ETA: <time> — <elapsed> of <budget>`. One number an operator will believe,
which is the whole reason the interesting part of this was deciding where it is
allowed to appear.

The denominator is the run's own recorded `comparability.budget.episodeMs` and
nothing else. A tier's nominal 90 or 360 minutes is a claim about the tier, and
`nav-probe` is the standing proof that a roster entry overrides it; deriving a
budget from an episode id would have produced a confident wrong number on exactly
the row most worth watching. A run with no recorded budget shows nothing. That
also meant no viewer API change: the runs feed already carries the tuple.

The numerator is `playtimeMs`, and it is the right clock now — but it was not
always. `tail.ts` still says the `episode-limit` watchdog resets on every resume
and never sees paused time, which was true when it was written (6f44a06,
2026-08-22) and stopped being true a day later, when 08cd691 made run.ts carry
`elapsedBeforeMs` from the persisted `episodeElapsedMs`. Both clocks now exclude
paused stretches; they are accumulated differently — trajectory segments against
process uptime — so they agree to within a segment boundary and the comment on
`rowProgress` says so rather than implying millisecond agreement. The stale
comment is item 73, not an edit: a live run was going through the viewer.

Only `running` and `draining` show progress. Everything else is a row whose
episode clock is not moving, and a countdown that ticks while nothing runs is a
lie: `paused` and `paused-deploy` hold a run that gave its session back,
`resuming` has not picked one up yet, `idle` holds nothing, `exited` is over. The
`resuming` gate is on the state and not on a missing run id, because a resuming
row *has* one (`runId ?? job.resuming`) and today shows nothing only by accident
of where the run lookup keys — there is a test that fails if that accident is
refactored away.

Freeplay shows nothing, against the evidence that it could. `nav-probe` records a
real six-hour watchdog and would light up honestly, but the id is uncapped and
"72% of freeplay" reads as a tier fact it is not. The gate is one predicate and
item 74 says where to delete it if the operator wants that number after all.

Over budget prints the real figure. `fleet-deepseek-flash-e90-…-a3` ran 114
minutes against 90 and ended on `episode-limit`; 127% is the signal, and clamping
to 100% would hide it. Past due, the title stops counting down and says how far
past it is, so no negative duration can reach `fmtDuration`.

No new timer. Both numbers come off the existing 10s poll of `/api/runs`, which
charges a live run's playtime up to request time — and because numerator and
denominator ride the same snapshot they cannot tear.

The one caveat is written into the comment rather than left implied: a run
resumed from a pause mark written before `episodeElapsedMs` existed restarts the
watchdog at zero while playtime keeps its earlier segments, so the percentage
over-reads on exactly those runs. It errs toward "further along", never toward
hiding an overrun.

Verified without clicking: eight new tests in the pure layer assert the shipped
strings, not just the maths — normal, draining, freeplay, over-budget, paused,
resuming, idle-and-exited, and no recorded budget — which is where the row maths
belongs (dashboard/README.md). `bun test dashboard/test/fleet.test.ts` is 30 pass,
0 fail; the full suite ran green (1337) alongside another session's unstaged map
work in the shared worktree, so that total is not a clean measure of this change.
The component was read against the tests and the built bundle checked for the
shipped title strings and the `.progress` rule; the title's elapsed figure is the
same `fmtDuration(elapsedMs)` the elapsed column prints, so the two cannot
disagree on screen. Dashboard build clean.

## The tier is the evidence budget (ADR-0043)

Trialling luna and gemini on one e90 each cost a per-entry `runsPerEpisode`
override, a queue job split in two, an account-class dance and four rounds of
test failures — and the board then said `gpt-luna paid promoted 1/1 L6 0/0`.
That row is the whole diagnosis. The projection asserts the model earned an
`e360`; the target asserts it will never run one; nothing reconciles them,
because a **gate** had been encoded as a **target** for want of any way to say
"this model is on trial". Four knobs answered how much a model runs, and they
could disagree.

A five-agent fanout mapped the current system before anything was designed, and
found more than the shape problem. Three defects with line cites: a manual queue
job merely *waiting* zeroed the entire policy pass across every account class
(so a job stuck behind a busy RUNNER held the LM Studio box idle) and reported
nothing while doing it; `paidPoolOf` only creates the paid class conditionally,
so a config without `policy.paid` silently re-spills paid picks into the free
pool that ADR-0034 exists to stop; and the coexistence rule is enforced at parse
time, so flipping one job's `enabled` takes the whole file down and every other
flag with it. The first is fixed here because the idle axis is built on that
gate; the other two are items 76 and 66.

The design went to Fable adversarially, and it was right about three things. The
freeplay axis as first drawn (`f0`/`f1`) named only freeplay, so defaulting it
off would have silently deleted the free roster's character extras — a behaviour
change smuggled into a stage claiming to be representation-only. It is one axis
with three values instead. The stage-1 golden test as specified contradicted its
own design point: "byte-identical `projectModel` output" is violated by the
`promoted 0/0` fix, which is deliberate. And the paid/free split in `t2` is not
a wart to remove but the price axis of evidence — though the operator's answer
was better than either of us had: put paid models on `t0` and let the ladder be
uniform, so money is expressed by *which tier is assigned*, not by a conditional
inside one. That collapses the last per-billing table.

The consequence worth pricing, raised before building: with a uniform ladder,
`t1 → t2` is automatic, so promoting a paid model to `t1` would auto-buy `t2`'s
e360s. `t2` is therefore `e360 x1` for everyone and deeper sampling becomes a
reserved `t3` — a rung an operator grants, not a conditional that hides. `t3`
stays unimplemented on purpose: it wants a criterion, and rung 2 of the game
ladder is not instrumented (item 35).

The subtle half is keeping the witness apart from the ladder. `t0` blocks only
the unlock, never the record: a trial model that hits level 5 shows `t0*` and
spends nothing, so moving it to `t1` promotes it immediately on evidence it
already has, with nothing re-run. The mirror case matters as much — a model an
operator hand-places on `t2` is eligible and never reads as promoted, because
"promoted" is now said only of a climb. Encoding the gate as a target is what
produced `promoted 0/0`; encoding it as a flag beside the tier would have
reproduced the same class of bug, which is why `promote: never` was rejected in
favour of `t0` being terminal.

The series does not bump, and that argument is worth more than the golden test
that evidences it. `harnessSeries`'s own contract is that a minor bump is a
change to what a run *measures*; this changes what gets *scheduled*. Every run's
comparability tuple, the counted-run set and the promotion witnesses are
identical across the change — targets are stopping rules, not measurements. Had
that been read the other way, every row on the board would have reset and the
paid track would have re-run at ~$10/day for a config cleanup.

One collision caught late: **tier** already meant *episode* in prose. In code it
never did (episodes have always been `EpisodeId`), but `docs/EPISODES.md` and
the dashboard both used it loosely, and a rename done in one place and skipped
elsewhere is worse than none. Both say *episode* now.

## The accounts table was naming a job that had already finished

Asked whether the board was drained enough to deploy 0.5, and answered from
`--live-runs`, I noticed it disagreed with the `--status` accounts table. That
turned out to be worth chasing before the restart rather than after.

`state.jobs` is keyed by job *name*, which is stable across attempts, so it is
a cumulative record of every job the supervisor has ever spawned — over a night
a dozen entries name the same pool account. `printStatus` built its account map
by writing every job into it and letting the last one win, which reads the
object's insertion order, and insertion order is *first*-spawn order. So a job
that exited at noon outranked the run holding the account at 14:00. On disk:
`hy3-e90` (index 3, live, spawned 13:15) was masked by `muse-spark-e90` (index

the bug it would be a double-lease: `planTick`, `planPolicyHeld` and the live
tick (`run-fleet.ts:3253`) all lease by `accountHeldBy`, the trajectory-store
inference, which is also what `--live-runs` prints. But it made the board

being told a finished job held an account that a live run was on.

shows" is how this hid, and is corrected: they are two sources — one is the

## Three cleanups behind the campaigns work (items 76, 66, 73)

Not campaign work, but the same file and the same class of problem: the config
was more fragile than the record said it was. Both fixes point the same way —
an incomplete or contradictory config should cost the operator the one thing
they got wrong, never the rest of the file.

**Item 65 — the paid class is split unconditionally.** `paidPoolOf` created the
class only when `accounts.paid` was non-empty or a `policy.paid` block was
present. With neither, a paid pick took a free pool account and billed on it,
while `fleet.json`'s `_notes` and ADR-0034's account-class amendment both state
the rule with no exception. The code was conditional where the record was
absolute. Now both split classes are unconditional, `classPoolsOf` is a two-key
literal, `paidPoolOf` is gone, and `formatPaidClass` is the same shape as
`formatLocalClass`. An unconfigured paid class holds its picks and names them,
exactly as `local` has since ADR-0034: the failure of an incomplete config is a
model that does not run, never an account that quietly spends. That leaves
`policy.paid` with its one real job, the concurrency cap, rather than doubling
as the switch deciding whether the class existed. No live change — the shipped
config sets both keys — and the test that asserted the spill now asserts the
hold.

**Item 66 — a violated account rule refuses the pin, not the file.** `parseFleet`
failed the whole config when an enabled job sat on a listed account or two
enabled jobs shared one; because a rejected re-read keeps the last good config,
one `enabled: true` made every other flag in the file inert until somebody read
the REJECTED banner. The rules are unchanged and right; the blast radius was
not. A violating pin is disabled in place and named in `config.refusals`, and
the rest of the file takes effect. Shape errors and duplicate job names still
fail — a file that does not parse has no rest to keep, and a duplicate name has
no losing pin to pick.

The jobs and campaigns loops were two near-identical 30-line copies of the same
rules; they are one `Pin` list now, checked once in file order. File order is
also what decides the loser when two pins want one account — the first keeps
it — so adding an entry above another never moves the verdict. The preflight
clash joins the refusals where there is a pin to name; where the loser would be
an account list, it still fails.

A refusal is quieter than the outage it replaces, which is the risk as much as
the point: the file loads, so nothing else looks wrong, and the only notice is
the message. So it is surfaced twice — a `!` block under the REJECTED banner in
`--status`, and a `config-refusal` event plus a log line in the supervisor,
deduped on the joined set so a standing refusal speaks once while a swapped one
still speaks.

Verified against the real `fleet.next.json`, not only fixtures: flipping the
parked burn-switch job on SHAKEOUT2 to `enabled: true` refuses that job alone
and leaves both campaigns, the 18-entry roster and the pool in effect. Before
today that same edit took the file down.

**And the regression that verification missed.** Every test stopped at
`parseFleet`'s output; nothing exercised what the tick does downstream of
`enabled: false`. It drains. `diffJobs` SIGTERMs a running job whose spawn is
gone or disabled at the next episode boundary — correct for a pin the operator
parked, catastrophic for one that was overruled. Adding a queue job on an
account a campaign already holds would have killed that campaign's probe hours
into its episode, where the whole-file rejection it replaced left the run
completely alone. A cheaper failure traded for a more expensive one, which is
the opposite of the point.

So a refusal means "do not schedule", never "stop what is running". A pin now
carries the job names it can spawn under — itself for a job, one per declared
cell for a campaign, matching `pinnedCampaignJobs` — and the tick spares any
live run under a refused pin, says so once, and records `refusal-spared`. The
run finishes and does not respawn. Proven against the live board: the raw diff
drains `nav-probe-coldridge` (the probe that was at L3 while this was written)
and the guard leaves it.

The lesson generalises past this item: a pure function's output was tested
exhaustively and the behaviour change was two call sites away. `enabled` is not
a fact about a config, it is an input to a scheduler that kills processes.

**The config notes are ahead of the running binary.** `infra/fleet.next.json`'s
`_notes` are hot-reloaded every 60s by a supervisor still running the
pre-`4eb455d` parser, so they now describe behaviour that binary does not have:
against it, flipping `sub-opus-low` on still takes the whole file down. The
supervisor was not restarted — five runs are live, including a campaign probe —
so this lands at the next deploy window.

**Item 62 — a comment that had gone false.** `playtimeMs` said `Watchdogs` is
built with `startedAt = now()` per process, so `episodeMs` was per-process
uptime and playtime a strict superset. 08cd691 made run.ts pass
`elapsedBeforeMs` from the persisted `episodeElapsedMs`, so the episode clock
carries across a pause. Both clocks exclude paused time and differ only in how
they accumulate it, and the comment now says where they still diverge: a run
that died without recording its elapsed time resumes the watchdog at zero while
the segments still remember the earlier work.

## Item 70 withdrawn: the ladder was never lane-shaped

Item 70 recorded that the defer ladder is not split per lane — a probe failure
climbs the same ladder an eval would — and argued that was the right default.
It is, but the item was written on a premise the code contradicts, so there was
nothing to revisit and nothing to record.

Two facts. `matchesRoster` is `model + effort`, and `projectModel` walks only
that entry's own runs, so the ladder is per roster entry: no model's failure
can cool another, whatever key or pool they share. And `isNoProgress` is
stillborn or `adapter-error` and nothing else — both properties of the
endpoint, neither of the task. A probe that runs its full 90 minutes and
achieves nothing ends `episode-limit` or `idle`, which resets the ladder rather
than climbing it.

So the item's own revisit trigger — "a campaign with a genuinely harder task
starts retiring models that were fine on `e90`" — cannot occur. Task difficulty
is invisible to the ladder by construction. Sharing it across lanes is not a
default worth defending; it is the only thing the ladder could mean.

Noted while checking, and deliberately NOT filed as an item: the converse is
mildly true. Entries sharing one credential — the four OpenCode Zen slugs, the
free OpenRouter pool — each climb their own ladder, so a dead key takes four
times the failed launches to cool all four. `concurrencyKeyOf` groups them for
the concurrency cap but nothing groups them for cooling. It costs a handful of
stillborn launches an hour and self-corrects; file it if a dead key ever
actually burns a night.

## Item 60: the map canvas costs scale with the screen now, not the world

Delegated to an Opus subagent and independently re-verified here. Both halves
landed in `dec01d2`.

The fallback lattice was one `strokeRect` per visible cell — the whole 64x64
world below `TILE_MIN_PX`, which a pan turned into 4096 calls per frame. It is
one stroked path of at most 130 segments now. The restructure is safe for a
reason worth stating: below the threshold nothing is drawn INTO a cell, so
nothing can be covered, while the per-cell arm above the threshold is left
exactly as it was because there a drawn tile still has to suppress its own
outline. The `t !== null` guard that went with it was already dead — `tile()`
returns `TileEntry`, never null; the null came only from the ternary.

The replay route is decimated to screen resolution, in world units with the
tolerance from the scale alone. That makes the result independent of the
offset, so a pan — the gesture item 60 actually named — reuses the cache, and
only a zoom or a freshly built prefix rebuilds. First and last points always
survive; the last is where the pip sits, and a route whose tail detaches from
the character is worse than a slow one.

The geometry is three pure functions in `mapview.ts` (`latticeLines`,
`worldPerPixel`, `decimateRoute`) with 13 tests. The decimation measures against
the last KEPT point rather than the last input point, which is what bounds the
error on a slow drift; verified here rather than taken on report, by making the
natural mis-implementation and confirming three of the tests fail on it (they
keep 2 points with a worst deviation of 60 world units).

Four caveats recorded rather than filed, none worth an item:

1. **No test covers the `drawGrid` restructure itself.** The geometry is
   covered; the branch that consumes it is imperative canvas code.
2. **The lattice style visibly changes at the threshold today.** Above it a

## Item 58: the gate's backpack is emptied at the start of the run

`kill-credit.ts` runs on the preflight gate with a persistent character, loots a
kobold every tick, and `scenarios.ts` cannot clear items (item 57). The item
proposed selling or destroying before logout. Start of run is strictly better and
that is what shipped: it is idempotent, it runs after a previous run FAILED and
skipped its own cleanup — which is exactly when the bag is fullest — and it makes
the loot line readable as "N free slots, then loot arrived". `destroy_item` is
`CMSG_DESTROYITEM`, the same opcode a player pressing delete sends, so this needed
no fixture change and never touched item 57's guid problem.

Two properties do the real work. The keep rule **fails toward keeping**: only a
slot positively identified as a non-keep item is destroyed, an unresolved slot is
kept and named in the output, and 6948 is protected — a fixture cannot restore a
Hearthstone it destroys, so a naive "empty bag 255" would have been permanently
destructive. And the clear is best-effort and REPORTED, never asserted: it calls
`req()` rather than `action()`, because `action()` fails the run on a refusal, and
a cleanup failure that aborts the smoke is indistinguishable from the loot bug
this exists to prevent. An empty read is reported as "contents unknown" rather
than as a reassuring zero, since the Hearthstone is a permanent occupant.

Re-verified independently rather than taken from the report: a fresh run found
three items left by earlier runs, cleared them to 15 free (16 minus the
Hearthstone), and `item 6948` was still in slot 23 afterwards.

The item's estimate was wrong in the direction that matters — the observed rate is
2-3 items per run, not 0-1, and five runs' worth was already sitting in the bag.

**A measurement lesson, from getting it wrong myself.** I read
`character_inventory` immediately after a run and concluded the smoke's own
"N free slots" line was undercounting, and edited the line to say so. It was not:
destroyed and looted items reach the database only when the LOGOUT SAVE lands, so
a read taken before `characters.online` flips to 0 shows a mix of rows already
destroyed in memory and rows not yet written. Waiting for the flag and reading
again gave Hearthstone plus exactly the two items that run looted — 13 free, which
is precisely what the smoke had logged. The edit was reverted. Any DB assertion
about a smoke character has to poll `online = 0` first, which is what
`apply.ts` already does and why it does it.

Durability is deliberately NOT fixed, and is quantified so the decision is a
decision: both durability-bearing items were 25/25 before and after three fights,
and the steady-state path (`Unit::DealMeleeDamage`, `DurabilityLossChance.Damage`
0.5%, one point off a uniform draw over 19 equipment slots of which 2 hold a
durability item) is ~0.05% per damage event — roughly one point per ~100 runs, so
thousands of gate ticks from zero. The only fast path is `DurabilityLoss.OnDeath`,
and this smoke treats a death as a failure by construction.

## A `<page>` block is not a page

A full-dump census for the era-cutoff work turned up a bug under it: the history
dump emits one `<page>` element per 50 revisions, so a page with 627 revisions
arrives as 13 consecutive blocks, newest-first. `parse.ts` finished a page on
`</page>`, which made every block a row — 114,501 `pages` rows for 104,808
distinct (title, ns). The 9,693 extra rows held 2005-2009 text and competed
with the same page's current text in `pages_fts`; `resolveTitle` picked between
them by rowid luck.

The parser now holds a page open and finishes it when the (title, ns) key
changes or the stream ends, adopting the pending accumulator when the next block
continues the same page. Blocks for a title are contiguous in the dump (the
census found zero exceptions), and `beats` already selects on (timestamp, rev
id), so peak memory is still one revision body whatever the history depth.

Two guards, because luck is not a design: `resolveTitle` orders explicitly
(ascending id — the dump is newest-first, so the block holding the newest
revision was written first), and the build calls `assertUniquePages` before it
indexes, recording `pages_distinct_keys` in `meta` and throwing otherwise, with
a UNIQUE index behind it. The check sits inside the try that unlinks the temp
file, so a failure leaves the deployed bundle untouched.

The deployed bundle keeps its 9,693 stale rows until it is rebuilt.

## The bundle reads the era it plays: prose from 2010, structure from 2020

Item 49's real fix, and the one the day's other wiki commits were clearing the
way for. A page row is now built from **two** revisions of itself: the prose is
the newest revision saved before 2010-10-12 (patch 4.0.1, the Cataclysm
pre-patch), while everything structured — coordinates, entity ids, the quest
infobox — still comes off the newest revision, where a decade of corrections
lives and where 30% of the coordinates only exist. ADR-0040 has the reasoning;
the short version is that prose ages badly and a `{{coords}}` template does not.

Two hygiene rules decide the era revision, because "newest before the cutoff" is
not the same as "what the page said": a revision where the page was a
`#REDIRECT` is not prose, and a revision that was immediately reverted (the next
revision restored a sha1 the page already had) is not what the page said either.
A page with no pre-cutoff revision at all — 20,428 of them, 18.6%, the wiki grew
after 2010 — keeps its newest text and carries a fixed page-level label saying
so. Nothing is dropped for being late. `meta` records both paths
(`pages_era_swapped`, `pages_era_fallback`), so the split is auditable per build.

Verified on a full rebuild: pages that mention Cataclysm with no label at all
2,025 → 650; Deathwing / the Shattering / Pandaria 2,032 → 306; the Coldridge
Valley "prior to its collapse" prose that triggered the item, 3 hits → 0.
Coordinates are down 2.6% and ids 1% — not the era swap, which does not touch
them, but the duplicate rows the block merge removed.

The residue is real and now its own item (FOLLOW-UPS 62): the ~650 left are
mostly 2009–10 prose about the expansion that had been *announced*, which no
revision line can reach, plus the labelled fallback pages.

## Direction change: the bundle is a Wrath snapshot, not a labelled dump

The operator's call, mid-item: nothing is labelled by era any more, because
content that is not 3.3.5 is not in the bundle. ADR-0029's "mark, never delete"
was never an operator decision — the implementing agent made it on 2026-08-23
and it went in as if it were policy — and the standing position is the opposite:
the dump is a known rough source, the bundle is a product filtered and stripped
as the evidence warrants, and removal is reversible by rebuilding. ADR-0029 now
carries a dated retraction of that rule; ADR-0040 was rewritten around the
principle.

What that made possible: the revision cutoff can now decide the whole page, not
just its prose. A page with no revision before 2010-10-12 is not emitted
(`pages_dropped_post_cutoff`), and redirect-ness is decided from the Wrath
snapshot too — a page that was a redirect then is one here, a page that was an
article then is an article here even if it was merged away in 2014 (144 pages
flip), and a redirect whose chain does not end at a surviving page goes with its
target.

Three levels below that, each counted in `meta`. **Page:** `admitPage`
(`wiki/src/post-wrath.ts`) is one pure function with five reasons —
`pre_cutoff`, `post_cutoff_wrath_signal`, `dropped_post_cutoff`,
`dropped_post_wrath`, `dropped_meta` — and the build test asserts those five plus
`empty_pages` account for every non-redirect page the parser yields, which is the
only thing that would catch a page counted twice or lost quietly. **Section:** a
`{{cata-section}}` or `== In Cataclysm ==` section is dropped, heading and all.
**Paragraph:** narrow phrase rules over the prose of a blank-line block, with the
templates removed first so an infobox field never decides.

The rules are narrow where the words collide, and the census is the evidence: of
the category names on late pages, `Burning Legion` appears 39 times against
`Legion`'s 29, so "category contains Legion" would have deleted the Burning
Legion from a bundle whose world contains it. The category rule fires only on a
category that *is* `Legion` or starts with `Legion `. `{{Removedwithlegion}}` and
`{{Removedwithcataclysm}}` are not signals at all — content removed later exists
here — and `{{legion-inline}}` (278 uses) marks a clause, not a page. Draenor is
Outland's own name, so only `Warlords of Draenor` counts. Deathwing, Garrosh and
the 7th Legion are all in this world and none of them is a rule.

The amendment that arrived with the direction change: a page created after the
cutoff that is right about Wrath should ideally be admitted.
`post_cutoff_wrath_signal` does it where the evidence is explicit — an infobox
`|patch=` below 4.0, an `|expansion=` naming Wrath or earlier, one of four
category names, with a Classic-2019 veto because WoW Classic's 1.13/1.14 patches
read as vanilla to every one of those rules. That reaches 15 of 20,407 late
pages. The rule that would reach the other 18,717 is a server-side id
cross-check, and it is deliberately not implemented: the wiki tooling reads
nothing from the server by design, so that is an operator decision (FOLLOW-UPS
62, ADR-0040).

Out-of-game pages moved with the same principle: `classifyMetaPage` runs at
build time and the build does not emit what it classifies. The search band,
`META_PAGE_LABEL` and the `metaPage` result field are gone, and with them the
carve-out that kept an exact-title hit at the top — the page is not there to
return. `search_reference`'s description loses the clause about labelled
paragraphs, since there are none, and keeps one fixed sentence: the bundle is a
Wrath-era snapshot of the wiki and describes this world, prefer what you can
observe in game.

`schema_version` stays 5 — no table changed — so a deployed bundle keeps
answering until it is rebuilt. The `pages_dropped_*` counters are what tells a
version-5 bundle built before this from one built after. The deploy is still
pending: swapping the bundle changes what every model reads, so per the ADR-0033
addendum it ships as a harness minor bump in a deploy window.

## The bundle keeps only what a character can act on

The era rules ask which world a page is about. A heading census over the
Wrath-snapshot revisions says that question was the smaller half of the problem:
`External links` sits on 66,140 pages and is 14.1% of raw bytes on its own, the
patch record another 1.4%, lore and story about 1.3%, and the commentary and
media set — trivia, quotes, speculation, galleries, videos, the other Warcraft
products — about 1.8%. None of that names a coordinate, an id, a giver or a
reward. The unambiguous candidates come to 16.3% of corpus bytes, all of it
reading cost inside a snippet window.

So a fixed heading drop set now runs at build time, on the raw wikitext, in the
same section walker the era cut already uses — heading line through the next
heading of the same or a shallower level, and nothing is rewritten. The era
check runs first, so a heading can never be counted under both. The match is on
the normalised heading (trimmed, case-folded, markup and trailing punctuation
gone) and it is exact, never a prefix or a substring: that is the whole reason
`changes` goes while `past changes` stays and `notes and trivia` goes while
`notes` stays. There is no keep list in the code — only the drop set exists, and
what was considered and deliberately kept (`notes`, `tips`, `tactics`,
`strategy`, `abilities`, `drops`, `source`, `objectives`, `description`,
`progress`, `completion`, `rewards`, `gains`, `quests`, `location`) is written
down in `wiki/README.md` instead.

A third pass runs last, after the paragraph rules, because those rules are
themselves a source of orphan headings: a section whose subtree carries no prose
after everything is stripped is not emitted at all. The test is on the subtree
rather than the direct body, so a heading with no text of its own but an
occupied subsection survives while an empty subsection of an occupied section
still goes.

`sections_trimmed` is the total and `sections_trimmed_json` the per-heading
breakdown, keys sorted so two builds from the same dump write the same string,
with empty-section removals under `(empty)`. The era counters stay separate — a
regression in one should not be able to hide in the other. The one wording debt:
a page that was nothing but a link list now empties and lands under
`pages_dropped_post_wrath`, which is the wrong name for the right outcome, and
the five-reasons-plus-`empty_pages` identity the build test asserts is not worth
widening for it.

Follow-on to item 49; the deploy is still pending with the rest of the era work,
since this changes what every lane can read. The staged bundle at

## The stripper survives a nested infobox, and protection starts at the announcement

Two residue items from 49, and the first one was not where the note said it was.

**Item 63.** The Orgrimmar canary failure was blamed on `removeBraced` never
returning to depth 0 on a multi-line infobox with nested template arguments. It
does not, but that is the symptom. An instrumented scan of the page's own 2010
revision — a stack of openers, printing what is still unclosed at end of input —
named the `{{infobox zone}}` opener and nothing else, on a page whose braces
balance. What unbalances them is upstream of the brace scanner: `CONTAINER_TAGS`
matches `<(ref|gallery|…)\b[^>]*>`, and `[^>]*` happily swallows the slash of a
repeated citation written `<ref name="Errata" />`. The regex reads that
self-closing tag as an *opening* one and deletes everything to the next
`</ref>`: 1,486 characters on that page, including the `}}` that closed the
infobox. After that the scanner is counting a document that really is
unbalanced, and it discarded the whole page. A `(?<!/)` before the closing angle
bracket is the fix; `SELF_CLOSING` already handles the tag itself.

The scanner is hardened as well, because the same page class has two more ways
to lose. Braces are now consumed a **run** at a time, `floor(run / 2)` on each
side: reading two characters at a time made the third brace of `{{{param|x}}}`
open a `{|` table that nothing ever closes, and the mirror case over-closed and
leaked a template's own fields out as prose (a synthetic achievement box in the
test file pins both directions). And a closer now matches its opener's kind, so
a `{|` written inside a template argument cannot eat the template's `}}`.
Finally, unbalanced input costs a paragraph rather than a page: an opener still
unclosed at end of input keeps the prose before it as before, and the strip
resumes at the first blank line after it, on the assumption that a malformed
template does not cross a paragraph boundary. Only when there is no blank line
after it does the tail go with it.

Measured over the dump, read-only, on the same definition before and after —
non-redirect pages whose newest pre-2010-10-12 revision strips to the empty
string while its raw text holds at least 200 characters of non-template prose:
**47 → 11**. Attribution, measured by stubbing each piece out rather than
asserted, because a fallback that carries the recovery would mean the defect was
never found: the ref fix alone recovers **22** of the 47, the run-and-kind
scanner with the paragraph fallback stubbed out takes it to **28**, and the
fallback carries the last **9**. So the root cause is the ref fix and the
scanner — 28 of 37 — and the net is a real net, not the whole rescue. The 11
that remain are recipe tables, imagemaps and season-comparison tables — pages
that are genuinely nothing but tables, where the ≥200 measure is counting cell
text. Orgrimmar, Scarlet Crusade, Red dragonflight, Syndicate, Twilight's Hammer
clan, Gnoll, Burning Blade clan and Crystalsong Forest are the largest
recovered.

It costs text in one direction, and the sample says how much. Of 2,457 pages
that stripped non-empty before (a 1-in-37 sample of the snapshot), exactly one
strips to nothing now: an achievement box that is a bare `<onlyinclude>`
transclusion with no prose at all, whose criteria line the old over-closing bug
leaked out of the template as if it were the page. That is the leakage fix
working, not a regression; extrapolated, roughly 35 to 40 pages dump-wide lose

## A page the section trim empties keeps its row

A full rebuild said `dropped: 22890 post-cutoff, 10027 post-Wrath`, and the
post-Wrath number should have been about five thousand: 6,935 pages carry a
post-Wrath signal on their era revision, 1,429 of them have no pre-cutoff prose
and are counted post-cutoff instead, and 489 are protected. The other five
thousand were pages the **section trim** emptied. `build.ts` had one branch for
a page that came out with no prose — had it prose before? then a cut took it,
call it post-Wrath — and that branch could not tell the two cuts apart.

Trimming an external-links section is not evidence that a page is from a later
world. It is evidence that the page's body was a link list, which is true of
28,471 sections the same build reported under `(empty)`. And dropping the row
threw away more than prose: the title, the `page_ids`, the `page_coords` and the
`page_quest` rows went with it, which is why id rows had fallen 71,231 → 64,284
between the pre-era bundle and this one. An NPC page whose body was an infobox
is still that NPC, and an exact-title or id query is exactly the query it
answers. Three of the first empty rows in the fixed build are `"Charlie"
Northtop`, `"Mad" Jonah Sterling` and `1000 Daily Quests Complete`.

So the discriminator is the **trim-only** text, not the era-only text: run the
same section walker with the era half switched off (`dropOutOfWorldOnly`, one
walker, an `eraCuts: false` option) and ask whether anything would have
survived. Something survives → the era cuts are what emptied the page and it is
dropped as post-Wrath; nothing survives → the page was a link farm or an
infobox, and it stays as an empty row. Era-only text was the first attempt and
is wrong: a Cataclysm page that also has an external-links section still has
prose in its era-only text, so it would have been kept. The trim-only text is
computed on demand, only for a page that came out empty, because the
empty-section sweep strips every section body to decide; the full build cost 3
seconds of 56.

Empty rows are rows, not FTS documents. A page with no body is the shortest
document in the index, and letting bm25 rank its title against pages that have
something to say would trade a real regression for the recovered ids. It is
found by exact title and by id, which is what it is there for.

## An empty reference page answers with what it states, or not at all

Keeping infobox-only pages as rows (9f06265) left roughly 6,900 pages with empty

## A redirect that dangles does not answer for its title

The canary caught a real one: 53 of 54, missing `Scarlet Monastery`. The page is
correctly absent — its first revision is 2012 — and this world's article is in
the bundle under `Scarlet Monastery (original)`, exactly the shape the sibling
rule exists for. It did not fire.

The cause was one line in the order of the two rules. `siblingRedirects` is told
which titles already answer so it leaves them alone, and the build was passing it
every kept page *plus every pending redirect source*. A source is not an answer:
the candidate still has to walk to a page, and the one that shadowed this title
never did. A lower-cased spelling of the title, `Scarlet monastery`, redirected
to the bare title; the bare title had no page; the row was dropped as dangling
and never written — but its source had already put `scarlet monastery` into the
answered set, so the sibling rule skipped the key and the article sat under a
title nobody types. The alternate spelling and `The Scarlet Monastery` were dead
rows for the same reason, and the case-variant candidate was in fact a self-loop:
source and target share a lower-cased key, so the walk burned its six hops.

So the resolution runs in two passes now. Every candidate the stream produced is
walked first; one that leads nowhere is held back rather than dropped. The
sibling rule then runs over the titles that are still unanswered — a kept page,
or a redirect that actually landed — and its candidates go into the same target
map, overwriting the dead entry for that key. That overwrite is the load-bearing
part and is commented as such: it is what lets the held-back rows land on the
retry, which is how `Scarlet monastery` and `Scarlet Cathedral` come back with
the name they were pointing at. A sibling is now only ever made from a page or
from a redirect that landed, so it can no longer point into a dead row.

Measured on a full rebuild, canary on: redirects 13,368 → 13,413, dangling
3,206 → 3,173, `(original)` siblings 63 → 75. The twelve new siblings are all
this world's — `Scarlet Monastery`, `Molten Core`, `Zul'Gurub`, `Zul'Aman`,
`Ignite`, `Seal of Justice` and six more — and the other 33 rows are the ones
that were pointing at those bare titles all along. `verify.ts` is green on that
bundle: 54 required pages, 19 forbidden titles, 28 phrase checks. The

## The build may ask the world DB whether an id exists

Mark approved the open decision ADR-0040 left (FOLLOW-UPS 62): the build — not
the agent, not the runner — may use the world DB as an existence oracle for the
late pages that say nothing about their era. `infra/export-world-ids.sh` writes
the four id sets to `data/wiki/world-ids.json` (quest 9,464, creature 29,947,
item 46,096, gameobject 21,580; server-derived, stays out of git) and
`--world-ids` feeds them to the build, which admits a page with no pre-cutoff
revision when an id it states about itself is one of them. An export file rather
than a live query, so the build stays a function of files and reproducible from
them. `spell` and `unknown` ids never match, the post-Wrath and Classic vetoes
still stand ahead of the door, and `meta.world_ids` records the export's
identity — or `none`, when the flag was absent.

The interesting part is the number. The rule was approved on "≈18,700
undecidable late pages, most of them real here"; it admits **145**. A control
rebuild without the flag reproduces the current bundle counter for counter
(81,217 kept), and with it the bundle is 81,368 rows: 145 admitted pages and 6
more empty rows. The reason is that the undecidable population is not what the
census implied — 16,010 of the 22,727 late pages state no id at all (lore,
tactics, disambiguation), and of the 6,717 that do, nearly all state an id in
the 40,000–130,000 range this server has never had. A hand-check of 18 admitted
titles found 5 false: Aeonaxx, Daakara, Grotto Vole, Feral Vermling and Guild
Herald are Cataclysm-or-later pages carrying a 3.3.5 id, either inherited (the
Cataclysm Zul'Aman boss states Zul'jin's 23863) or copy-pasted (three unrelated
pages all state `itemid=44822`). So the door buys 0.18% coverage at roughly 0.7
precision, and the levers if it ever matters — name agreement, and distrusting
an id many unrelated pages claim — are written down in item 62 and not built.
Canary and `verify.ts` are both green on the flag build, but neither can see
this: verify's forbidden titles are zones and dungeons, and every false admit is
a mob or an item.

An exhaustive review of all 151 rows followed — two reviewers, every title
judged, DB names joined in — and it came back 94 true / 57 false, precision
**0.62**, worse than the 18-title sample. It also found the fix, which was
already written down as an unbuilt lever: nearly every false admit states an id
the DB knows under a different name. So the export carries id→name now
(`LogTitle` for quests, `name` for the other three, ~3 MB) and the door requires
agreement between the DB's name and the page's subject — the title minus its
namespace prefix and its trailing parentheticals, compared as words with case
and punctuation folded, one name's words being all of the other's. Word
containment and not substring, because `car` sits inside `carnie`; measured over

## The resolved ledger is gone from FOLLOW-UPS

It existed to make a citation resolve: an ADR or a commit message says "item 64",
the item has left the open list, and the ledger was the one line that said what
that number meant. Reasonable, and it worked — but at 64 entries and 20.5k
characters it was **larger than the open list it was appended to**, so a file
whose whole job is "what could someone pick up" opened as an archive. That is the
liability, and it grows by construction: every item that closes makes the archive
longer and the list shorter.

All 64 entries were folded verbatim into the day file for the date each was
resolved on — 22 to 2026-08-22, 21 to 2026-08-23, 21 to today — under a section
explaining where they came from. Nothing was summarised or dropped; every entry
carried a date and none needed a judgement call about where it belonged. The
citation still resolves, just one grep further out:

    grep -rn "item 64" docs/worklogs/

FOLLOW-UPS went from 37.7k characters to 17.4k, and is now 11 real open items
(plus the three Next-up pointers). The header, `docs/WORKLOG.md` and CLAUDE.md's
working-memory rule were all updated together — a convention changed in one place
and left stale in the other two is worse than not changing it.

One thing worth stating so it is not rediscovered: the day-file
`shipped: item N — commit — where it lives` line is **no longer optional
bookkeeping**. With no ledger it is the only bridge between an old citation and
what that number meant, which is why CLAUDE.md now says so explicitly.

## Three small items close: 61, 74, 72

**61 — a replay reopens where it was left** (`6ac93d7`). The cursor is deliberately
not a URL parameter, because the play slider would rewrite history four times a
second; the cost was that every route back into a replay dropped the operator at
hour zero. It is now remembered beside the route instead of in it — a module-scope
`Map<runId, ts>`, in memory only, because `localStorage` would hand back
yesterday's scrub against a track that has since grown. `resume` does not trust
the memory: a timestamp the freshly loaded track no longer covers falls back to
the first sample. Module scope is load-bearing, since the reported case unmounts
`MapPage`.

The detail worth keeping: `remember` is called from the two places the operator
deliberately moves the cursor, and NOT from an effect watching `cursor()` —
`clearReplayState` sets it to zero on the way out, and an effect would have
recorded that zero as where they left off. Verified independently: four
`setCursor` writers, and only the two deliberate ones remember.

**74 — a freeplay row shows its clock when the run recorded one** (`386750d`,
after `b4f85c4` pinned the other half). `rowProgress` gated on
`episode === "freeplay"` because the id is uncapped, so a percentage would read as
a tier fact. **Measured against the runs on disk, that gate was wrong for half the
population**: four of eight freeplay runs carry an enforced `21_600_000` — every
session under `idle: "unlimited"` does, and a watchdog ends it there — and four
carry null. The discriminator was never the episode id; it is whether this run
recorded a budget, which the next line already checked. Dropping the name gate
shows a real clock for the capped half and changes nothing for the uncapped half.
What must never appear is a percentage against a TIER's nominal budget, and
`budgetMs` is never that.

**72 — why the `SMSG_INITIAL_SPELLS` decoder tolerates a lying count** (`9f5202f`).
Comment only; the tolerance is structural, not luck. The loop bound is
`i < cdCount && p.rpos() + 16 <= p.size()`, a tuple is exactly 16 bytes, and
cooldowns are the packet's final field — so an over-declared count terminates on
the buffer rather than the count, yielding exactly the rows present. Traced and
re-verified rather than accepted. No test: C++ decode is unreachable from
`bun test`, which the item said and remains true.
