## Muse Spark 1.3 freeplay: cost baseline, and freeplay turned on

Mark asked what a continuous freeplay stream on Muse Spark 1.3 would cost per day
before committing to one. The measurement, off the two finished e90s:

- **$0.271 and $0.266 per 90-minute episode**, provider-reported. Pricing the token
  counts by hand off `runner/viewer/prices.openrouter.json` reproduces both to within
  0.5%, so the reported figure and the price table agree and either can be trusted.
- **~$0.179/hour → ~$4.30/day, ~$129/month** at continuous occupancy.
- The number is linear in wall-clock because **context plateaus**: ~21k prompt tokens
  per call from minute 10 onward, flat to the end. The 32-hour minimax freeplay stream
  shows 18.9k tokens/call over a full day, so the plateau holds across a day and not
  just an episode. Cost per hour therefore does not grow with session length.
- The real error bar is call *pace*, not token size. Spark ran 242-268 calls/h, with
  the fast group (minimax 258, sonnet-low 178-328); some nemotron freeplay sessions
  collapsed to 7-95 calls/h. If it stalls that way the bill is nearer $2/day. Range
  $2-4.30/day, central estimate $4.30.

Both finished e90s reached **level 5** and ended on the episode wall, not on a stall —
it stays productive for the full 90 minutes.

`roster."muse-spark-13".idle: "unlimited"` is the whole change. An earlier draft of this
analysis claimed a freeplay stream on the single paid lane would starve the other paid
models; that was wrong and is worth recording as wrong. `planNextJobs` orders evidence,
then probe campaigns, then idle work, and the extras loop takes only "accounts nothing
else wanted... never one a counted run could have used" — so freeplay cannot displace a
counted run at scheduling time. `--status` confirms the practical side: every other paid
entry reads `targets met`, so the paid queue is drained and the stream will take an idle
slot rather than a contested one.

What is true, and is the only thing to keep in mind: a **live** stream is not preempted
by scored work that arrives later. `policyJobDropped` drains a live policy job only when
its ref leaves the roster or its `idle` flips to `"none"`; account-busy and the paid cap
are transient and deliberately do not drain it. So a newly added paid model waits behind
a stream that can run 12-38h. The remedy is the one-line flip to `idle: "none"`, which
SIGTERMs the stream at once and pauses it to resume in place later. Worth remembering
given two paid models were added today.

Freeplay will not start immediately: `muse-spark-13` promoted to t1>t2 and now reads
e90 2/3, e360 0/1, so it owes one more e90 and a six-hour e360 before its targets are
met and it becomes an extras candidate.

## Shared chart-axis reactivity

The shared `XAxis` and `YAxis` components now keep each tick's coordinate and
formatted label as Solid accessors. When a chart changes its mapping or
formatter while primitive tick values survive, the retained SVG nodes update
in place instead of holding the old episode's positions or text. LadderChart
and StreamChart remain unchanged consumers of the shared components.

A focused `happy-dom` regression mounts both axes, changes the mapping factors
and label prefixes, and asserts both values and node identity after the
reactive update. The dashboard README now documents the focused component
coverage and the small test dependency.

Verification, on merge into master (Linux): root `bun test` is 2850 pass / 0 fail,
`bun run typecheck` and the dashboard build are clean. The 59 failures the branch
reported were its macOS host being unable to load `libc.so.6` for the runner sandbox
suite, and do not reproduce here. The regression was also checked the way a regression
test has to be — reverting `ChartParts.tsx` to its pre-fix state fails it on 9
assertions, so it is pinning the behaviour rather than restating it.
