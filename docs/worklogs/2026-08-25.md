## Ladder scatter — cost per run against xp earned

Operator's request: a point chart on the ladder, x the average cost per task for
the selected episode, y the XP earned, above the table; drop `all`, overridden
and the harness filter from the ladder; drop the filter-note text; point the
episodes page's filtering at the ladder rather than runs.

What "task" and "XP earned" mean, since neither is on the wire as such:

- **x = mean cost per run** over the entry's counted (scored, series-filtered,
  character-filtered) runs on the tier. A run's cost is the provider's reported
  figure when it reported one, else `CostView.expected` — the price table over
  the run's own tokens, which is $0 for a free tier or local hardware and
  as-if-metered for a subscription. The runs table deliberately shows only the
  reported figure; the chart takes the fallback because a free model has no
  reported figure ever and its honest cost is zero, not blank. The point's hover
  says which basis fed it and over how many of its runs.
- **y = mean XP earned** over the same runs, where a run's XP earned is the
  viewer's new `xpEarned`: the run page's cumulative-chart lower bound (last
  observed within-level xp of every level below, plus the xp within the top
  one), computed server-side so the two cannot disagree.
- One point per `(model, effort)` — `sonnet (low)` is its own point — because
  effort is a roster dimension. Unscored runs never enter. An entry with no
  reading on either axis is named under the chart, never plotted at zero.
- Linear axes with 1/2/5 ticks from zero; free models sit on the y axis. Labels
  are placed greedily around eight slots per point. Points are coloured by
  harness with the table's own semantics (`--accent` wrathbench, `--claude`
  claude-code, `--dim` mixed) and link to `/runs?model=…&effort=…&episode=…`.

Where it lives: maths in `dashboard/src/lib/ladder.ts` (`ladderPoints`,
`niceTicks`, `ladderChartLayout`, `runCostReading`, `xpEarnedOf`) with tests in
`dashboard/test/ladder.test.ts`; the SVG in
`dashboard/src/components/LadderChart.tsx`, hand-drawn like `XpChart`.

Viewer: `ResultRun` gained optional `xpEarned` and `expectedCost`
(`runner/viewer/api-types.ts`, `results.ts` `xpEarned()`, `api.ts`

## Achievement and flight milestones recorded; rung 4 derives fully

Second track for ADR-0048 (issue #8): the module's new taps existed but nothing
read them. Written against `module/PROTOCOL.md` and fixtures only — the
worldserver still runs the old image, so no live run has emitted one of these
yet and nothing here was verified against a core (FOLLOW-UPS 79 is still the
deploy).

**SDK.** `SMSG_ACHIEVEMENT_EARNED`, `SMSG_ALL_ACHIEVEMENT_DATA` and
`SMSG_ACTIVATETAXIREPLY` get schemas and fold into the state cache.
`state.self.achievements` is `{ entries, points, loginSeen }`, one entry per
achievement in observation order, each tagged `source: "login" | "earned"` —
the backlog a client gets at login is history, an earn is a thing that just
happened, and that distinction is what keeps a resumed run from re-reporting
its own past as firsts. First writer wins on an id, so a re-login cannot double
a points total. `points` sums only what the module could name from
`Achievement.dbc`: a lower bound, never a guess. The say-range broadcast is
filtered here, at the cache: `self !== true` never enters, so no consumer can
forget. `self.taxiFlight` is derived from the `UNIT_FLAG_TAXI_FLIGHT` bit on
`unitFlags` rather than from the module's named boolean, because `self.fields`
holds numbers only and a boolean in it would be a lie about the type; it is set
only from a block that actually carried `unitFlags`, so the observation keeps
its packet's provenance. `self.taxiReply` holds the last reply. No `fly()`
helper — activation stays raw (ADR-0015).

**HUD.** One line, `achievements: N (P pts)`, and `unobserved` when no
achievement packet has arrived. Not the list: that is tens of lines of prompt
every turn for something a snippet can read off `state.self.achievements`, and
the ids are on the trajectory anyway.

**Producer.** In the same sampler as the zone/area marks:
`{ kind: "achievement", id, name?, points?, categoryId? }` per own earn,
`{ kind: "achievements_at_login", ids, points }` once per process, and
`{ kind: "taxi", from: { areaId } }` / `{ kind: "taxi_landed", to: { areaId } }`.
Three decisions worth the words:

- The login record is written **even when the backlog is empty**. It is the only
  thing that says the taps were live for this run, and without it a run that
  flew nowhere and a run from before the deploy are the same file. With it,
  `{ flights: 0 }` becomes representable and `null` keeps its one meaning.
- Recorded achievements are tracked **by id**, not by a high-water mark: a
  sandbox restart re-reads the whole backlog, and the second pass must write
  nothing rather than re-announce the run's history.
- A takeoff is only `false → true` **after an accepted reply**. A first
  observation of `true` seeds the flag silently — a process that opens mid-flight
  joined a flight, it did not start one. A landing is recorded either way,
  because it is its own observation.

The area id is keyed `areaId`, not `id`, so no consumer can mistake a flight
record for an area mark. `MilestoneLine` is now a union over the five kinds.

**Viewer.** `scanRunTotals` picks both out of the pass it already makes;
`achievementFactsFrom` unions the ids and takes points from the *last* backlog
record plus every earn outside it (a resumed run's later backlog is a superset,
so summing them all would count the same achievement once per resume);
`taxiFactsFrom` counts takeoffs and returns null only when nothing — no taxi
record and no achievement record — proves the taps were live. `ResultRun` gains
`achievements` and `taxi`. The run page reads them off `TrajectoryTail`, which
now accumulates the marks as it indexes (cleared on the shrink path with the
rest of the index), so a live run's line grows with the file instead of missing
the whole-file cache on every 10s poll; both paths call the same pure
derivations, so the two pages cannot disagree.

**Ladder.** Rung 4 tests `capitalZone !== null && (taxi?.flights ?? 0) >= 1` and
its rule text says exactly that, including that a pre-deploy run has no flight
record and cannot pass. No tri-state was added: a cell is "reached" as soon as
any of the model's runs passes, so a run that cannot answer says nothing about
one that can — the rung-2 precedent from this morning. Achievement points are
displayed only; the ordering is still highest rung, XP, gold (ADR-0018/0043) and
nothing is added to anything.

typecheck` green for every project, dist rebuilt. Runs were live: no deploy, no
viewer restart, no worldserver restart.

## Scored runs fail and retry instead of resuming (ADR-0049)

ADR-0036 resumed every paused run, which was written to stop a deploy costing an
in-flight `e360`. It does stop that, and it buys it by recording a run that sat
out a two-hour quota window as ninety minutes of play. The operator's decision:
a scored run that pauses **was not a properly recorded episode**. It is a failed
attempt — ended, account and character released, a fresh attempt with a new run
id and a full clock — and after three counted failures on one (model, episode,
series) the model is tainted for that episode. Resuming stays the rule for
`freeplay` and becomes an opt-in per campaign (`campaigns.<name>.resume`,
default false).

The rule is one pure function, `classifyLapse` in `runner/src/lapse.ts`, read by
the supervisor, the roster and `--status` alike, with the whole thing as a table
test (`runner/test/lapse.test.ts`). Two judgement calls of Mark's are encoded in
it and stated in the ADR: an `operator-pause` (a fleet stop, a deploy) still
ends the attempt but does **not** count toward the three strikes, and neither
does an offline gap — both are the harness's doing. Provider pauses do.

Counting is one predicate and never a parsed detail string, which is what
settled the vocabulary: `attempt-failed` (new) is written exactly when the
failure counts, `manual` when the harness stopped it, `stale` (new) when nothing
came back for it. All three are in `NOT_THE_MODELS_FAULT`, so no target ever
counts one.

That set turned out to be two sets. The scheduler had `NOT_THE_MODELS_FAULT`
and the viewer's `unscoredReason` had its own list, so the first cut of this
change wrote a deploy-stopped `e90` off as `manual` in the policy and still drew
it on the ladder — at the level it reached the minute the fleet stopped, at
deploy scale, which is the exact failure the ADR exists to prevent arriving
through the back door. The set now lives in `lapse.ts` and both read it, which
also drops historical `manual`, `harness-error` and `stale-character` runs off
the ladder and out of the Episodes page's member count. That is the sentence
FOLLOW-UPS 78 is already written in. Those runs are not hidden: the Episodes
page grew a `lapsed` column for them and the runs page shows every one with its
reason, with the Models page still spending the attempt.

Three places had to change together or the decision would have been half-made.
The supervisor's `planResumes` now ends a lapse instead of listing it; a new
pure `planStaleRuns` sweeps runs with no pause record at all; and `run-roster`
had **two** resume paths of its own — the in-place `RESUME_BACKOFF` retry and
the defer ladder, whose stored `runId` is deliberately a resume target — so a
rate-limited eval would have come back regardless of what the supervisor
decided. Both are now short-circuited for a non-resuming lane by a
`resumeOnPause` flag the fleet writes onto the spec. The session goes back with
the run (`releaseRunSession`, split out of the roster's `freeSession`): a
provider-paused run keeps its module session alive on purpose, and ending one
without releasing it would land the promised fresh attempt on a held account.

Stale is now a sweep rather than a listing, measured from a run's own recorded
budget (12h for one with no wall clock) — that is the 12.7h outage case, which
had left a qwen pause dangling forever because it was past twice its budget and
so was never auto-resumed and never ended. `lastActivityOf` takes the pause mark
over the mtime rather than the max of the two: a paused run's directory is still
touched afterwards (meta.json, the session release), and a max() read those
seconds as hours of life.

A tainted model reports `blocked`, not `free`. That was the one place the
simple version was wrong: emptying `eligible` would have made three burnt evals
buy the model idle work. The manual queue still outranks the taint, which is
ADR-0034's rule and the second escape hatch beside `--clear-model`.

`--status` numbers the batch it is about to write rather than the projection it
read before writing any of it (`retryNumbers`): a sweep that ends three failures
of one model in one tick reads 1/3, 2/3, 3/3 — tainted, instead of "retry 1/3"
three times.

## State samples on a timer during long turns, on every driver (item 77)

Hoisted rather than ported. The claude driver's `setInterval` ticker became
`startStateTicker` in `runner/src/loop.ts`, and both drivers now call it — one
mechanism, model-agnostic, which is the whole point of the loop being shared.
Porting the pattern a second time into the openai-compatible path would have
left two copies of a timer whose stop conditions are the subtle part.

The tick is deliberately **not** derived from `stateIntervalMs`. It is a coarse
5s opportunity to sample; the interval is still the gate inside `sampleState`
that decides whether a row is written. That is the shape the claude ticker
already had (5s tick, 60s gate), and keeping it means the fast stub-adapter
tests that run with `stateIntervalMs: 1` and an ordered snapshot array are not
suddenly sampled by a 1ms timer that would consume their snapshots.

`sampleState` grew a one-at-a-time mutex: a caller arriving mid-sample joins the
promise in flight instead of starting a second one. The turn preamble needs the
snapshot for its state summary, so it joins rather than skips, and no high-water
mark (quests, zone/area, achievements, taxi) can be advanced by two readers at
once. `runLoop` gained a `finally` that clears the timer on every exit path —
`run.ts` closes the trajectory as soon as the loop returns, and a surviving
ticker would write state rows into a closed sqlite handle. Stopping *awaits* the
sample in flight, because `clearInterval` does not cancel one already waiting on
the sandbox — that trailing sample keeps its row but can no longer enforce
anything, the outcome having been decided. The timer is `unref`'d, so it can
never hold the process open.

Mid-turn samples feed the watchdogs the way they always did — `sampleState`
calls `noteProgress`, so idle and no-xp see real XP during a long call. They do
not *enforce* on the openai path: the fixed loop still terminates at the turn
boundary, as it always has, so the episode clock semantics do not change. Only
the claude driver enforces on each sample (the `onSample` hook), because it can
kill the CLI from outside the turn; the openai adapter's request is already
abandoned by the stop signal. Trajectory `state` records from the ticker are
indistinguishable from turn samples and carry the in-flight turn number, so
`viewer/results.ts` (reads by `ts`) and `MAX(turn)` are unaffected — nothing
keyed on one row per turn.

Test: a fake driver whose turn takes 300ms against a 25ms tick asserts at least
one `state` record lands between the `request` and the `response`, stamped with
turn 1, and that a concurrency counter on `stateSnapshot` never exceeds 1. It
fails (0 mid-turn samples) with the tick raised above the turn length. The
claude ticker tests are unchanged and still pass — `watchdogTickMs` now flows
into the shared helper.

Verified: `bun test` in runner 654 pass / 0 fail; `bun run typecheck` green
everywhere.

## The model names its character; fresh attempts prefer its account (ADR-0050)

The defect: after ADR-0049 a fresh attempt no longer returns to the account its
predecessor used, and the roster's fixed per-model name is realm-wide unique
while episode hygiene is per-account. `fleet-sonnet-e90-sonnet-20260825-a12`
launched on RUNNER3 at ~01:01 while `Fleetsonnet` — from the ended a10 run —
still stood on RUNNER5; hygiene cleared an already-clear RUNNER3 and the model
looped `char_create_failed_code_50` for eight minutes with no character in the
world. SIGTERMed by hand (operator-pause, retried).

Four changes, in the order they matter.

**The model names its own character** (ADR-0050, Mark's decision). The
fresh-launch session note moved out of `run.ts` into
`prompt.freshCharacterNote()` and now invites the model to pick a name — 2-12
letters, no spaces, no three identical in a row, the same rule
`isValidCharacterName` enforces everywhere else — with the roster's `character`
offered as the suggestion. `CreateSessionRequest.character` is required by the
SDK, so the note makes the model supply one; the runner cannot inject a default
into a call the model itself writes. Race and class are stated in the same note
as *not* the model's to choose, with the reason (they are the episode's
comparability dimensions). The resume note is untouched, "do not create a
different one" included.

**Code 50 says what to do about it.** `CHAR_RESPONSE_HINTS[0x32]` in the SDK now
renders "choose a different character name and call createSession again", in the
naming rule. Deterministic and model-agnostic, like every other row in that
table. No fail-fast termination was added — the earlier plan for one was dropped:
a failure the model can route around must not end its episode.

**The recorded character is the observed one.** `ContextBuilder.snapshot` writes
the name at the first sight of a character in the world through a new
`Trajectory.setCharacter`, which updates `run.character`, rewrites
`meta.json`'s `config.character` and appends a `character` record. Three places,
three readers: the runs page and the positions feed read the run row (`runs.ts`
already lets sqlite win over meta), and a resumed runner reads meta.json before
any database is open — so a resumed run's note names the character that actually
exists. `accountHeldBy` reads only the account and needed nothing;
`comparability.ts` has no `character`, so a model-chosen name marks nothing
incomparable. `--status` and the roster's launch line now say "suggested".

**Account affinity, and a cross-account sweep behind it.** `RunFact` gained
`character`; `affinityFrom(runs, roster)` gives each roster ref the account and
name of its latest run, and `takeAccount(free, prefer)` replaces the `shift()`
in `planQueue` and the index walk at the end of `planPolicyHeld`. A preference
only: a busy affine account is not waited for. `planNameSweeps` + `sweepNames`
are the fallback — when a fresh launch goes elsewhere and the old account is
free *this tick* (nothing holds it, nothing was assigned it), the stale name is
deleted there through `POST /character-delete`, the same client path hygiene
uses, with a random ≥32-char token because the module refuses weak ones. Best
effort, never fatal. `planTick` takes the affinity too, so `--dry-run` places
accounts the way the live tick would.

The other rows of that table got the same treatment: `0x59`-`0x5f` (no name,
too short, too long, invalid character, mixed languages, profane, reserved) were
unreachable while the harness assigned the name and are model-reachable now —
`createSession` validates race and class before the wire, never the name — so
each says which name to try next rather than only what was wrong.

Expect `character_not_found` in the sweep log routinely and read it as normal:
affinity takes the name from `meta.config.character`, which on a stillborn run
is still the harness's suggestion for a character that was never created. The
sweep is best-effort by construction, so a miss costs a log line.

ADR-0006 still holds and the proof is unchanged: `expectFreshCharacter` arms on
every guid hygiene *listed* and the first observation fails on a listed guid or
any level above 1 — neither reads a name. The new braces are that the note names
the survivors hygiene could not delete, because `createSession` reuses a
character of the name it is given.
