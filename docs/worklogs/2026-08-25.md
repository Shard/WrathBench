## Ladder scatter — cost per run against xp earned

Operator's request: a point chart on the ladder, x the average cost per task for
the selected episode, y the XP earned, above the table; drop `all`, overridden
and the harness filter from the ladder; drop the filter-note text; point the
episodes page's filtering at the ladder rather than runs.

What "task" and "XP earned" mean, since neither is on the wire as such:

- **x = mean cost per run** over the entry's counted (scored, series-filtered,
  character-filtered) runs on the tier. A run's cost is the provider's reported
  figure when it reported one, else `CostView.expected` — the price table over
  the run's own tokens, which is $0 for a free tier or local hardware and
  as-if-metered for a subscription. The runs table deliberately shows only the
  reported figure; the chart takes the fallback because a free model has no
  reported figure ever and its honest cost is zero, not blank. The point's hover
  says which basis fed it and over how many of its runs.
- **y = mean XP earned** over the same runs, where a run's XP earned is the
  viewer's new `xpEarned`: the run page's cumulative-chart lower bound (last
  observed within-level xp of every level below, plus the xp within the top
  one), computed server-side so the two cannot disagree.
- One point per `(model, effort)` — `sonnet (low)` is its own point — because
  effort is a roster dimension. Unscored runs never enter. An entry with no
  reading on either axis is named under the chart, never plotted at zero.
- Linear axes with 1/2/5 ticks from zero; free models sit on the y axis. Labels
  are placed greedily around eight slots per point. Points are coloured by
  harness with the table's own semantics (`--accent` wrathbench, `--claude`
  claude-code, `--dim` mixed) and link to `/runs?model=…&effort=…&episode=…`.

Where it lives: maths in `dashboard/src/lib/ladder.ts` (`ladderPoints`,
`niceTicks`, `ladderChartLayout`, `runCostReading`, `xpEarnedOf`) with tests in
`dashboard/test/ladder.test.ts`; the SVG in
`dashboard/src/components/LadderChart.tsx`, hand-drawn like `XpChart`.

Viewer: `ResultRun` gained optional `xpEarned` and `expectedCost`
(`runner/viewer/api-types.ts`, `results.ts` `xpEarned()`, `api.ts`
`listingFacts`). Optional so a dashboard against an older viewer still works;
the chart then says the viewer predates `xpEarned` and needs a restart. **The
8090 viewer was not restarted and needs one to serve the fields**; the render
check ran against a second viewer on 8091 from this checkout, since stopped.

Removed: `EpisodePicker`, `HarnessPicker` and `EpisodeFilterNote` from
`dashboard/src/components/EpisodePicker.tsx` (only `HarnessTag` remains there),
`harnessParam`/`HARNESS_CHOICES` and the `all` choice from `lib/episodes.ts`,
and the `includeOverrides`/`harness` arguments of `api.ladder`. The shell-wide
series selector (ADR-0046) and its note stay: that is the comparability group,
not the loop tag. `/api/ladder` still accepts the old query parameters; nothing
in the dashboard sends them.

Episodes page: the tier id and the member count link to
`/ladder?episode=<id>`; the overridden count links to `/runs?episode=<id>`
because the ladder has no overridden view any more.

A Solid detail worth remembering: a `<For>` template rooted at `<a>` inside an
`<svg>` is created in the HTML namespace and paints nothing; rooting it at
`<g>` puts the subtree in the SVG namespace.

## Playtime over-read on paused runs (fleet page showed 127%)

Morning report: `fleet-laguna-or-e90-laguna-s-2-1-20260824-a7` sat at 127% of its 90-minute budget. Not a data problem — every trajectory, state row and XP figure was intact and the `episode-limit` watchdog runs on its own persisted `episodeElapsedMs` (15 min for that run), so no run was cut short or scored on the wrong clock. The number was the viewer's derived `playtimeMs`: since 08cd691 (2026-08-23) the pause path calls `writeMeta({ pause })` milliseconds after `setPause`, which appends a `meta` record, and `segmentsFrom` let any `meta` reopen a closed segment — so each quota wait counted as driving. The a7 run had paused six times on OpenRouter's free daily cap, and 83 runs on disk carry pauses; every one of them listed after 08-23 over-read on the runs page, ladder cost-per-minute and time-to-level.

Fix: only the first `meta` opens a segment; `resume` alone reopens (runner/viewer/tail.ts, test added). Read-time computation, so all runs correct themselves on restart — a7 now reads 17.6 min, a10 41 min (was 239). Host viewer restarted.

## Ladder rungs 2 and 4 derive from the zone/area milestones

The ladder had been stale for two days for a boring reason: the producer shipped
without a consumer. Since a33c9f8 (2026-08-23) the loop writes
`{ t: "milestone", kind: "zone" | "area", from, to, turn }` on every change it
observes in the state cache, and 51 runs on disk carry them — but nothing read
them, so rungs 2 ("leave the starting subzone") and 4 ("reach a capital city")
still printed "not instrumented (FOLLOW-UPS 35)" while the data to answer both
sat in the trajectories.

Wired now, consumer side only — nothing about the recording changed, so this is
a derivation under ADR-0018 rule 3 and invalidates no run. `scanRunTotals` picks
the marks out of the streaming pass it already makes (above the request/response
early return, next to `claude_result`), `areaFactsFrom` derives
`{ startArea, distinctAreas, leftStartArea, capitalZone }`, and it rides to the
dashboard on `ResultRun.areas`, memoised on (size, mtime) like every other
per-run scan. Rung 2 tests `leftStartArea === true`; rung 4 tests
`capitalZone !== null` and follows the rung-3 precedent of saying in its rule
text what it did *not* read — the flight-master half is still unrecorded. Rung 6
stays not instrumented.

Two honesty details worth keeping. A run that wrote no mark reads `null`, never
`false`: everything before 08-23 has to be "not recorded", not "never left", and
`leftStartArea: null` covers the narrower case of a zone seen with no area. And
`startArea` is the *first* area mark, not "the mark with no `from`" — a resumed
run opens a second process whose `lastAreaId` starts unset, so several marks
carry no `from` and only the first is the start.

What the data says, over all 51 runs that carry marks: 45 of the zone marks are
Elwynn, 26 are Dun Morogh, and exactly three are a capital — all from
`fleet-nav-probe-coldridge-sonnet` (Ironforge, 11 areas, 88 area marks), which
is a probe run, unscored, and so reaches no ladder row. Nine runs recorded
exactly one area mark and never left it — five of them sonnet, which is worth a
look on its own — and no scored run has entered a capital. So rung 2 is a real
column with real misses in it, and rung 4 is honestly empty rather than blank.

## Achievement and flight milestones recorded; rung 4 derives fully

Second track for ADR-0048 (issue #8): the module's new taps existed but nothing
read them. Written against `module/PROTOCOL.md` and fixtures only — the
worldserver still runs the old image, so no live run has emitted one of these
yet and nothing here was verified against a core (FOLLOW-UPS 79 is still the
deploy).

**SDK.** `SMSG_ACHIEVEMENT_EARNED`, `SMSG_ALL_ACHIEVEMENT_DATA` and
`SMSG_ACTIVATETAXIREPLY` get schemas and fold into the state cache.
`state.self.achievements` is `{ entries, points, loginSeen }`, one entry per
achievement in observation order, each tagged `source: "login" | "earned"` —
the backlog a client gets at login is history, an earn is a thing that just
happened, and that distinction is what keeps a resumed run from re-reporting
its own past as firsts. First writer wins on an id, so a re-login cannot double
a points total. `points` sums only what the module could name from
`Achievement.dbc`: a lower bound, never a guess. The say-range broadcast is
filtered here, at the cache: `self !== true` never enters, so no consumer can
forget. `self.taxiFlight` is derived from the `UNIT_FLAG_TAXI_FLIGHT` bit on
`unitFlags` rather than from the module's named boolean, because `self.fields`
holds numbers only and a boolean in it would be a lie about the type; it is set
only from a block that actually carried `unitFlags`, so the observation keeps
its packet's provenance. `self.taxiReply` holds the last reply. No `fly()`
helper — activation stays raw (ADR-0015).

**HUD.** One line, `achievements: N (P pts)`, and `unobserved` when no
achievement packet has arrived. Not the list: that is tens of lines of prompt
every turn for something a snippet can read off `state.self.achievements`, and
the ids are on the trajectory anyway.

**Producer.** In the same sampler as the zone/area marks:
`{ kind: "achievement", id, name?, points?, categoryId? }` per own earn,
`{ kind: "achievements_at_login", ids, points }` once per process, and
`{ kind: "taxi", from: { areaId } }` / `{ kind: "taxi_landed", to: { areaId } }`.
Three decisions worth the words:

- The login record is written **even when the backlog is empty**. It is the only
  thing that says the taps were live for this run, and without it a run that
  flew nowhere and a run from before the deploy are the same file. With it,
  `{ flights: 0 }` becomes representable and `null` keeps its one meaning.
- Recorded achievements are tracked **by id**, not by a high-water mark: a
  sandbox restart re-reads the whole backlog, and the second pass must write
  nothing rather than re-announce the run's history.
- A takeoff is only `false → true` **after an accepted reply**. A first
  observation of `true` seeds the flag silently — a process that opens mid-flight
  joined a flight, it did not start one. A landing is recorded either way,
  because it is its own observation.

The area id is keyed `areaId`, not `id`, so no consumer can mistake a flight
record for an area mark. `MilestoneLine` is now a union over the five kinds.

**Viewer.** `scanRunTotals` picks both out of the pass it already makes;
`achievementFactsFrom` unions the ids and takes points from the *last* backlog
record plus every earn outside it (a resumed run's later backlog is a superset,
so summing them all would count the same achievement once per resume);
`taxiFactsFrom` counts takeoffs and returns null only when nothing — no taxi
record and no achievement record — proves the taps were live. `ResultRun` gains
`achievements` and `taxi`. The run page reads them off `TrajectoryTail`, which
now accumulates the marks as it indexes (cleared on the shrink path with the
rest of the index), so a live run's line grows with the file instead of missing
the whole-file cache on every 10s poll; both paths call the same pure
derivations, so the two pages cannot disagree.

**Ladder.** Rung 4 tests `capitalZone !== null && (taxi?.flights ?? 0) >= 1` and
its rule text says exactly that, including that a pre-deploy run has no flight
record and cannot pass. No tri-state was added: a cell is "reached" as soon as
any of the model's runs passes, so a run that cannot answer says nothing about
one that can — the rung-2 precedent from this morning. Achievement points are
displayed only; the ordering is still highest rung, XP, gold (ADR-0018/0043) and
nothing is added to anything.

viewer restart, no worldserver restart.
